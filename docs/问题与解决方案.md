## 一、检索与重排序

### 1. 重排序截断导致“假知识缺口”

**现象**

问“客服几点在线？收到货破损怎么办？”时，系统回答“暂无相关资料”，运营台出现知识缺口。但知识库中确实有这两条 FAQ。

**根因**

为降低 CPU 重排序耗时，最初把每个候选块的正文直接截断为前 240 个字符。FAQ 类分块通常把“问 / 答”放在块尾，关键词与答案都被截掉：

- 重排序分数从 `0.9404` 掉到 `0.0961`；
- 低于 `RERANK_SCORE_THRESHOLD=0.25`，候选被全部过滤；
- `_filter_qualified` 返回空列表，触发知识缺口记录。

**解决**

`app/services/reranker.py::_build_passage` + `_excerpt_text` 改为**按查询相关性选摘要**，而不是简单取头部：

1. 标题、章节始终保留；
2. 正文按行切分，同时构造“单行”和“相邻两行”两种候选单元（覆盖 FAQ 的问/答两行）；
3. 用查询的中文双字片段、英文/数字整词给行打分，问句结尾额外加分；
4. 在字符预算内按分数从高到低选取互不重叠的单元，再按原文顺序拼接；
5. 最终仍受 `RERANK_PASSAGE_CHARS` 限制，CPU 耗时不回退。

**回归验证**

- `tests/test_reranker.py::test_rerank_excerpt_keeps_relevant_tail_fact`：预算 80 字时仍保留 `9:00-22:00`；
- `tests/test_reranker.py::test_rerank_caps_candidates_and_truncates_passages`：候选数与长度上限生效；
- 线上复测该问题重排序分数恢复到 `0.9404`，不再产生假缺口。

**经验**

> 重排序截断可以省时间，但**不能按固定位置截断**。RAG 的答案经常在块尾，必须按查询选片段。

### 2. CPU 上响应慢（50–57 秒）

**现象**

一次完整问答耗时约 50–57 秒，历史日志中最慢达到 110 秒。用户感知为“系统卡住了”。

**误导点**

日志中“检索召回”是在重排序**之前**打印的，之后到 LLM 首个 httpx 请求之间出现约 50 秒空档，第一眼容易误判为 LLM 慢。实际单独测 LLM，首 token 约 1 秒。

**根因**

`BGE-reranker-v2-m3` 是交叉编码器，在 CPU 上耗时近似与「候选数 × 文本长度」成正比。原配置：

- `RERANK_CANDIDATE_K=20`（20 个候选）；
- 每个候选使用接近完整父块（数百到上千字）；
- `RERANK_MAX_LENGTH=512`；
- `RERANK_BATCH_SIZE=8`（CPU 上批量反而更慢）。

20 个长文本对在 CPU 上单次可达数十秒。

**解决**

| 措施 | 配置/代码 | 效果 |
|---|---|---|
| 收紧候选数 | `RERANK_CANDIDATE_K=6` | 线性减少对数 |
| 按查询选摘要 | `RERANK_PASSAGE_CHARS=240` | 显著缩短每对文本 |
| 降低最大长度 | `RERANK_MAX_LENGTH=256` | 减少 padding/计算 |
| 批量设为 1 | `RERANK_BATCH_SIZE=1` | CPU 上避免大 batch 的调度开销 |
| 启动预热 | `app/services/warmup.py::warmup_models` 依次加载 intent BERT、BGE-M3、reranker 并各跑一次短推理 | 首个请求不再承担加载与冷启动耗时 |
| 空闲保活 | `app/services/warmup.py::keep_warm_loop`，周期 `MODEL_WARMUP_INTERVAL_SECONDS`（默认 600 秒） | 长时间空闲后首个问答不再退化数倍 |
| 分阶段日志 | `app/services/retrieval.py::_log_retrieval_timing`、`app/services/reranker.py::rerank`、`app/services/chat.py::stream_reply` | 一眼看出瓶颈在 embed / vector / bm25 / rerank / LLM |

**效果（本机 CPU 实测）**

- 重排序：约 4.8–10.3 秒（典型 5–7 秒）；
- 检索总耗时：约 5.8–11.5 秒；
- TTFT：约 8.0–15.5 秒；
- 端到端：约 8.5–16.7 秒（典型 12–13.5 秒）。

**后续复核：空闲后单次问答 39.5 秒**

同一台机器在服务空闲约 47 分钟后提问“我想在你这里买件短袖,有什么推荐啊”，端到端耗时 39.5 秒。分阶段日志：

| 阶段 | 耗时 | 说明 |
|---|---|---|
| 意图识别 | 0.85 秒 | 冷启动，热态约 0.02–0.3 秒 |
| 查询准备 | 10.43 秒 | 其中 HyDE 生成等待 8 秒超时，随后回退 direct |
| 向量化 | 2.32 秒 | 热态 0.19–0.48 秒 |
| 向量检索 | 0.57 秒 | 正常 |
| BM25 | 0.27 秒 | 正常 |
| 重排序 | 22.25 秒 | 热态 4.19–5.52 秒 |
| 首 token | 1.34 秒 | 正常 |
| 其余流式输出 | 1.44 秒 | 正常 |

两个独立问题叠加：

1. **HyDE 误触发**：问题含“推荐”且长度 ≥12，命中抽象线索，被升级为 HyDE；生成超时 8 秒后仍回退 direct，8 秒完全没有产出。商品推荐类问句应直接检索。
2. **冷启动**：服务长时间无推理，首次调用时模型换入、线程池与 CPU 频率恢复，三个模型分别慢 3–4 倍。仅“加载权重”不足以消除该开销，必须真正执行一次推理。

**解决**

| 措施 | 配置/代码 | 效果 |
|---|---|---|
| 收紧 HyDE 线索 | `app/services/query_strategy.py::_rule_strategy` 移除“推荐 / 介绍” | 商品推荐问句保持 direct |
| 缩短策略超时 | `STRATEGY_TIMEOUT_SECONDS=4.0` | 即使生成失败，最多损失 4 秒 |
| 预热含推理 | `app/services/embedding.py::warmup`、`app/services/reranker.py::warmup`、`app/services/intent_bert.py::warmup` 均执行一次极短推理 | 首个请求不再承担冷启动 |
| 周期保活 | `app/services/warmup.py::keep_warm_loop`，`MODEL_WARMUP_INTERVAL_SECONDS=600` | 空闲后仍保持热态 |

**回归验证**

- 启动日志出现三条 `模型预热完成`，之后每 600 秒出现 `模型保活完成`；
- 每次检索出现 `检索耗时 ... embed/vector/bm25/rerank/total`；
- 每次回答出现 `回答完成 ... intent/prep/retrieval/ttft/latency`；
- 361 项后端测试全部通过。

**公网部署后再复核：重排序 15–20 秒**

部署到公网后连续三次提问：

| 时间 | 问题 | embed | rerank | 端到端 |
|---|---|---|---:|---:|
| 00:21 | 冬天马上要到了，有什么衣服推荐吗 | 1737ms | 15.34s | 21.38s |
| 00:22 | 好的，我注意是想买个羽绒服 | 1415ms | 20.29s | 25.13s |
| 00:23 | 衣服满多少钱包邮 | 1292ms | 20.14s | 24.07s |

保活日志在 23:58 / 00:08 / 00:18 均正常，排除冷启动。关键线索是同一时段 `embed` 从热态 0.26 秒涨到 1.3–1.7 秒（约 5 倍），说明**宿主机 CPU 被其他进程抢占**，重排序随之被放大 2–3 倍。

空载复测同一批 240 字文本：

| 配置 | 重排序 |
|---|---:|
| 6 候选 × 240 字 @256 | 7.6–9.3 秒 |
| 5 候选 × 160 字 @192 | 4.7–5.5 秒 |
| 4 候选 × 160 字 @192 | 4.0–4.3 秒 |

单候选开销约 1.0–1.3 秒，减少候选数比缩短文本更有效；`torch` 线程数 4/6/8/12 实测无差异。

**解决**

| 措施 | 配置/代码 | 效果 |
|---|---|---|
| 收紧候选 | `RERANK_CANDIDATE_K=5` | 减少一次推理，保留 5 条引用 |
| 缩短摘要 | `RERANK_PASSAGE_CHARS=160`、`RERANK_MAX_LENGTH=192` | 空载重排序约 5 秒 |
| 超时兜底 | `RERANK_TIMEOUT_SECONDS=6.0`，`app/services/reranker.py::RerankerService.rerank` | 排队+推理超过预算按向量顺序降级，最坏延迟有上限 |
| 超时不熔断 | 超时只标记 `rerank_timeout`，不增加失败计数 | 瞬时负载不会永久关闭重排序 |
| 线程收尾 | `RerankerService._release_when_done` | 无法取消的推理线程结束后再释放信号量，避免请求堆积 |
| 指标 | `asktofit_rerank_timeouts_total{stage}` | 区分排队超时与推理超时 |

**回归验证**

- `tests/test_reranker.py`：推理超时快速降级、排队计入超时预算、超时不触发熔断、`timeout=0` 保持原行为；
- `tests/test_config.py`：`RERANK_TIMEOUT_SECONDS` 解析与负值拒绝；
- 日志出现 `重排序完成 candidates=5 elapsed=...` 或 `重排序超时 stage=...`。

**经验**

> 性能问题先用分阶段日志定位，再改参数。重排序参数是 CPU 部署的第一优先级。参数只能降低基线，超时兜底才能限制负载尖峰下的最坏延迟。

### 3. 跨检索模式分数不可直接比较

**现象**

同一轮检索里同时有 `hybrid`（Milvus WeightedRanker 分）与 `dense`（cosine 分）结果时，按 `score` 取最大值合并，排序结果不稳定：某一路分数天然偏大，会系统性压过另一路。

后来加入 BM25，分数量纲又多了一种，问题更明显。

**根因**

不同召回器的分数不是同一量纲：

- hybrid：dense/sparse 加权后的分数；
- dense：余弦相似度；
- BM25：未归一化的词法分。

直接比较等同于拿“厘米”和“公斤”比大小。

**解决**

- 新增 `app/services/fusion.py::rrf_fuse`，按**名次**做 Reciprocal Rank Fusion：
  `score = Σ weight / (k + rank)`；
- 每个 `(mode, query)`、BM25 各作为一路；单路时保持原始分数；
- 融合后 `score` 是 RRF 分，原始向量分保存到 `vector_score`，BM25 分保存到 `bm25_score`；
- 重排序只使用 `rerank_score` 过滤，知识缺口统计分别记录 `vector_score` / `rerank_score` / `retrieval_mode`；
- 缓存键加入 RRF 与 BM25 配置指纹，调参后不会命中旧结果。

**回归验证**

- `tests/test_fusion.py`：手算 RRF 顺序与分数、重复 UID 只计一次、确定性 tie-break、BM25-only 的 `vector_score=0.0`；
- `tests/test_reranker.py`：成功路径与降级路径都不会把 RRF 分写成 `vector_score`。

### 4. BM25 索引 TTL 内命中已删除分块

**现象**

删除文档或分块后，短时间内（`BM25_INDEX_TTL_SECONDS=120`）仍可能检索到已删除的分块，甚至进入提示词。

**根因**

BM25 是进程内索引，删除后只做了主动失效；如果失效遗漏或有多 worker，索引在 TTL 内仍持有旧数据。向量库删除也可能有短暂延迟。

**解决**

`app/services/retrieval.py::enrich_hits` 在数据库可达时做二次校验：

- 只保留 `Document.is_current=True` 的版本；
- 丢弃数据库中已不存在的 `chunk_uid`；
- 再用父分块正文替换子分块正文。

数据库查询失败时保留原始命中（不因扩展失败而丢结果），但会记录异常日志。

**回归验证**

- `tests/test_retrieval.py` 覆盖 `is_current=False`、缺失分块、父块扩展；
- `tests/test_bm25.py` 覆盖 TTL、`invalidate`、多知识库隔离。

### 5. 重排序失败时的“静默降级”

**现象**

模型异常时，如果直接把向量分当重排序分继续过滤，会混淆量纲；如果直接丢弃全部资料，又会把“模型故障”误记成“知识缺口”。

**解决**

显式定义失败语义：

- `RERANK_FAILURE_MODE=drop`（默认）：丢弃本轮资料，并按真实得分记录知识缺口；
- `RERANK_FAILURE_MODE=vector`：保留候选，但标记 `rerank_failed=True`、`score_mode=vector`，明确使用向量分；
- 连续失败达到 `RERANK_MAX_CONSECUTIVE_FAILURES` 后熔断，后续请求直接按失败策略处理，避免每次请求都等模型超时；
- 降级结果只缓存 `RETRIEVAL_DEGRADED_CACHE_TTL=30` 秒。

**回归验证**

- `tests/test_reranker.py::test_rerank_failure_returns_vector_hits_with_flag`
- `tests/test_reranker.py::test_rerank_circuit_opens_after_consecutive_failures`
- `tests/test_chat_service.py` 覆盖 `drop` / `vector` 两种过滤行为。

### 5A. 知识缺口里“向量分中等、重排分接近 0”

**现象**

缺口列表里大量记录呈现“向量 0.67–0.75、重排 0.002–0.21”，看起来像向量分算错，或者重排序失效。

**根因**

`vector_score` 与 `rerank_score` 不是同一量纲：

```text
vector_score = 0.7 * (1 + dense_cosine) / 2 + 0.3 * (0.5 + atan(sparse_ip) / π)
rerank_score = sigmoid(cross_encoder_logit)
```

归一化把 cosine 0.5 放大成 0.75，sparse 无命中也会得到 0.5，所以**完全无关的段落混合分也常在 0.65–0.75**。交叉编码器的重排分才是相关性概率：相关问答对通常 > 0.8，无关约 0.000x。用“怎么转人工”实测：dense 0.5156 → 0.7578，sparse 0.0281 → 0.5089，混合 0.6832，与线上缺口一致。

**解决**

- 不修改分数计算；缺口页为向量分和重排分增加量纲说明，判断相关性以重排分为准；
- 用已知样本校验模型：相关对 0.9518，无关对 0.0002，排除模型故障；
- 早于新知识入库的旧缺口要重跑后再判断，避免把“当时没资料”当成“现在仍缺”。

**回归验证**

- 缺口页展示与 tooltip（`frontend/src/views/KnowledgeGapView.vue`）；
- 对同一问题手工复算 `0.7*N(dense)+0.3*N(sparse)` 与缺口记录一致。

### 5B. 口语化追问未改写 + 重排模型加载占用推理超时

**现象**

- “我刚刚问的哪款衣服来着”“对照预算做取舍”直接以原文检索，召回无关资料并记为缺口；
- 日志先出现 `重排序超时 stage=inference timeout=6.0s`，几秒后才出现 `BGE Reranker 加载完成`。

**根因**

1. `_FOLLOW_UP_CUES` 只收录“刚才”，漏掉“刚刚/哪款/来着”等口语线索；无线索时只对 ≤6 字碎片改写，7–10 字的省略句（如“对照预算做取舍”）不触发改写。
2. `rerank()` 把 `_ensure_model()` 放在 `asyncio.wait_for(..., RERANK_TIMEOUT_SECONDS)` 内部，冷启动加载的数十秒被当作推理超时，直接降级为向量顺序。生产环境有启动预热，但脚本、评估和预热未完成的启动窗口会命中。

**解决**

- 扩充追问线索（刚刚、哪款、哪件、哪个、这款、那款、来着、上次、前面、上述等）；
- 7–10 字且意图为 `other` 的句子，只要不含“吗/么/怎么/多少/多久/什么/是否/能不能/？”等完整疑问结构，也执行改写；“支持以旧换新吗”这类完整短问题保持独立检索；
- `rerank()` 先在超时外 `await asyncio.to_thread(_ensure_model)`，加载失败按 `rerank_failed` 显式降级；加载完成后再开始计算排队+推理预算。

**回归验证**

- `tests/test_rag.py::test_should_rewrite_only_for_follow_up`
- `tests/test_reranker.py::test_rerank_model_load_does_not_consume_inference_timeout`
- `tests/test_reranker.py::test_rerank_model_load_failure_degrades_with_flag`
- 日志中不再出现“超时后才加载完成”的顺序；冷启动场景 `rerank_timeout` 不出现。

## 二、缓存与一致性

### 6. 降级/空结果被按正常 TTL 缓存

**现象**

一次 embedding 或 Milvus 抖动产生空结果后，接下来 3 分钟（`RETRIEVAL_CACHE_TTL=180`）所有相同问题都回答“暂无资料”，即使服务已经恢复。

**根因**

正常结果、降级结果、空结果、异常结果使用同一个缓存 TTL 与同一个“是否写缓存”的规则。

**解决**

在 `app/services/retrieval.py::RetrievalService.retrieve` 中区分：

| 结果类型 | 缓存策略 |
|---|---|
| 正常结果 | `RETRIEVAL_CACHE_TTL`（默认 180s） |
| 含 `rerank_failed` / `rerank_timeout` 的降级结果 | `RETRIEVAL_DEGRADED_CACHE_TTL`（默认 30s） |
| 空召回 | 30s |
| 由 embedding / Milvus 异常造成的空结果 | **不写缓存**，让下一次请求立即重试 |
| `redis=None`（评估脚本） | 全部绕过缓存 |

**回归验证**

- `tests/test_retrieval.py` 覆盖降级 TTL、空结果 TTL、异常不缓存；
- `tests/test_cache.py` 覆盖缓存键对查询列表、策略、BM25、配置指纹的敏感性。

### 7. 缓存失效逻辑分散，容易漏

**现象**

知识库、文档、分块变更后，需要同时清理 Redis 的检索缓存和进程内 BM25 索引。最初六个写路径各写各的，新增路径很容易漏掉 BM25，导致“改了文档但检索还是旧内容”。

更严重的是最初的 Redis 清理方式：任何一次知识变更都 `scan_iter` 扫描并删除所有用户的检索/回答缓存。知识库越多、缓存越大，删除耗时越长，还会把无关知识库的缓存一起清空，形成缓存雪崩。

**解决**

`app/services/search_index.py::invalidate_search_caches` 仍是统一入口，但 Redis 侧改为**版本号**：

1. `bump_kb_version(get_redis_client(), kb_id)`：递增该知识库的版本号（`kb_id` 为空时递增全局版本）；
2. `bm25_service.invalidate(kb_ids)`：清空对应知识库的进程内索引。

检索缓存的键包含所查询知识库的版本号（`app/services/cache.py::retrieval_key`）。版本号变化后旧键不再被命中，并按各自 TTL 自然过期，不需要扫描或批量删除任何键。

所有写路径统一调用它：

- 文档入库成功 / 跳过未变化（`app/services/ingestion.py`）；
- 删除文档、编辑分块、删除分块、删除知识库（`app/api/routes/knowledge.py`）。

**回归验证**

- `tests/test_cache.py` 覆盖版本号递增、缺失版本按 0 处理、版本参与缓存键；
- `tests/test_bm25.py` 覆盖 `invalidate`；
- `tests/test_retrieval.py` 验证版本号变化后缓存失效、并发生成时只回源一次（single-flight）；
- `tests/test_knowledge_api.py` 断言写操作后调用失效。

**经验**

> 缓存失效必须收敛到一个入口，否则“新增一个写接口”就是一次潜在的数据不一致。

## 三、知识库入库与判重

### 8. 改标点 / 改文件名造成重复文档

**现象**

同一份制度文档，只改了几个标点或重命名后再次上传，系统里出现两份内容几乎相同的文档；检索时同一段内容命中两次，提示词被重复资料占满。

**根因**

最初只按文件名判断重复，正文没有归一化指纹。

**解决**

`app/services/dedup.py` + `app/services/ingestion.py`：

1. **归一化**：NFKC、去零宽字符、去 Markdown/HTML、去 URL、casefold，只保留字母数字；
2. **完全重复**：归一化正文 SHA-256 相同 → `update_action=unchanged`、`status=skipped`，不产生新文档；
3. **近重复**：SimHash（字符 4-gram）距离 ≤ `DOC_DEDUP_SIMHASH_MAX_DISTANCE`，且文本相似度 ≥ `DOC_DEDUP_SIMILARITY`（默认 0.90）→ 视为同一逻辑文档的新版本；
4. **版本切换**：新版本先完成解析、切块、向量写入，数据库提交成功后才把旧版本 `is_current=False`；任一步失败，旧版本继续可检索；
5. **强制新文档**：上传时可勾选 `force_new=true` 跳过判重；
6. **分块与检索去重**：父块按归一化哈希去重，子块按 `CHUNK_NEAR_DUP_SIMILARITY`，检索结果按 `RETRIEVAL_DEDUP_SIMILARITY` 去重（小于 20 字的短块不参与相似度合并，避免误删）。

**回归验证**

- `tests/test_dedup.py`：标点/空白/大小写/全半角/链接变化的哈希一致性；
- `tests/test_retrieval.py`：检索结果近重复去重；
- 线上验证：同一文档改标点重传返回 `skipped`，改内容重传只保留一个 current 版本。

**经验**

> “文件名”不是文档身份，“归一化正文指纹”才是。

### 9. 旧版本被提前下线

**现象（设计阶段规避）**

如果上传新版本时先下线旧版本，再解析新文件，一旦解析失败，知识库会在一段时间内“没有这份文档”。

**解决**

入库流程固定为“先建新、后切旧”：

1. 新文档以 `is_current=False` 状态创建并解析；
2. 解析、切块、向量写入全部成功；
3. 数据库提交后，旧版本 `is_current=False`、`update_action=superseded`，新版本 `is_current=True`；
4. 失败时新文档标记 `create_failed` / `update_failed`，旧版本保持 current。

**回归验证**

- `tests/test_ingestion` 相关用例（通过 `tests/test_knowledge_api.py` 间接覆盖）；
- 手工验证：上传损坏文件，旧版本仍可检索。

### 10. MinerU 失败被静默降级

**现象（设计阶段规避）**

用户显式选择“深度解析（MinerU）”后，如果 Docker 或镜像不可用，若自动退回标准解析，用户会以为拿到的是深度解析结果，实际版式/表格可能丢失。

**解决**

- 显式选择 MinerU 后，Docker/镜像/解析失败 → 文档标记失败并保留旧版本可检索，**不静默降级**；
- 上传接口会在入库前检查 `mineru_status()`，不可用直接返回 400 和原因；
- 解析器记录在文档上，重建索引沿用同一解析器，保证判重口径一致。

**回归验证**

- `tests/test_mineru_parser.py`：状态检测、超时清理、失败语义；
- `tests/test_knowledge_api.py`：不可用时上传返回 400。

### 10A. 入库任务与向量同步不持久（重启丢任务 / 库里有记录但检索不到）

**现象**

- 上传接口用 `BackgroundTasks` 执行解析：进程重启或崩溃后，文档永久停在 `pending/processing`，没有任何重试入口；
- MySQL 提交成功、Milvus 写入失败时，文档显示已入库，但检索召不回来；删除/编辑同样可能只改了一边；
- 同一文档被重复触发入库时，可能并发写同一批分块。

**根因**

- 任务只存在于进程内存，没有持久化状态、租约与重试；
- MySQL 与 Milvus 两次写入不在同一事务内，也没有补偿/重试机制；
- 分块 UID 使用 `uuid4()`，重试会产生新主键，旧向量残留，无法幂等。

**解决**

1. **持久化任务队列** `async_tasks`：上传/重建索引只写任务行（`pending`），
   BackgroundTasks 仅加速；`task_worker` 轮询并用 `SELECT ... FOR UPDATE SKIP LOCKED`
   领取，带 `attempts/max_attempts`、`lease_until`、指数退避；
2. **向量 outbox** `vector_outbox`：分块与 outbox 条目同一事务提交，再同步 Milvus；
   `replace_doc / upsert_chunk / delete_doc / delete_kb / delete_chunk` 失败自动重试；
3. **删除/编辑改为 DB-first**：先提交数据库与 outbox，再同步向量；
4. **确定性 UID**：`sha256(doc_id:version:kind:index:content_hash)[:32]`，
   `upsert` 幂等，重建索引时删除 `stale_uids`；
5. **启动恢复**：回收过期租约、为丢失任务的文档补入队、超时任务标记失败
   （`UPLOAD_TASK_TTL` 真正生效）；
6. **版本切换**：新版本向量就绪前保持旧版本 `is_current=true`，就绪后同一事务切换。

**回归验证**

- `tests/test_task_queue.py`：去重、领取、租约回收、重试、失败落库、启动补入队；
- `tests/test_outbox.py`：`replace_doc` 幂等 upsert、版本切换、失败标记、确定性 UID；
- `tests/test_knowledge_api.py`：上传/删除/编辑/重建索引均通过 outbox 执行；
- 真实链路：上传后重启进程，任务自动续跑并最终 `completed`。

**经验**

> 跨存储写入只能做**最终一致**：先把意图持久化（任务 + outbox），再异步收敛；
> 主键必须可重复计算，否则重试就是在制造脏数据。

### 11. RAGAS 依赖与运行时环境冲突

**现象**

直接 `pip install ragas==0.3.0` 会解析到未锁定的 LangChain 1.x / LangGraph，并把运行时的 `websockets` 降级，可能影响其他依赖；同时评估依赖进入运行时 `.venv`，违背“评估工具不污染服务”的原则。

**解决**

- RAGAS 只通过 `scripts/eval_requirements.txt` overlay 安装：

  ```text
  ragas==0.3.0
  langchain>=0.3,<0.4
  langchain-core>=0.3,<0.4
  langchain-community>=0.3,<0.4
  langchain-openai>=0.2,<0.4
  ```

- 运行方式：

  ```bash
  uv run --with-requirements scripts/eval_requirements.txt \
    python scripts/evaluate_rag.py --limit 5
  ```

- 运行时 `.venv` 不新增 ragas；
- `scripts/evaluate_rag.py` 对 ragas **惰性导入**：检索指标与 `--validate-dataset` 不依赖 ragas，未安装时只提示命令，不崩溃、不把生成指标记 0；
- CI 使用 `--validate-dataset`，不需要 DB、不需要 ragas。

**回归验证**

- `uv run python scripts/evaluate_rag.py --validate-dataset` 在无 ragas 环境可运行；
- overlay 内 `import ragas; print(ragas.__version__)` 输出 `0.3.0`；
- 运行前后对比 `uv.lock` / `.venv`，无新增运行时依赖。

### 12. 缺失的 RAGAS 分数被当成 0

**现象（设计阶段规避）**

LLM 评委调用失败、返回 `NaN` 或某题缺少结果时，如果直接填 0，会把“无法评估”误判成“效果极差”，拉低均值。

**解决**

`app/services/evaluation.py::merge_ragas_scores`：

- `None` / `NaN` / 缺行 → 保持 `None`；
- 聚合时只对非 `None` 值求均值；
- 报告同时输出 `valid_counts`，让读者知道每个指标实际有多少有效样本；
- `judge_failed` 只统计“所有生成指标都不可用”的样本，单项缺失由 `valid_counts` 体现；
- RAGAS 逐题缓存要求所有请求指标都有可用分数，缺少的指标下次运行会重算，
  不会把一次 `None` 永久复用。

**回归验证**

- `tests/test_evaluation.py` 覆盖 `None`、`NaN`、缺行、多行；
- 报告 Markdown 中生成指标表显示“有效样本”列。

### 13. 评估样本量过小导致误读

**现象**

现有 `reports/eval_*.md` 中 doc/section 指标全是 `1.0000`，但样本数只有 1–3 条。如果直接对外宣称“检索准确率 100%”，会严重误导。

**解决**

- 报告中显式输出 `样本：N（可回答 M）`；
- `docs/评估指标.md` 明确标注当前结果与样本量，不把 1–3 条样本当整体结论；
- 数据集固定为 60 条手写样本，CI 断言数量与必填字段；
- 正式验收应运行全量 60 条，并报告 `valid_counts`；
- 评估看板的概览与趋势只统计 `sample_count ≥ EVAL_MIN_MEANINGFUL_SAMPLES`
  （默认 10）的成功运行；样本不足的运行仍保留在运行列表中并标记 `is_meaningful=false`，
  前端显示“样本不足”，避免 1 条样本的 100% 占据首屏。

**经验**

> 指标必须和样本量一起读；没有样本量的百分比没有意义。

### 13A. RAGAS 列名别名覆盖导致 `context_precision` 全为空

**现象**

全量 60 条评估中，`faithfulness`、`answer_relevancy`、`context_recall` 都有有效分数，
但 `context_precision` 在 60 条里全部是 `null`，看起来像“裁判服务对该指标全部失败”。
日志中只有运行末段的 402 余额不足，前 30 多条并没有 402。

**根因**

RAGAS 0.3.0 的结果列名是 `metric.name`，该指标为
`llm_context_precision_with_reference`。脚本为了兼容不同版本，把长列名和
`context_precision` 都映射到同一个输出键，然后用字典推导式逐项取值：

```python
{cli_name: row.get(column) for column, cli_name in column_to_key.items()}
```

后一个别名 `context_precision` 在结果表中不存在，返回 `None`，把前一个长列名刚取到的
有效分数覆盖掉。其余三个指标只有一个列名，所以不受影响。

**解决**

`scripts/evaluate_rag.py::_first_usable_value` 按别名顺序返回第一个有限数值，
`None`/`NaN` 不覆盖已有值；并新增回归测试
`tests/test_evaluate_rag.py::test_first_usable_value_prefers_long_ragas_column_name`。

**经验**

> 多别名映射不能“后写覆盖”，应按优先级取第一个可用值；缺失值与 0 也必须区分。

`context_precision` 的分数当时没有写入报告缓存，无法事后恢复，需在裁判余额充足后重跑。

### 13B. 不可回答样本拉低生成指标，与旧运行不可比

**现象**

修复别名覆盖后，60 条样本的 overall `faithfulness` 从 0.81 降到 0.65，
看起来像系统退步。但按 `answerable` 拆分后发现：48 条可回答样本为 0.78，
12 条不可回答样本只有 0.11；而旧运行恰好缺少这 12 条（以及另外 7 条），
两次运行的分母根本不同。

**根因**

不可回答样本的“正确答案”是拒绝作答。RAGAS 的 faithfulness、answer_relevancy、
context_precision、context_recall 都以参考答案或上下文为依据，拒绝作答天然得分很低，
把它和可回答样本放进同一个均值，既不反映能力，也让不同覆盖率的运行无法比较。

**解决**

- `app/services/evaluation.py::_group_summary` 的 `generation` 只聚合
  `answerable=true` 的样本；
- 不可回答样本单独输出 `unanswerable` 块：
  `{count, refused, refusal_accuracy, generation}`；
- 拒答判定 `is_refusal` 用一组明确表述（未收录、未找到、无法确认、抱歉等），
  只判断“是否承认资料不足”，不评价措辞好坏；
- 报告与看板同时展示“正确拒答率”，`valid_counts` 使用
  `generation.*` 与 `unanswerable.generation.*` 两套前缀；
- 看板持久化时把 `refusal_accuracy` 并入 run 级 `generation_metrics`，
  前端标签为“正确拒答率”；概览卡片仍优先取 `faithfulness`。

**回归验证**

- `tests/test_evaluation.py` 覆盖可回答/不可回答分组均值、空输入与拒答边界；
- 全量重跑后，`generation.valid_counts` 的分母为可回答样本数（48），
  正确拒答率单独报告。

**经验**

> 一个均值要么限定在同质样本上，要么拆开报告；分母变了就不能直接比。

### 16. 异步数据库脚本报 `Event loop is closed`

**现象**

**回归验证**

迁移/清理脚本连续运行两次不报错。

### 19. SSE 在 nginx 后面“憋着不吐字”

### 20. 调参后仍命中旧检索结果

**现象**

**根因**

检索缓存键只包含问题、知识库、TopK，没有包含影响排序/过滤的配置。

## 六、通用排查顺序

遇到线上问题时，建议按以下顺序缩小范围：

1. **看请求是否到达**：`X-Request-ID` + `[request_id] METHOD PATH -> status (ms)`；
2. **看意图与策略**：`asktofit_intent_total`、`检索策略 strategy=... source=...`；
3. **看检索分段耗时**：`检索耗时 ... embed/vector/bm25/rerank/total`；
4. **看重排序是否降级**：`重排序完成` / `重排序模型调用失败` / `已熔断`；
5. **看过滤与缺口**：`记录知识缺口 ... best/vector/rerank`；
6. **看首包与总耗时**：`首包到达 ttft=...`、`回答完成 ... latency=...`；
7. **看缓存**：`检索命中缓存`、`回答命中缓存`；
8. **看依赖**：MySQL、Redis、Milvus、模型目录、LLM 接口。
