## 一、测试分层

| 层级 | 工具 | 运行方式 | 是否依赖外部服务 |
|---|---|---|---|
| 后端单元测试 | pytest | `uv run python -m pytest tests/ -v` | 否（FakeVectorStore / fakeredis / 内存 SQLite） |
| 前端单元测试 | Vitest | `cd frontend && npm run test` | 否（mock API） |
| 端到端验收 | Playwright（脚本） | `cd frontend && npm run test:e2e` | 是（后端 + 前端 + MySQL/Redis/Milvus） |
| 评估数据集校验 | 纯文件 | `uv run python scripts/evaluate_rag.py --validate-dataset` | 否 |

设计原则：**单元测试不依赖真实模型、MySQL、Milvus、Redis**，保证 CI 可稳定运行；真实链路由评估脚本、E2E 脚本和手工验收覆盖。

## 四、性能指标

### 4.1 指标定义

| 指标 | 定义 | 日志关键字 |
|---|---|---|
| **embed** | 查询向量化耗时 | `检索耗时 ... embed=` |
| **vector** | Milvus 向量召回耗时 | `检索耗时 ... vector=` |
| **bm25** | 词法召回耗时 | `检索耗时 ... bm25=` |
| **rerank** | 交叉编码器重排序耗时 | `重排序完成 ... elapsed=` / `检索耗时 ... rerank=` |
| **retrieval** | 检索全链路（embed + vector + bm25 + rerank） | `检索耗时 ... total=` |
| **prep** | 意图 + 查询改写 + 策略规划 | `回答完成 ... prep=` |
| **TTFT** | 从请求开始到 LLM 首个 token | `首包到达 ... ttft=` |
| **latency** | 从请求开始到回答完成 | `回答完成 ... latency=` |

### 4.2 优化前后对比

测试问题包含单跳、条件、多要素、不可回答等类型；下表为第一轮优化结果，当时配置为 `RERANK_CANDIDATE_K=6`、`RERANK_PASSAGE_CHARS=240`、`RERANK_MAX_LENGTH=256`、`RERANK_BATCH_SIZE=1`。当前默认已收紧为 5 候选 × 160 字，基准见 [4.4](#44-重排序参数基准2026-10-19)。

| 指标 | 优化前 | 优化后 |
|---|---|---|
| 重排序 | 数十秒（20 候选 × 长文本） | **4.8–10.3 秒**，典型 5–7 秒 |
| 检索全链路 | 约 50–57 秒（最慢 110 秒） | **5.8–11.5 秒** |
| TTFT | 约 50 秒量级 | **8.0–15.5 秒** |
| 端到端 | 约 50–57 秒，历史峰值 110 秒 | **8.5–16.7 秒**，典型 12–13.5 秒 |

> 端到端波动主要来自机器负载（同时运行前端构建、浏览器、评估脚本等）。同一台机器上重排序耗时与候选数、文本长度近似线性，参数可按硬件调整。

### 4.3 模型预热

启动后后台依次加载模型并各执行一次极短推理，首个问答不再承担加载与冷启动耗时；之后按 `MODEL_WARMUP_INTERVAL_SECONDS`（默认 600 秒）周期保活：

| 模型 | 首次加载耗时（本机） |
|---|---|
| intent-bert | 约 21.6 秒 |
| bge-m3 | 约 3.9 秒 |
| bge-reranker-v2-m3 | 约 4.5 秒 |

日志：

```text
模型预热完成 name=intent-bert elapsed=21.56s（app/services/warmup.py:warmup_models）
模型预热完成 name=bge-m3 elapsed=3.92s（app/services/warmup.py:warmup_models）
模型预热完成 name=bge-reranker elapsed=4.53s（app/services/warmup.py:warmup_models）
模型保活完成 interval=600s elapsed=0.75s（app/services/warmup.py:keep_warm_loop）
```

### 4.4 重排序参数基准（2026-10-19）

背景：公网部署后实测重排序 15.3–20.3 秒，同时 `embed` 从 0.26 秒涨到 1.3–1.7 秒，判断为宿主机负载尖峰。空载复测同一批 240 字文本（i5-13500H，CPU-only）：

| 配置 | 重排序耗时 |
|---|---:|
| 6 候选 × 240 字 @256（调整前） | 7.6–9.3 秒 |
| 5 候选 × 180 字 @192 | 5.0–5.6 秒 |
| 5 候选 × 160 字 @192（当前默认） | 4.7–5.5 秒 |
| 4 候选 × 160 字 @192 | 4.0–4.3 秒 |

结论：

- 单候选开销约 **1.0–1.3 秒**，**减少候选数**比缩短文本更有效；
- `torch` 线程数 4/6/8/12 实测差异在误差内，不需要调整；
- 新增 `RERANK_TIMEOUT_SECONDS=6.0`，排队+推理超过预算即按向量顺序降级并标记 `rerank_timeout`（与 `rerank_failed` 区分，避免被 drop 策略丢弃）；超时不触发熔断，线程结束后再释放信号量，避免请求堆积。

日志关键字：

```text
重排序完成 candidates=5 elapsed=...s（app/services/reranker.py:RerankerService.rerank）
重排序超时 stage=inference timeout=6.0s candidates=5，按向量顺序降级（app/services/reranker.py:RerankerService.rerank）
```

### 4.5 如何复现

1. 启动后端并等待预热完成：

   ```bash
   uv run uvicorn app.main:app --host 127.0.0.1 --port 8000
   ```

2. 登录并创建会话（用你自己的账号，不要把 token 贴到公开位置）：

   ```bash
   # 1) 获取验证码，按返回的 captcha_id / image 完成识别
   curl -s http://127.0.0.1:8000/api/auth/captcha

   # 2) 登录
   curl -s -X POST http://127.0.0.1:8000/api/auth/login \
     -H "Content-Type: application/json" \
     -d '{"username":"<账号>","password":"<密码>","captcha_id":"<id>","captcha_code":"<code>"}'

   # 3) 创建会话（Bearer <access_token>）
   curl -s -X POST http://127.0.0.1:8000/api/chat/conversations \
     -H "Authorization: Bearer <access_token>" \
     -H "Content-Type: application/json" \
     -d '{"kb_ids":[<kb_id>]}'

   # 4) 发起流式提问
   curl -N -X POST http://127.0.0.1:8000/api/chat/conversations/<id>/messages/stream \
     -H "Authorization: Bearer <access_token>" \
     -H "Content-Type: application/json" \
     -d '{"content":"<问题>"}'
   ```

3. 从日志提取指标：

   ```bash
   grep "检索耗时\|重排序完成\|首包到达\|回答完成" logs/app.log | tail -20
   ```

4. 清理测试会话（可选）：

   ```bash
   curl -s -X DELETE http://127.0.0.1:8000/api/chat/conversations/<id> \
     -H "Authorization: Bearer <access_token>"
   ```

### 4.6 性能调优建议

| 目标 | 调整 | 代价 |
|---|---|---|
| 降低重排序耗时 | 优先减小 `RERANK_CANDIDATE_K`，其次 `RERANK_PASSAGE_CHARS`、`RERANK_MAX_LENGTH` | 可能漏掉长尾候选或块尾答案 |
| 限制最坏延迟 | 设置 `RERANK_TIMEOUT_SECONDS`（默认 6） | 超时降级为向量顺序，答案质量可能下降 |
| 降低 TTFT | 减少 `history_rounds`、关闭策略生成、关闭重排序 | 多轮/复杂问题效果下降 |
| 提升召回 | 增大 `CANDIDATE_K`、`BM25_TOP_K` | 重排序耗时上升 |
| 提升吞吐 | 增大 `MAX_CONCURRENT_LLM`、多 worker | CPU/内存与外部服务压力上升 |
| 减少重复计算 | 保持缓存开启、合理 TTL | 知识更新后可能有短暂旧结果（已由失效机制控制） |

## 五、压测指标（Locust）

### 5.1 依赖与准备

Locust 放在独立依赖组，不进入运行时：

```bash
uv sync --group loadtest
uv run python scripts/prepare_load_test.py --users 20
```

准备脚本会：

- 要求存在可检索的**公共**知识库；
- 创建 `loadtest_` 前缀的临时用户与会话；
- 只把 JWT 写入 `loadtest/users.json`，**不打印 token**。

### 5.2 运行

```bash
# Windows 中文环境：Locust 会按 GBK 读取 pyproject.toml，需强制 UTF-8
PYTHONUTF8=1 uv run locust -f scripts/locustfile.py --headless -u 20 -r 2 -t 60s \
  --host http://127.0.0.1:8000
```

任务权重：

| 任务 | 权重 |
|---|---:|
| 健康检查 | 1 |
| 知识库列表 | 2 |
| 会话列表 | 2 |
| SSE 提问 | 6 |
| 缺口统计 | 1 |

### 5.3 关注指标

| 指标 | 说明 |
|---|---|
| `SSE_FIRST` | 首 token 延迟（流式请求的 TTFT） |
| `SSE_TOTAL` | 整段回答耗时 |
| 失败率 | 出现 `error` 事件、缺少 `meta`/`done`、回答为空均判失败 |
| RPS | 每秒请求数 |
| P95/P99 | 长尾延迟 |

> Locust 对 `stream=True` 的 `response_time` 只统计首包，因此脚本额外手动记录 `SSE_FIRST` 与 `SSE_TOTAL`，不要直接拿默认 `response_time` 当总耗时。

### 5.4 压测注意事项

- 压测时建议 `CACHE_ENABLED=false`，否则会大量命中缓存，测不到真实检索/LLM 路径；
- 按并发数调整 `RATE_LIMIT_REQUESTS`，否则主要压到限流器（429）；
- CPU-only 环境下重排序是瓶颈，建议先单 worker；
- 压测结束清理：

  ```bash
  uv run python scripts/prepare_load_test.py --cleanup
  ```

### 5.6 本机冒烟结果（2026-10-18）

条件：Windows 11、16 逻辑核、CPU-only；单 uvicorn worker；`CACHE_ENABLED=false`、
`RATE_LIMIT_REQUESTS=600`；`RERANK_CANDIDATE_K=6`、`RERANK_MAX_CONCURRENT=1`、
`MAX_CONCURRENT_LLM=8`、`MAX_CONCURRENT_EMBEDDING=2`。每轮都是短时冒烟（30–40 秒），
用于确认容量趋势，不等于正式容量测试。

| 并发用户 | 时长 | SSE 请求数 | 失败率 | SSE_FIRST 中位 / P95 | SSE_TOTAL 中位 / P95 | 浏览类接口 |
|---:|---:|---:|---:|---|---|---|
| 5 | 30s | 4 | 0% | 17.0s / 23.4s | 18.0s / 25.3s | 12–670ms |
| 10 | 40s | 6 | 0% | 22.0s / 33.0s | 23.0s / 34.5s | 4–49ms |
| 20 | 40s | 5 | 0% | 23.0s / 31.4s | 25.0s / 32.5s | 4–100ms |

结论：

- **短时冒烟吞吐约 8 次/分钟**（20 并发下 40 秒完成 5 次）；样本只有 4–6 个 SSE 请求，
  该数字只用于看趋势，不代表长测容量。瓶颈是 `RERANK_MAX_CONCURRENT=1`
  的 CPU 重排序：并发升高时检索耗时从约 5–11 秒涨到 20–30 秒；
- 非生成接口（健康检查、知识库/会话列表、缺口统计）在 20 并发下仍在 100ms 内，
  不受重排序队列影响；
- 本轮没有出现 429、LLM 排队超时或失败；继续加压主要增加排队时间而不是错误率；
- 提升方向：GPU 或更小重排序模型、调低 `RERANK_CANDIDATE_K` / `RERANK_PASSAGE_CHARS`、
  按核数增加 uvicorn worker（注意每个进程各自持有一份模型与重排序并发）。

### 5.7 真实链路长测（2026-10-22）

条件：Windows 11、16 逻辑核、CPU-only；单 uvicorn worker；服务实际为
`CACHE_ENABLED=true`，压测脚本给每条问题追加唯一编号以绕过缓存；
`MAX_CONCURRENT_LLM=16`、`RERANK_MAX_CONCURRENT=1`、`RERANK_CANDIDATE_K=5`、
`RERANK_PASSAGE_CHARS=160`、`RERANK_MAX_LENGTH=192`、`RERANK_TIMEOUT_SECONDS=6`、
`RATE_LIMIT_REQUESTS=120`。Locust 20 并发、540 秒、每个用户独立 JWT。

| 指标 | 结果 |
|---|---:|
| SSE 请求数 | 639 |
| SSE 失败 | 1（0.16%，模型未返回有效内容） |
| SSE_FIRST P50 / P95 / P99 | 13.0s / 24.0s / 30.0s |
| SSE_TOTAL P50 / P95 / P99 | 15.0s / 26.0s / 32.0s |
| 总 SSE 吞吐 | 1.18 次/秒（约 71 次/分钟） |
| 未命中检索缓存的吞吐 | 约 0.82 次/秒（445 / 540s） |
| 浏览接口 P95 | 健康 45ms、知识库列表 59ms、会话列表 75ms |

补充说明：

- 639 次 SSE 中检索缓存命中 183 次（28.6%），回答缓存命中 0 次；查询改写会去掉部分
  问题的唯一编号，因此不是严格 100% 未命中；P95/P99 仍由未命中请求主导。
- 445 次未命中检索中，444 次重排序在 6 秒超时后降级（114 次推理超时、330 次排队超时），
  即 20 并发下几乎全部请求都没有拿到完整重排结果。
- 因此这组 P95/P99 是“重排序降级模式”下的延迟与吞吐，不代表完整重排质量；完整重排的
  容量更低。
- 缺口统计接口 39 次 403 是压测临时用户非管理员导致，未计入 SSE 失败率。
- 结论：当前 CPU-only 单 worker 在 20 并发下，瓶颈仍是 `RERANK_MAX_CONCURRENT=1`；
  吞吐提升以重排序降级为代价。若要同时保证完整重排和吞吐，需要 GPU 或更小的重排模型、
  提高重排并发，或降低 `RERANK_CANDIDATE_K`。
- 严格 `CACHE_ENABLED=false` 的对照仍需重启后复测；5.6 保留为历史短冒烟对照。
