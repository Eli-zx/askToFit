## 一、加载规则

1. 启动时加载项目根目录 `.env`，**不覆盖进程中已存在的同名环境变量**（`override=False`）。容器、CI、systemd 注入的值优先。
2. 路径类变量（`UPLOAD_DIR`、`LOG_DIR`、`DATA_DIR`、模型路径）支持相对路径，统一按**项目根目录**解析。
3. 空字符串等同于未设置，使用默认值。
4. 非法值在启动时直接抛 `ValueError`，不会带病运行。
5. `VALIDATE_MODELS_ON_STARTUP=true` 时，启动阶段检查模型目录，缺失直接失败。
6. 本文件涉及密码、Key、JWT 密钥的变量**不得提交到版本库**；`.env` 已在 `.gitignore` 中。

布尔变量接受：`1 / true / yes / on`（不区分大小写）。

## 三、本地模型

| 环境变量 | 默认值 | 作用 |
|---|---|---|
| `BGE_M3_PATH` | `models/bge-m3` | BGE-M3 向量模型目录 |
| `BGE_RERANKER_PATH` | `models/bge-reranker-v2-m3` | 重排序模型目录 |
| `INTENT_MODEL_PATH` | `models/intent-bert` | 意图分类模型目录 |
| `EMBEDDING_DEVICE` | `cpu` | 向量模型设备，可设 `cuda` |
| `INTENT_DEVICE` | `cpu` | 意图模型设备 |
| `EMBEDDING_BATCH_SIZE` | `16` | 文档向量化批大小 |
| `VALIDATE_MODELS_ON_STARTUP` | `true` | 启动校验模型目录 |
| `MODEL_WARMUP_INTERVAL_SECONDS` | `600` | 模型保活间隔（秒），`0` 关闭 |

说明：

- `EMBEDDING_DIM` 固定 1024，与 Milvus collection 一致，**不可通过环境变量修改**；换模型必须同步重建 collection；
- 批大小影响入库速度与内存，CPU 建议 8–16；
- 关闭 `VALIDATE_MODELS_ON_STARTUP` 只跳过启动检查，不会让缺失模型的问答成功；
- 重排序关闭时不会校验 reranker 目录；意图关闭时不会校验 intent 目录；
- 启动预热会加载模型并各跑一次极短推理；`MODEL_WARMUP_INTERVAL_SECONDS` 控制空闲保活周期，避免长时间无请求后首个问答出现数倍冷启动开销。CPU 环境下不建议设为 `0`。

## 六、安全与认证

| 环境变量 | 默认值 | 作用 |
|---|---|---|
| `JWT_SECRET` | 开发占位串 | JWT 签名密钥 |
| `JWT_ALGORITHM` | `HS256` | 签名算法 |
| `ACCESS_TOKEN_EXPIRE_MINUTES` | `1440` | token 有效期（24 小时） |
| `CAPTCHA_TTL_SECONDS` | `300` | 验证码有效期 |
| `BCRYPT_ROUNDS` | `12` | 密码哈希成本 |
| `PASSWORD_HASH_CONCURRENCY` | `2` | bcrypt 线程池并发上限 |

要求：

- **生产必须替换 `JWT_SECRET`**，至少 32 字节随机串；
- 密码长度 6–64，且 UTF-8 编码不超过 72 字节（bcrypt 限制）；
- 验证码长度固定 4 位，不可通过环境变量修改；
- token 泄露等同于账号泄露，日志中不得输出；
- bcrypt 在 `asyncio.to_thread` 中执行，并受 `PASSWORD_HASH_CONCURRENCY` 限制，避免阻塞事件循环或占满线程池；
- 账号不存在时仍执行一次等价耗时的校验，降低用户名枚举风险。

## 八、切块与判重

### 8.1 切块

| 环境变量 | 默认值 | 作用 |
|---|---|---|
| `CHUNK_SIZE` | `500` | 子块目标长度（字） |
| `CHUNK_OVERLAP` | `80` | 子块重叠 |
| `MIN_CHUNK_SIZE` | `80` | 最小有效块长度 |
| `PARENT_CHUNK_SIZE` | `1200` | 父块目标长度 |

约束：`chunk_overlap < chunk_size`；`chunk_size ≥ 50`；`parent_size ≥ chunk_size × 2`。

调优：

- 子块过小 → 语义不完整、召回噪声多；
- 子块过大 → 检索精度下降、重排序变慢；
- 父块过大 → 上下文预算被单条资料占满；
- 服装 FAQ、条款类文档建议 400–600 字，叙述类可到 800。

### 8.2 判重

| 环境变量 | 默认值 | 作用 |
|---|---|---|
| `DOC_DEDUP_SIMILARITY` | `0.90` | 文档级近重复阈值 |
| `DOC_DEDUP_SIMHASH_MAX_DISTANCE` | `10` | SimHash 最大汉明距离（64 位） |
| `CHUNK_NEAR_DUP_SIMILARITY` | `0.97` | 切块阶段近重复阈值 |
| `RETRIEVAL_DEDUP_SIMILARITY` | `0.95` | 检索结果去重阈值 |

判重顺序：归一化 SHA-256 完全相同 → SimHash 距离 → 文本相似度。阈值降低会增加“误判为重复”的概率，提高会保留更多近重复文档。

## 十、检索与融合

| 环境变量 | 默认值 | 作用 |
|---|---|---|
| `RETRIEVAL_K` | `5` | 最终返回条数 |
| `CANDIDATE_K` | `20` | 每路召回条数 |
| `DENSE_WEIGHT` | `0.7` | 混合检索 dense 权重（Milvus WeightedRanker） |
| `SPARSE_WEIGHT` | `0.3` | 混合检索 sparse 权重 |
| `RRF_K` | `60` | RRF 平滑常数 |

调优：

- `CANDIDATE_K` 增大提升召回，但重排序只取前 `RERANK_CANDIDATE_K`，过大主要增加融合开销；
- `RETRIEVAL_K` 增大给模型更多上下文，但噪声与 token 成本上升；
- `RRF_K` 越小，头部排名差异被放大；通常 60 不需要改；
- dense/sparse 权重只影响 Milvus 内部混合打分，不影响跨路 RRF。

## 十二、BM25

| 环境变量 | 默认值 | 作用 |
|---|---|---|
| `BM25_ENABLED` | `true` | 总开关 |
| `BM25_MODE` | `fuse` | `off` / `fallback` / `fuse` |
| `BM25_TOP_K` | `20` | 每 KB 返回条数 |
| `BM25_RRF_WEIGHT` | `0.5` | 融合模式下的 RRF 权重 |
| `BM25_INDEX_TTL_SECONDS` | `120` | 进程内索引 TTL |
| `BM25_K1` | `1.5` | 词频饱和参数 |
| `BM25_B` | `0.75` | 长度归一化参数 |
| `BM25_TITLE_WEIGHT` | `3.0` | 标题字段权重 |
| `BM25_SECTION_WEIGHT` | `2.0` | 章节字段权重 |
| `BM25_CONTENT_WEIGHT` | `1.0` | 正文字段权重 |
| `BM25_MAX_CORPUS_CHUNKS` | `50000` | 单次建索引最大分块数 |
| `BM25_MAX_TOTAL_CHUNKS` | `100000` | 进程内索引分块总量上限（超出按 LRU 淘汰） |
| `BM25_MAX_INDEXED_KBS` | `20` | 进程内最多缓存的 KB 索引数 |
| `BM25_MAX_CONCURRENT_SEARCHES` | `2` | 同时执行的查询打分数（线程池限流） |
| `BM25_MIN_QUERY_COVERAGE` | `0.4` | 重排序关闭时的最低查询词覆盖率 |

模式选择：

- `fuse`：默认，正常路径也有词法召回，适合型号、金额、专有名词；
- `fallback`：只在向量路异常或为空时启用，最省 CPU；
- `off`：完全关闭。

注意：

- 多 worker 各自维护索引，写操作只能清理当前进程；
- 语料超过单库上限会截断，建索引日志会提示；
- 索引按 `BM25_MAX_TOTAL_CHUNKS` / `BM25_MAX_INDEXED_KBS` 做 LRU 淘汰，内存不会只涨不消；
- 查询打分走 `asyncio.to_thread`，并受 `BM25_MAX_CONCURRENT_SEARCHES` 限制，不阻塞事件循环；
- 索引 TTL 内新文档不可见，写路径会主动失效。

| `INTENT_DEVICE` | `cpu` | 推理设备 |

## 十四、重排序与提示词

| 环境变量 | 默认值 | 作用 |
|---|---|---|
| `RERANK_ENABLED` | `true` | 重排序总开关 |
| `RERANK_CANDIDATE_K` | `5` | 送入重排序的候选数 |
| `RERANK_PASSAGE_CHARS` | `160` | 每个候选的摘要正文预算 |
| `RERANK_MAX_LENGTH` | `192` | 交叉编码器最大 token |
| `RERANK_TIMEOUT_SECONDS` | `6.0` | 排队+推理总预算，超时按向量顺序降级并标记 `rerank_timeout`；`0` 不限制 |
| `RERANK_BATCH_SIZE` | `1` | 推理批大小 |
| `RERANK_MAX_CONCURRENT` | `1` | 同时进行的重排序推理数（线程池限流） |
| `RERANK_SCORE_THRESHOLD` | `0.25` | 合格阈值 |
| `RERANK_FAILURE_MODE` | `drop` | 失败策略：`drop` / `vector` |
| `RERANK_MAX_CONSECUTIVE_FAILURES` | `3` | 熔断阈值 |
| `QUERY_REWRITE_ENABLED` | `true` | 多轮查询改写 |
| `MAX_CONTEXT_CHARS` | `6000` | 提示词资料总预算 |
| `MAX_HISTORY_CHARS` | `3000` | 提示词历史总预算 |

性能关系（CPU）：

```text
重排序耗时 ≈ 候选数 × 每个 passage 的 token 数
```

建议：

- CPU 环境默认 `candidate_k=5`、`passage_chars=160`、`max_length=192`、`batch_size=1`；本机实测重排序约 5 秒；
- 单候选开销约 1.0~1.3 秒，优先降 `candidate_k`，其收益高于缩短文本；
- 降低 `passage_chars` 会漏掉块尾答案，必须先跑评估；
- `timeout` 超时只降级不熔断：线程在后台跑完后再释放信号量，避免请求堆积；连续失败仍由 `RERANK_MAX_CONSECUTIVE_FAILURES` 熔断；
- `threshold` 提高会减少噪声但增加知识缺口；
- `drop` 宁可回答“资料不足”也不返回低质资料；`vector` 用于重排序模型不可用时的持续降级；
- 熔断后不会自动恢复，需要重启进程。

## 十六、缓存

| 环境变量 | 默认值 | 作用 |

| `RETRIEVAL_DEGRADED_CACHE_TTL` | `30` | 降级/空结果 |
| `EMBEDDING_CACHE_TTL` | `86400` | 查询向量 |
| `RETRIEVAL_SINGLEFLIGHT` | `true` | 同一查询并发未命中时只回源一次 |
| `CACHE_TTL_JITTER` | `0.1` | TTL 随机抖动比例（0–1），避免同时过期 |

说明：

- 检索缓存键包含所查询 KB 的版本号；知识变更时只递增对应版本，不扫描删除全库缓存；
- 单飞（single-flight）按进程生效；多 worker 部署时每个进程各合并一次；
- TTL 抖动只影响实际写入的过期时间，不影响配置值。

建议：

- 压测时关闭，避免命中缓存测不到真实路径；
- 知识库频繁更新时可适当降低 TTL，但写路径已主动失效；
- 回答缓存键包含完整提示词，知识变化后自然不命中。

## 十九、LLM 容错与并发

| 环境变量 | 默认值 | 作用 |
|---|---|---|
| `LLM_TIMEOUT_SECONDS` | `60.0` | 单次请求超时 |
| `LLM_MAX_RETRIES` | `3` | 最大重试次数 |
| `LLM_RETRY_BACKOFF_SECONDS` | `0.5` | 指数退避基数 |
| `LLM_CIRCUIT_FAILURE_THRESHOLD` | `5` | 熔断阈值 |
| `LLM_CIRCUIT_RESET_SECONDS` | `30` | 熔断冷却 |
| `MAX_CONCURRENT_LLM` | `8` | LLM 并发信号量 |
| `LLM_QUEUE_TIMEOUT_SECONDS` | `5.0` | 等待并发槽位的最长时间，超时返回“当前咨询较多” |
| `MAX_CONCURRENT_EMBEDDING` | `2` | 向量化并发信号量 |
| `PASSWORD_HASH_CONCURRENCY` | `2` | bcrypt 线程池并发上限 |
| `UPLOAD_TASK_TTL` | `86400` | 入库任务与 outbox 已完成记录保留时间（秒，最小 60） |
| `TASK_MAX_ATTEMPTS` | `3` | 入库任务最大尝试次数 |
| `TASK_LEASE_SECONDS` | `3600` | 入库任务租约；进程崩溃后超时由其他 worker 接管 |
| `TASK_POLL_SECONDS` | `2.0` | worker 空闲轮询间隔 |
| `VECTOR_OUTBOX_MAX_ATTEMPTS` | `5` | 向量同步条目最大尝试次数 |
| `VECTOR_OUTBOX_LEASE_SECONDS` | `600` | 向量同步条目租约 |

入库任务与向量同步：

- 上传/重建索引先写 `async_tasks`，返回 202；后台任务只做加速，DB 行是唯一真相；
- 分块与 `vector_outbox` 在同一事务内提交，再同步 Milvus；同步失败按指数退避重试，进程重启后继续；
- 服务启动时回收过期租约、为丢失任务的 `pending/processing` 文档补入队、清理超期未完成任务（依赖 `UPLOAD_TASK_TTL`）；
- `SELECT ... FOR UPDATE SKIP LOCKED` 保证多 worker 不会重复执行同一任务（MySQL 8）。

重试规则：

- 只重试超时、连接错误、限流、429、5xx；
- 已输出 token 后不重试；
- 退避上限 8 秒，附加 0–0.2 秒抖动；
- SDK 自身重试关闭，避免叠加。

并发规则：

- 每个进程最多同时进行 `MAX_CONCURRENT_LLM` 路生成；
- 等待槽位超过 `LLM_QUEUE_TIMEOUT_SECONDS` 直接返回“当前咨询较多，请稍后重试”，不再重试；
- 槽位在成功、失败、取消、流式断开时都会释放。
