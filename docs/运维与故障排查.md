## 一、日常巡检

### 1.1 每日

| 检查项 | 方式 | 正常表现 |
|---|---|---|
| 进程存活 | `GET /api/health` | `{"status":"ok"}` |
| 依赖连通 | `uv run python scripts/check_services.py` | 三项全部 OK |
| 模型预热 | 启动日志 `模型预热完成` | 三个模型各一行 |
| 模型保活 | 日志 `模型保活完成` | 每 `MODEL_WARMUP_INTERVAL_SECONDS` 一行 |
| 错误日志 | `grep ERROR logs/app.log` | 无持续新增 |
| 知识缺口 | `/api/chat/knowledge-gaps/stats` 或前端页面 | 无异常突增 |
| 磁盘 | `df -h` / 资源管理器 | 上传、日志、模型目录有余量 |
| 会话归档任务 | 日志 `会话归档完成` | 每日一次或 0 条 |

### 1.2 每周

- 检查 `logs/app.log` 轮转是否正常（默认 10MB × 5）；
- 检查 MySQL 连接数与慢查询；
- 检查 Milvus 数据量与 collection 状态；
- 检查 Redis 内存与键数量；
- 确认备份任务成功、可恢复；
- 抽查知识库文档状态是否为 `completed`。

### 1.3 告警建议

| 指标 | 建议阈值 |
|---|---|
| `/api/health` 连续失败 | 2 次 / 1 分钟 |
| HTTP 5xx 比例 | >2% 持续 5 分钟 |
| `asktofit_llm_requests_total{status="error"}` | 5 分钟内持续增长 |
| `asktofit_rerank_failures_total` | 5 分钟内 ≥3 |
| `asktofit_knowledge_gaps_total` | 环比突增 3 倍 |
| 检索耗时 P95 | >15 秒（CPU 环境） |
| TTFT P95 | >20 秒 |
| 磁盘使用率 | >85% |

## 二、日志

### 2.1 位置与格式

```text
logs/app.log
logs/app.log.1 ... app.log.5
```

格式：

```text
2026-10-18 12:03:21 | INFO     | chat.py:412 | app.services.chat | 回答完成 ...
```

字段：时间 | 级别 | **文件名:行号** | logger | 消息。行号可直接定位代码。

### 2.2 关键日志

| 关键字 | 含义 |
|---|---|
| `模型预热完成` | 启动预热成功 |
| `模型预热失败` | 预热异常，首个请求会重试加载 |
| `模型保活完成` / `模型保活失败` | 周期保活成功 / 保活异常 |
| `文档入库` / `入库完成` | 入库阶段 |
| `文档解析失败` / `解析结果为空` | 解析问题 |
| `文档判重` / `跳过未变化` | 判重结果 |
| `检索命中缓存` | 检索缓存生效 |
| `检索召回` | 向量/BM25 召回数量 |
| `重排序完成` | 重排序耗时 |
| `重排序失败` / `重排序连续失败` | 模型异常或熔断 |
| `重排序超时` | 排队/推理超过预算，已按向量顺序降级 |
| `记录知识缺口` | 过滤后无合格资料 |
| `查询改写` | 改写前后文本 |
| `检索策略` | 策略与来源 |
| `首包到达` | TTFT |
| `回答完成` | 各阶段耗时 |
| `已失效知识库相关缓存` | 写路径缓存失效 |
| `后台维护任务失败` | 归档任务异常 |
| `未捕获异常` | 500 类错误 |

### 2.3 常用命令

```bash
# 最近错误
grep -n "ERROR" logs/app.log | tail -50

# 某个会话
grep -n "conversation_id=39" logs/app.log

# 慢请求（回答完成日志里的 latency）
grep "回答完成" logs/app.log | tail -100

# 重排序
grep "重排序" logs/app.log | tail -50

# 检索耗时
grep "检索耗时" logs/app.log | tail -50

# 入库
grep -E "文档入库|入库完成|解析失败" logs/app.log | tail -100
```

> 日志可能包含用户问题文本，导出或外发前需脱敏。

## 三、指标

### 3.1 抓取

```bash
curl -s http://127.0.0.1:8000/api/metrics
```

Prometheus 配置示例：

```yaml
scrape_configs:
  - job_name: asktofit
    scrape_interval: 15s
    static_configs:
      - targets: ["asktofit-api:8000"]
```

### 3.2 指标含义

| 指标 | 看什么 |
|---|---|
| `asktofit_http_requests_total` | 按 route/status 看错误分布 |
| `asktofit_http_request_duration_seconds` | 接口延迟 |
| `asktofit_intent_total` | 意图分布与来源（bert/keyword） |
| `asktofit_retrieval_strategy_total` | 各策略使用量与回退 |
| `asktofit_retrieval_duration_seconds` | 检索延迟 |
| `asktofit_retrieval_candidates_total` | 召回规模 |
| `asktofit_rerank_failures_total` | 重排序异常 |
| `asktofit_bm25_searches_total` | BM25 使用与结果 |
| `asktofit_bm25_fallback_total` | 向量失败转 BM25 的次数 |
| `asktofit_cache_hits_total` | 各层缓存命中 |
| `asktofit_llm_requests_total` | LLM 成功率与模型分布 |
| `asktofit_knowledge_gaps_total` | 知识缺口增长 |

### 3.3 常用查询

```promql
# 5xx 比例
sum(rate(asktofit_http_requests_total{status=~"5.."}[5m]))
/
sum(rate(asktofit_http_requests_total[5m]))

# 检索 P95
histogram_quantile(0.95,
  sum(rate(asktofit_retrieval_duration_seconds_bucket[5m])) by (le))

# LLM 错误率
sum(rate(asktofit_llm_requests_total{status="error"}[5m]))
/
sum(rate(asktofit_llm_requests_total[5m]))

# 缓存命中率
sum(rate(asktofit_cache_hits_total[5m]))
/
sum(rate(asktofit_cache_hits_total[5m]) + rate(asktofit_http_requests_total{route="/api/chat/conversations/{conversation_id}/messages/stream"}[5m]))
```

> 指标存进程内存。多 worker 时每个进程独立计数，Prometheus 按实例汇总；不要用单实例数值推断全局。

## 四、Redis 运维

### 4.1 键空间

| 前缀 | 用途 |
|---|---|
| `asktofit:intent:` | 意图缓存 |
| `asktofit:embedding:` | 查询向量 |
| `asktofit:strategy:` | 策略计划 |
| `asktofit:retrieval:` | 检索结果 |
| `asktofit:answer:` | 回答缓存 |
| `captcha:` | 验证码 |
| `ratelimit:` | 限流窗口 |

### 4.2 查看

```bash
redis-cli -h <host> -p 6379 -a <password> --scan --pattern 'asktofit:retrieval:*' | head
redis-cli -h <host> -p 6379 -a <password> dbsize
redis-cli -h <host> -p 6379 -a <password> info memory
```

**生产禁止使用 `KEYS *`**，用 `SCAN` 或 `--scan`。

### 4.3 手动失效

知识库写路径会自动失效。确需手动清理：

```bash
# 清检索缓存
redis-cli --scan --pattern 'asktofit:retrieval:*' | xargs -r redis-cli del

# 清回答缓存
redis-cli --scan --pattern 'asktofit:answer:*' | xargs -r redis-cli del
```

注意：

- 清空 Redis 会同时清掉验证码、限流窗口；
- BM25 索引在进程内存，清 Redis 不会清它；需重启进程或触发一次知识库写操作；
- 多 worker 时每个进程的 BM25 索引都需要重启才能整体刷新。

### 4.4 故障影响

Redis 不可用时：

- 缓存全部绕过；
- 限流放行；
- 验证码不可用（注册/登录失败）；
- 问答本身仍可继续，但明显变慢。

## 五、MySQL 运维

### 5.1 常用查询

```sql
-- 文档状态分布
SELECT status, COUNT(*) FROM documents GROUP BY status;

-- 非当前版本
SELECT id, kb_id, original_name, version, status
FROM documents WHERE is_current = 0 ORDER BY id DESC LIMIT 50;

-- 最近失败文档
SELECT id, original_name, error_message, updated_at
FROM documents WHERE status = 'failed' ORDER BY updated_at DESC LIMIT 20;

-- 知识缺口
SELECT id, intent, best_score, rerank_score, status, created_at
FROM knowledge_gaps ORDER BY id DESC LIMIT 50;

-- 各意图缺口数量
SELECT intent, COUNT(*) FROM knowledge_gaps
WHERE status = 'open' GROUP BY intent ORDER BY COUNT(*) DESC;

-- 会话与消息量
SELECT COUNT(*) FROM conversations;
SELECT COUNT(*) FROM chat_messages;

-- 评估运行
SELECT id, strategy, sample_count, status, created_at
FROM eval_runs ORDER BY id DESC LIMIT 20;
```

### 5.2 连接与锁

```sql
SHOW STATUS LIKE 'Threads_connected';
SHOW VARIABLES LIKE 'max_connections';
SHOW ENGINE INNODB STATUS;
```

连接池耗尽时接口会阻塞或报连接错误；检查是否有长事务、未释放会话。

### 5.3 注意

- 删除知识库会级联删除 `documents`、`chunks`、`parent_chunks`，但**不会删除 Milvus 向量**——必须走 API，不能直接删库；
- 删除会话不会删除 `knowledge_gaps`（无外键）；
- 不要手工修改 `documents.is_current`，会造成检索与版本关系不一致；
- 生产变更前先备份。

## 六、Milvus 与模型

### 6.1 Milvus 检查

```bash
uv run python scripts/check_services.py
```

或：

```python
from pymilvus import MilvusClient

client = MilvusClient(uri="http://127.0.0.1:19530")
print(client.list_databases())
print(client.describe_collection("fitrag"))
print(client.get_collection_stats("fitrag"))
```

关注：

- collection 是否存在；
- 实体数量是否与 MySQL 当前分块数大致一致；
- 索引状态是否为 `Finished`；
- pymilvus 是否仍是 2.4.x。

### 6.2 向量与 DB 不一致

可能出现：

| 现象 | 原因 | 处理 |
|---|---|---|
| MySQL 有分块，检索不到 | 向量未写入或被删 | 重新索引文档 |
| 检索到已删除分块 | BM25 索引未失效 | 重启进程 / 触发写操作 |
| 文档 `completed` 但无结果 | 分块为空或 embedding_mode 不匹配 | 查看日志与分块列表 |

`enrich_hits` 会丢弃数据库中不存在的 `chunk_uid`，所以“脏向量”不会进入提示词，但会浪费召回名额。

### 6.3 模型加载

启动预热顺序：intent-bert → bge-m3 → bge-reranker。

本机耗时：约 21.6s / 3.9s / 4.5s。预热在后台执行，服务可先响应，但首个相关请求会等待模型加载。预热不仅加载权重，还会跑一次极短推理；空闲保活由 `app/services/warmup.py::keep_warm_loop` 周期执行，间隔为 `MODEL_WARMUP_INTERVAL_SECONDS`（默认 600 秒，`0` 关闭）。

排查：

```bash
grep "模型预热" logs/app.log
grep "模型加载" logs/app.log
```

模型目录缺失时启动直接失败；生产不要关闭 `VALIDATE_MODELS_ON_STARTUP` 来“绕过”。

## 七、故障速查表

| 现象 | 最可能原因 | 快速验证 | 处理 |
|---|---|---|---|
| 启动报模型目录缺失 | 路径/挂载错误 | 看报错中的路径 | 修正 `*_PATH` 或 volume |
| 启动报 MySQL 失败 | 地址/账号/权限 | `check_services.py` | 修正 `.env`，容器内别用 localhost |
| 启动报 pymilvus 版本 | 装了 2.5+ | `pip show pymilvus` | 固定 2.4.x |
| 401 | token 过期/无效 | 重新登录 | 重新获取 token |
| 403 评估接口 | 非管理员 | `users.is_admin` | `set_admin.py` 授权 |
| 429 | 限流 | Redis 计数 | 调大阈值或等待窗口 |
| 注册/登录失败 | 验证码过期/Redis 故障 | 看验证码接口 | 重取验证码/恢复 Redis |
| 上传 400 | 扩展名/大小/参数 | 响应 detail | 按限制调整 |
| 文档一直 pending | 后台任务未跑/进程重启 | `documents.status` + 日志 | 重新上传或重建索引 |
| 文档 failed | 解析失败/空文档/OCR | `error_message` | 换 parser 或修文件 |
| 文档 skipped | 判重为未变化 | `update_action` | 如需新版本用 `force_new` |
| 提问无引用 | 过滤后为空/问候 | `meta.sources`、日志 | 补知识或调阈值 |
| 回答“资料不足”但文档有 | 重排序失败/阈值过高/摘要漏答案 | 重排序日志 | 检查模型、阈值、摘要参数 |
| 回答一次性出现 | nginx 缓冲 | 响应头/代理配置 | 关闭 `proxy_buffering` |
| 首答特别慢 | 模型未预热 / 空闲后冷启动 / 重排序慢 | 预热日志、检索耗时 | 等预热完成、调重排序参数 |
| 检索结果旧 | 缓存/BM25 未失效 | 日志 `已失效` | 手动清缓存/重启 |
| LLM 429/超时 | 服务商限流 | `llm_requests_total` | 降并发、换模型、稍后重试 |
| 重排序连续失败 | 模型异常/内存不足 | `重排序失败` 日志 | 重启；或临时 `RERANK_FAILURE_MODE=vector` |
| 知识缺口异常多 | 阈值过高/召回差/模型故障 | 缺口分数分布 | 查重排序、BM25、文档覆盖 |
| 评估接口 404 | run 不存在 | DB 查询 | 确认 run id |
| 评估无生成指标 | 未跑 RAGAS/Key 缺失 | 报告 `generation_metrics` | 按命令跑 overlay |
| 页面刷新 404 | nginx SPA 回退缺失 | nginx 配置 | `try_files ... /index.html` |
| 容器重启后文件丢失 | 未挂载 uploads/logs | `docker inspect` | 补 volume |
| 中文日志乱码 | 控制台非 UTF-8 | 日志文件是否正常 | 日志模块已强制 UTF-8；检查终端 |

## 八、典型故障处置

### 8.1 LLM 服务不可用

**现象**：SSE 返回 `error`，日志出现重试与熔断；检索指标仍正常。

**处置**：

1. 确认 Key 是否有效（只检查是否设置，不打印）；
2. 看 `asktofit_llm_requests_total{status="error"}` 与日志状态码；
3. 若 429：降低 `MAX_CONCURRENT_LLM`，等待限流窗口；
4. 若持续 5xx：切换 `DEFAULT_LLM_MODEL` 到另一服务商；
5. 熔断后等待 `LLM_CIRCUIT_RESET_SECONDS`，或重启进程；
6. 恢复后用一个简单问题验证 `meta` + `delta` + `done`。

注意：LLM 不可用不影响文档入库，也不影响离线检索评估。

### 8.2 Milvus 不可用

**现象**：检索报错或返回空；日志 `向量检索失败`；回答可能转为“资料不足”或 `error`。

**处置**：

1. `check_services.py` 确认连通；
2. 若 `BM25_MODE=fuse/fallback`，检索仍有词法兜底；
3. 恢复 Milvus 后，确认 collection 存在、索引 Finished；
4. 若数据损坏，按文档重新入库；
5. 清除检索缓存，避免继续读空结果（空结果只缓存 30 秒，通常自动恢复）。

### 8.3 重排序熔断

**现象**：连续回答“资料不足”，日志出现 `重排序连续失败` 且不再调用模型。

**处置**：

1. 看首个失败堆栈（内存、ONNX/torch、模型文件）；
2. 重启进程重置熔断；
3. 临时设置 `RERANK_FAILURE_MODE=vector` 维持服务；
4. 修复后恢复 `drop` 并验证分数分布；
5. 若因内存不足，降低 `RERANK_CANDIDATE_K` 或增加内存。

### 8.4 入库卡住或失败

**现象**：文档长时间 `processing` 或变为 `failed`。

**处置**：

1. 看 `error_message`；
2. 看日志中的解析阶段：
   - PDF 加密/损坏 → 换文件；
   - 扫描件无文字 → 用 `parser=mineru`；
   - 表格版式 → 用 `parser=mineru`；
   - 文件为空 → 拒绝；
3. MinerU 失败检查 Docker 是否可用、镜像是否存在、内存是否足够；
4. 重建索引：`POST /api/documents/{id}/reindex`；
5. 仍失败则重新上传。

### 8.5 知识缺口异常增长

**现象**：`knowledge_gaps` 快速增加，用户反馈“明明有资料却答不出”。

**处置**：

1. 取最近缺口，看 `best_score`、`retrieval_mode`；
2. 若 `retrieval_mode=vector` 且分数不低 → 重排序失败或阈值过高；
3. 若 `retrieval_mode=none` → 召回问题：检查文档状态、BM25、embedding_mode；
4. 若集中在某意图 → 该主题文档缺失或切块切断答案；
5. 抽查重排序摘要是否遗漏块尾答案（参数是否被改小）；
6. 调整后清理检索缓存，复测同一问题。

### 8.6 SSE 中断

**现象**：回答到一半停止；前端收到 `error` 或网络错误。

**处置**：

1. 看日志是 `LLMError`、`CancelledError` 还是代理超时；
2. nginx：确认 `proxy_buffering off`、`proxy_read_timeout 300s`；
3. 客户端主动断开时，服务端会保存已生成部分，属正常；
4. LLM 中途失败不会重试，避免重复输出；提示用户重试；
5. 检查响应头是否含 `X-Accel-Buffering: no`。

### 8.7 评估脚本失败

| 报错 | 原因 | 处理 |
|---|---|---|
| `ModuleNotFoundError: ragas` | 未用 overlay | 加 `--with-requirements scripts/eval_requirements.txt` |
| 数据集校验失败 | 字段/唯一性/负样本约束 | 按 `data/evaluation/README.md` 修 |
| DB 连接失败 | 未启动 MySQL | 先跑 `check_services.py` |
| 知识库不存在 | `--kb-name/--kb-id` 错 | 用前端或接口确认 |
| 生成指标全 null | Key 缺失/裁判失败 | 检查 Key 是否设置、模型可用 |
| 报告指标为 0 但检索明明命中 | 期望文档名不一致 | 用 `--validate-only` 校验 |

## 九、数据备份与恢复

### 9.1 必须备份

| 数据 | 位置 | 说明 |
|---|---|---|
| MySQL | `asktofit` 库 | 用户、知识库、文档、分块、会话、缺口、评估 |
| 上传文件 | `uploads/` | 原始文档，重建索引用 |
| 配置 | `.env` | 密钥与连接信息，单独安全保存 |
| 模型 | `models/` | 可重新下载/训练，但恢复慢 |

Redis、Milvus 不是事实来源：Redis 可丢弃，Milvus 可由上传文件与 MySQL 重建。

### 9.2 MySQL 备份

```bash
mysqldump -h <host> -u <user> -p \
  --single-transaction --routines --triggers \
  asktofit > asktofit_$(date +%Y%m%d_%H%M%S).sql
```

恢复：

```bash
mysql -h <host> -u <user> -p asktofit < asktofit_20261018_120000.sql
```

恢复后：

- 清理 Redis（避免旧缓存）；
- 校验 `documents` 与 Milvus 数量；
- 必要时逐文档重建索引。

### 9.3 上传文件备份

```bash
tar -czf uploads_$(date +%Y%m%d).tar.gz uploads/
```

恢复后路径必须与 `documents.file_path` 一致。

### 9.4 恢复顺序

```text
1. MySQL
2. uploads/
3. .env
4. 启动 API（自动建库建表）
5. 检查 documents/chunks
6. 重建缺失的 Milvus 向量
7. 清 Redis
8. 冒烟：登录 → 提问 → 引用
```

## 十、数据清理

### 10.1 会话

- 定时任务自动归档超过 `CONVERSATION_RETENTION_DAYS` 未活跃的会话；
- 归档不删除消息；
- 用户可手动归档/取消归档/删除；
- 删除会话不会删除 `knowledge_gaps`，需要单独清理。

孤儿缺口清理示例（先备份）：

```sql
DELETE g FROM knowledge_gaps g
LEFT JOIN conversations c ON c.id = g.conversation_id
WHERE g.conversation_id IS NOT NULL AND c.id IS NULL;
```

### 10.2 压测数据

```bash
uv run python scripts/prepare_load_test.py --cleanup
```

按 `chat_messages → conversations → knowledge_gaps → users` 顺序清理 `loadtest_` 前缀数据。

### 10.3 评估数据

- 前端可删除单次运行；
- 或 `DELETE /api/evaluations/runs/{id}`（管理员）；
- 删除运行会级联删除 `eval_cases`；
- 报告文件 `reports/` 需单独清理。

### 10.4 日志

按 `LOG_MAX_BYTES × LOG_BACKUP_COUNT` 自动轮转。需要保留更久时，配置外部采集，不要把 `LOG_BACKUP_COUNT` 无限增大。

## 十一、性能问题排查

### 11.1 先定位阶段

从一条“回答完成”日志拿到分解：

```text
intent=120ms prep=480ms retrieval=6123ms ttft=8024ms latency=12093ms
```

- `intent` 高 → 意图模型首次加载或 CPU 争抢；
- `prep` 高 → 查询改写/策略生成在等 LLM；
- `retrieval` 高 → 看向量、BM25、重排序的分项日志；
- `ttft - retrieval - prep` 高 → LLM 排队或服务商慢；
- `latency - ttft` 高 → 生成长或 token 多。

### 11.2 重排序慢

```bash
grep "重排序完成" logs/app.log | tail -20
```

优化顺序：

1. 降 `RERANK_CANDIDATE_K`（当前默认 5；单候选约 1.0–1.3 秒，收益最高）；
2. 降 `RERANK_PASSAGE_CHARS`（当前默认 160）；
3. 降 `RERANK_MAX_LENGTH`（当前默认 192）；
4. 确认 `RERANK_BATCH_SIZE=1`（本机实测比 8 快）；
5. 设置 `RERANK_TIMEOUT_SECONDS=6.0`，用超时兜底限制最坏延迟；
6. 仍有压力时评估关闭重排序，但必须先跑检索指标。

若日志出现 `重排序超时`，同时 `embed` 也明显变慢，说明宿主机 CPU 被其他进程抢占，优先排查负载，而不是继续压缩参数。

若 `重排序超时` 紧接着出现 `正在加载 BGE Reranker 模型` / `加载完成`，说明请求走到了未预热的冷启动路径（脚本、评估任务或预热尚未完成）。模型加载已移出推理超时，加载时间不会再触发 `rerank_timeout`；仍出现该顺序时检查是否运行的是旧代码或预热失败。

### 11.3 检索慢

- 向量化慢：检查 embedding 并发与首次模型加载；
- Milvus 慢：检查 collection 索引、负载、网络；
- BM25 慢：首次建索引或语料过大；看 `BM25_MAX_CORPUS_CHUNKS`；
- 多 query × 多 mode 会线性放大，检查策略是否过度触发。

### 11.4 LLM 慢

- 看首包时间与服务商状态；
- 降低 `MAX_TOKENS_DEFAULT`、历史轮数；
- 减少资料条数（`RETRIEVAL_K`）与上下文预算；
- 检查 `MAX_CONCURRENT_LLM` 是否成为排队点。

### 11.5 吞吐上不去

- 单 worker CPU 是主要瓶颈；
- 多 worker 可提升 LLM 等待型吞吐，但 BM25 索引与指标各自独立；
- 数据库连接池、Milvus 连接数、Redis 连接数要同步评估；
- 压测前关闭缓存，否则测的是缓存命中率。

## 十二、升级与回滚

### 12.1 升级前

- [ ] 备份 MySQL 与 `uploads/`
- [ ] 记录当前镜像 tag
- [ ] 对比 `.env.example`，补齐新增变量
- [ ] 确认模型路径仍有效
- [ ] 确认磁盘余量

### 12.2 升级

```bash
export IMAGE_TAG=v0.2.1
docker compose -f docker-compose.deploy.yml pull
docker compose -f docker-compose.deploy.yml up -d
docker compose -f docker-compose.deploy.yml logs -f api
```

### 12.3 回滚

```bash
export IMAGE_TAG=v0.2.0
docker compose -f docker-compose.deploy.yml pull
docker compose -f docker-compose.deploy.yml up -d
```

回滚后必须清 Redis 检索/回答缓存；如新版本改过分块或向量结构，还需要重建索引。

### 12.4 数据库变更

当前使用 `create_all + ensure_schema_upgrades` 做幂等补列/补索引，只做向前兼容的加法。若未来出现删列、改类型，必须引入正式迁移工具并准备回滚脚本。

## 十三、上报问题时收集什么

1. 发生时间与时区；
2. 请求路径、状态码、`X-Request-ID`；
3. 是否能稳定复现，问题文本（脱敏后）；
4. `logs/app.log` 对应时间段 ±5 分钟；
5. 相关 `document_id` / `conversation_id` / `kb_id`；
6. `/api/metrics` 快照；
7. 最近一次部署/配置变更；
8. 依赖服务状态（MySQL/Redis/Milvus/模型/LLM）。

**不要**在工单、截图或聊天中粘贴 `.env`、API Key、JWT、数据库密码。
