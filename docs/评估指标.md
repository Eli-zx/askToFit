# 评估指标

本文说明 AskToFit 如何衡量 RAG 效果：每个指标怎么算、代表什么、当前实测结果，以及结果为什么不能直接外推。检索指标由项目内纯函数计算，生成指标由官方 **RAGAS 0.3.0** 计算，两者分开报告、不混为一谈。

## 一、评估体系总览

| 类别 | 指标 | 计算方 | 依赖 LLM |
|---|---|---|---|
| 检索 | Hit@K、Recall@K、MRR、NDCG@K | 本地纯函数 `app/services/evaluation.py` | 否 |
| 检索 | 关键词覆盖 keyword_coverage | 本地纯函数 | 否 |
| 生成 | Faithfulness（忠实度） | 官方 RAGAS 0.3.0 | 是（裁判模型） |
| 生成 | AnswerRelevancy（答案相关性） | 官方 RAGAS 0.3.0 | 是 |
| 生成 | LLMContextPrecisionWithReference（上下文精确率） | 官方 RAGAS 0.3.0 | 是 |
| 生成 | LLMContextRecall（上下文召回率） | 官方 RAGAS 0.3.0 | 是 |

为什么拆开：

- 检索指标判断“该找到的资料有没有找到、排得够不够前”，不需要 LLM，可离线、可重复、零成本；
- 生成指标判断“答案是否忠于资料、是否回答了问题”，必须调用 LLM 当裁判，有成本和波动；
- 二者失败原因不同：检索差要调召回/重排序，生成差要调提示词或模型。混成一个分数无法定位问题。

RAGAS 只通过 overlay 安装（`scripts/eval_requirements.txt`），不进入运行时依赖；评估脚本对 `ragas` 惰性导入，未安装时检索评估照常运行。

## 二、数据集

文件：`data/evaluation/qa_eval.jsonl`，**手写 60 条**，覆盖 9 份业务文档、10 类意图。其中 10–15 条为不可回答/无证据问题，至少 10 条为多跳、对比或条件类问题。

### 2.1 字段

| 字段 | 必填 | 说明 |
|---|---|---|
| `id` | 是 | 唯一编号，如 `eval-001` |
| `question` | 是 | 用户问题 |
| `ground_truth` | 是 | 参考答案 |
| `expected_doc_names` | 是（可空） | 期望命中的文档名，使用 `Document.original_name` |
| `expected_sections` | 否 | 期望命中的章节片段，如 `"四、运费标准"` |
| `expected_keywords_all` | 否 | 答案必须全部包含的关键词 |
| `expected_keywords_any` | 否 | 答案至少包含其一的关键词 |
| `answerable` | 是 | 是否可由知识库回答 |
| `intent` | 是 | 意图标签，用于分组统计 |
| `tags` | 否 | 题型标签，如 `single-hop`、`multi-hop`、`conditional`、`unanswerable` |

### 2.2 约束

- `answerable=false` 时 `expected_doc_names` 必须为空；
- `answerable=true` 时，`expected_doc_names`、`expected_sections`、`expected_keywords_*` 至少要有一项；
- `id` 全局唯一；
- 数据集变更后 SHA-256 会写入报告，便于确认两次运行是否用了同一份数据。

### 2.3 相关性单元

评估不是比较 `chunk_uid`（重建索引后会变），而是比较**可读的业务单元**：

- **doc 级单元**：期望文档名；
- **section 级单元**：期望章节名，且命中章节必须落在期望文档上（避免“章节名相同但文档不对”被误判）。

文档名与章节在比较前做 NFKC、转小写、去空白和标点，再做双向包含匹配。同一单元被多个 chunk 命中只计一次。

## 三、检索指标

设：

- `K`：评估时实际返回的条数（`--top-k`，默认 10）；
- `E`：该题的期望相关单元集合（doc 级或 section 级）；
- `R`：按排序取前 K 条命中，每条映射为其覆盖到的期望单元集合；
- `|E|`：期望单元数量。

### 3.1 Hit@K

```text
Hit@K = 1  如果前 K 条中至少命中一个期望单元
        0  否则
```

**作用**：最直观的“有没有找到”。适合看召回是否完全失效，但对排序不敏感，也不能区分“命中 1 个”和“命中全部”。

### 3.2 Recall@K

```text
Recall@K = 前 K 条覆盖到的期望单元数 / |E|
```

**作用**：多文档、多章节问题必须看 Recall。比如问题同时涉及“运费”和“发货时效”，只命中一个文档时 Hit@K 仍是 1，但 Recall@K 只有 0.5。

### 3.3 MRR（Mean Reciprocal Rank）

```text
RR = 1 / 第一个命中期望单元的排名
MRR = 所有题目 RR 的均值
```

**作用**：衡量“第一个正确结果排得多靠前”。RAG 只把前几条送给模型，正确资料排第 1 和第 6 的体验差别很大，而 Hit@K 看不出来。

### 3.4 NDCG@K

采用二元增益，同一排名位置命中多个新单元仍按一次相关计：

```text
DCG@K  = Σ (1 / log2(位置 + 1))  仅在该位置首次覆盖到新的期望单元时累加
IDCG@K = Σ (1 / log2(i + 1))     i = 0 .. min(|E|, K) - 1
NDCG@K = DCG@K / IDCG@K
```

**作用**：同时考虑“命中多少”和“排得多前”，比 Hit@K 更细，比 MRR 更全面。适合作为检索排序质量的主指标。

### 3.5 关键词覆盖 keyword_coverage

```text
1.0   expected_keywords_all 全部出现在上下文中，
      且 expected_keywords_any 至少出现一项（若配置了）
0.0   否则
None  两个关键词字段都没配置
```

**作用**：不依赖 LLM 的业务兜底检查，确认“金额、时效、门槛”等关键事实确实进入了上下文。它只看有没有，不判断语义是否用对。

### 3.6 不可回答问题怎么算

`answerable=false` 的题目没有期望单元，四个检索指标都返回 `None`，**不进入均值分母**；它们主要参与生成侧评估（是否承认“资料未收录”而不是编造）。因此报告中的有效样本数可能小于总样本数，必须结合 `valid_counts` 看。

### 3.7 doc 级与 section 级

| 层级 | 期望单元 | 适合判断 |
|---|---|---|
| doc | 文档名 | 是否召回到了正确的文档 |
| section | 章节名（受文档约束） | 是否定位到了正确章节 |

doc 高、section 低，通常说明文档找对了但分块/排序不够细；两者都低，说明召回或查询理解有问题。

## 四、生成指标（RAGAS）

| 指标 | 衡量什么 | 低分通常意味着 |
|---|---|---|
| **Faithfulness** | 答案中的陈述能否由检索上下文支持 | 模型编造、过度推断、把常识当资料 |
| **AnswerRelevancy** | 答案是否切题、是否直接回应问题 | 答非所问、堆砌无关信息、回避结论 |
| **LLMContextPrecisionWithReference** | 上下文中与参考答案相关的内容占比及排序 | 噪声块太多、正确块排太后 |
| **LLMContextRecall** | 参考答案中的信息有多少能在上下文中找到 | 召回不足、分块切断关键信息 |

计算方式：把每题构造成 RAGAS 的 `SingleTurnSample`：

```text
user_input          = question
response            = 模型生成的答案
retrieved_contexts  = 过滤后的上下文列表
reference           = ground_truth
```

裁判模型复用项目的模型配置（`--judge-model`），答案相关性所需 embedding 使用本地 BGE-M3 适配器，不额外调用外部 embedding。

### 4.1 有效样本与缺失值

- RAGAS 某题返回 `NaN`、缺行或调用失败时，该题该指标记为 `null`，**不记 0**；
- 均值只对非 `null` 值计算，并单独报告有效样本数；
- 全部失败时指标为 `null`，报告标注 unavailable，而不是给出一个误导性的 0。

### 4.2 缓存

RAGAS 逐题结果按 `(样本哈希, 裁判模型, ragas 版本, 指标列表)` 缓存在 `reports/.eval_cache.json`，重复运行不会重复计费。改题、改模型或改指标会自然失效。

只有**当次请求的每个指标都有有限数值**时才会复用缓存；`None`、`NaN`、`Infinity` 一律视为不可用。这样一次裁判服务抖动（例如 402 余额不足）不会把缺失分数永久固化，补足余额后重跑会自动补算。

### 4.3 可回答与不可回答分开统计

不可回答样本的“正确答案”是**拒绝作答**，而 RAGAS 四项指标都以参考答案或检索上下文为依据：
既然没有可引用的事实，忠实度、答案相关性、上下文召回都会天然偏低。把它和可回答样本放进
同一个均值，既不能反映真实能力，也会让覆盖率不同的两次运行无法比较。

因此报告分两块：

| 块 | 样本 | 指标 | 说明 |
|---|---|---|---|
| `generation` | `answerable=true` | 四项 RAGAS 均值 | 主要能力指标，分母为可回答样本数 |
| `unanswerable` | `answerable=false` | `count`、`refused`、`refusal_accuracy` | 正确拒答率：答案明确表示资料不足的比例 |
| `unanswerable.generation` | `answerable=false` | 四项 RAGAS 均值 | 仅作参考，不参与主指标，也不用于横向比较 |

拒答判定是**启发式**：答案中出现“未收录、未找到、未提及、未说明、无法确认、无法给出、抱歉”等
明确表述即视为正确拒答。它只判断有没有承认资料不足，不评价措辞是否自然；把答案改写成
更委婉的说法不会影响判定，但直接编造一个数字会被判为错误。

看板中 `refusal_accuracy` 与 RAGAS 指标并列展示，标签为“正确拒答率”，口径以本节为准。

### 5.3 如何正确理解

- 60 条样本足以看出方向性问题，但仍不足以做严格的统计推断；section 级只统计了配置了 `expected_sections` 的 24 条，不能与 doc 级直接横向比较分母；
- 生成指标只统计可回答的 48 条。不可回答样本的“正确答案”是拒绝作答，RAGAS 四项指标天然偏低，把它们混进同一个均值会让不同覆盖率的运行无法比较（见 [4.3](#43-可回答与不可回答分开统计)）；
- 正确拒答率 1.0000 来自启发式判定：12 条不可回答样本的答案都明确承认资料不足，没有编造。它只说明“没有硬答”，不评价措辞是否自然；
- 所有指标都应按 `sample_count` 与 `valid_counts` 一起读，跨运行比较必须保持数据集 SHA-256、`judge_model`、指标集合与聚合口径一致；
- run 9 的 `context_precision` 分数没有被持久化，无法事后恢复；run 9 / run 12 与 run 13 的分母不同，趋势图不应把三者放在一起解读。

## 六、结果解读与局限

| 现象 | 可能原因 | 优先排查 |
|---|---|---|
| doc Hit 高、section Hit 低 | 文档对了但章节定位差 | 分块边界、章节识别、重排序 |
| Recall 低、Hit 高 | 多文档问题只召回了一部分 | 子查询策略、`CANDIDATE_K`、BM25 |
| MRR/NDCG 低、Hit 高 | 正确结果排在后面 | 重排序阈值、RRF 权重、候选数 |
| 关键词覆盖低 | 金额/时效未进上下文 | 分块切断、父块扩展、重排序摘要 |
| Faithfulness 低 | 答案超出资料 | 提示词、温度、上下文噪声 |
| AnswerRelevancy 低 | 答非所问 | 意图识别、查询改写、提示词 |
| ContextPrecision 低 | 噪声块多 | 提高重排序阈值、减少 `RETRIEVAL_K` |
| ContextRecall 低 | 资料没召回 | 提高候选数、开启 BM25/HyDE |

已知局限：

1. **样本量仍有限**：全量为 60 条，可回答 48 条，适合发现方向性问题，不足以做统计推断或对外承诺；
2. **裁判模型偏差**：RAGAS 用 LLM 打分，换模型分数会变，跨运行比较必须保持 `judge_model` 一致；
3. **字段归一化与裁判服务可用性**：RAGAS 不同版本对 `context_precision` 的列名不同（0.3.0 为 `llm_context_precision_with_reference`），脚本曾因别名覆盖丢弃该列；另有一次运行因 402 余额不足导致 19 条样本缺失生成指标。两处均已修复，最新全量运行 60/60 条有结果。缺失值不等于低分；
4. **参考答案单一**：`ground_truth` 是手写参考答案，措辞不同但语义正确的答案可能在 ContextRecall 上吃亏；
5. **不可回答问题不进入检索均值**：检索指标的有效样本数小于总数；section 级只统计配置了期望章节的题目；
6. **检索指标是本地口径**：与论文或其他项目的 Hit/Recall 实现可能不同，比较时以本项目的定义为准；
7. **离线评估与线上流量不同**：数据集问题经过人工设计，真实用户表达更口语、更模糊。

## 七、运行方式

### 7.1 数据集校验（CI 同款，不连 DB、不需 RAGAS）

```bash
uv run python scripts/evaluate_rag.py --validate-dataset
```

### 7.2 连接知识库校验期望文档/章节

```bash
uv run python scripts/evaluate_rag.py --validate-only
```

### 7.3 仅检索指标

```bash
uv run python scripts/evaluate_rag.py --retrieval-only --limit 10 --strategy direct
uv run python scripts/evaluate_rag.py --retrieval-only --limit 10 --strategy auto
```

### 7.4 检索 + 官方 RAGAS 生成指标

```bash
uv run --with-requirements scripts/eval_requirements.txt \
  python scripts/evaluate_rag.py --limit 5 \
  --judge-metrics faithfulness,answer_relevancy
```

首次运行会加载本地模型，耗时较长；API Key 只做 set/unset 检查，不会打印。

### 7.5 全量运行

```bash
uv run --with-requirements scripts/eval_requirements.txt \
  python scripts/evaluate_rag.py --limit 60 --strategy auto
```

### 7.6 常用参数

| 参数 | 说明 |
|---|---|
| `--dataset` | 数据集路径 |
| `--kb-name` / `--kb-id` | 评估目标知识库 |
| `--top-k` | 检索返回条数，默认 10 |
| `--limit` | 只跑前 N 条 |
| `--strategy auto\|direct\|hyde\|subquery\|backtrack` | 检索策略 |
| `--retrieval-only` / `--no-llm` | 跳过生成指标 |
| `--judge-model` | RAGAS 裁判模型 |
| `--judge-metrics` | 只跑指定生成指标 |
| `--persist/--no-persist` | 是否写入 `eval_runs` / `eval_cases`，默认写入 |
| `--output-dir` | 报告目录，默认 `reports/` |

## 八、报告字段

每次运行产出：

- `reports/eval_<timestamp>.json`：完整结构化结果；
- `reports/eval_<timestamp>.md`：可读报告；
- 可选 `reports/ragas_<timestamp>.csv`：RAGAS 逐题分数。

关键字段：

| 字段 | 说明 |
|---|---|
| `metadata` | 数据集 SHA-256、知识库、策略、TopK、样本数、ragas 版本、配置快照 |
| `aggregate.retrieval.doc` | doc 级四项指标均值 |
| `aggregate.retrieval.section` | section 级四项指标均值 |
| `aggregate.retrieval.keyword_coverage` | 关键词覆盖率 |
| `aggregate.generation` | 可回答样本的各生成指标均值 |
| `aggregate.unanswerable` | `count`、`refused`、`refusal_accuracy` 与不可回答样本的参考分数 |
| `aggregate.valid_counts` | 每个指标的有效样本数（`generation.*` 与 `unanswerable.generation.*`） |
| `aggregate.by_intent` / `by_tag` | 按意图/题型分组 |
| `cases` | 逐题问题、答案、命中、指标、错误 |

写入数据库后，管理员可在前端“评估看板”查看概览、趋势、运行列表和逐题明细。
