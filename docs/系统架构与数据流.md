## 一、系统定位与边界

AskToFit 是一个**服装售前 RAG 问答系统**：

- 输入：用户围绕商品、尺码、物流、退换、发票、支付、会员等问题；
- 知识来源：运营上传的业务文档（Markdown / PDF / Office / 图片）；
- 输出：基于知识库的流式回答 + 可追溯引用；
- 边界：不做订单查询、不做真实交易、不替用户下单，也不访问企业外部系统。

系统不是“通用聊天机器人”，而是**有知识边界的售前助手**：资料不足时应明确说明，而不是用模型常识补全。

```text
                               │ HTTPS / SSE
┌──────────────────────────────▼───────────────────────────────┐
│                      FastAPI（uvicorn）                        │
│  中间件：请求日志 / 指标 / CORS                                  │
│  鉴权：JWT / 限流 / 管理员                                       │
│  路由：auth  chat  knowledge  evaluation  health                │
│  服务：chat  retrieval  reranker  bm25  query_strategy          │
│        intent  rag  llm  evaluation  ingestion                 │
└───────┬───────────────┬───────────────┬───────────────┬───────┘
        │               │               │               │
   ┌────▼────┐     ┌────▼────┐     ┌────▼────┐     ┌────▼─────────┐
   │ MySQL 8 │     │ Redis   │     │ Milvus  │     │ 本地模型       │
   │ 业务数据 │     │ 缓存/限流│     │ dense+  │     │ BGE-M3        │
   │ 评估结果 │     │ 验证码   │     │ sparse  │     │ reranker      │
   └─────────┘     └─────────┘     └─────────┘     │ intent-BERT   │
                                                   └──────┬────────┘
                                                          │
                                                   ┌──────▼────────┐
                                                   │ LLM API        │
                                                   │ DeepSeek/千问   │
                                                   └───────────────┘
```

外部依赖职责：

| 组件 | 存什么 | 丢了会怎样 |
|---|---|---|
| MySQL | 用户、知识库、文档、父子分块、会话、消息、知识缺口、评估运行 | 业务数据丢失，必须备份 |
| Redis | 验证码、意图/向量/检索/策略/答案缓存、限流窗口 | 只是降级变慢，不影响正确性 |
| Milvus | 子分块向量（dense + sparse） | 检索为空，需要重建索引 |
| 本地模型 | BGE-M3、BGE-reranker、意图 BERT | 无法向量化/重排序/识别意图，启动校验失败 |
| LLM API | 查询改写、策略扩展、最终回答、RAGAS 裁判 | 无法生成答案；检索指标仍可离线跑 |

**MySQL 是事实来源，Milvus 是可重建索引，Redis 是可丢弃缓存。**

分层原则：

- **路由只做参数校验、权限、事务边界**，不写检索/生成逻辑；
- **服务层不依赖 FastAPI**，评估脚本可以直接复用 `retrieval`、`rag`、`llm`；
- **纯函数优先**：RRF、BM25 打分、指标计算、SSE 解析都可以脱离外部服务单测；
- **重依赖懒加载**：PDF/Office/OCR/模型在首次使用时导入，保证启动轻量。

## 四、文档入库数据流

### 4.1 入口

`POST /api/documents/upload`（multipart）：

| 字段 | 说明 |
|---|---|
| `file` | 必填，≤50MB，扩展名白名单 |
| `chunk_size` | 可选，100–2000 |
| `chunk_overlap` | 可选，0–1000，且小于 `chunk_size` |
| `embedding_mode` | `dense` / `hybrid` |
| `parser` | `auto` / `mineru` |
| `force_new` | 强制作为新文档，不参与版本替换 |

### 4.2 同步阶段（请求内完成）

```text
1. 校验知识库归属（只允许 owner 写）
2. save_upload()
   - 文件名清洗（路径穿越、控制字符、长度 200）
   - 扩展名白名单
   - 分块写入 uploads/kb_<id>/<uuid>.<ext>，边写边计数
   - 超过 MAX_UPLOAD_MB 立即删除并报错
3. 创建 Document：
   status=pending, version=1, is_current=true,
   chunk_size/overlap/embedding_mode/parser 固化到文档
4. 知识库 document_count += 1
5. 写入 async_tasks（status=pending）并提交事务
6. 通过 BackgroundTasks 触发 execute_task 加速；worker 轮询是兜底
7. 返回 202 + 文档摘要
```

请求内不做解析和向量化，避免大文件把 HTTP 连接占满。任务行已持久化，
即使进程重启，启动恢复也会重新领取；BackgroundTasks 只是加速路径。

### 4.3 后台入库阶段

```text
Document(status=processing)
        │
        ▼
[1] 解析 parse_document()
    auto：Markdown / PDF(fitz) / PPTX / DOCX / 图片(RapidOCR)
    mineru：调用 Docker 容器做复杂版式、表格、扫描件识别
    输出 ParsedDocument(blocks=[ParsedBlock(text, title, section, page)])
        │
        ▼
[2] 正文清理与指纹
    clean_text()：统一换行、去零宽字符、压缩空行
    Fingerprint：normalize_text → SHA-256 + SimHash + 长度
        │
        ▼
[3] 文档级判重（同一知识库）
    完全同哈希              → unchanged：标记 skipped，删除上传文件，结束
    SimHash 距离 ≤ 阈值     → update：进入版本替换
    无相似文档              → created
    force_new=true          → 跳过替换，作为新文档
        │
        ▼
[4] 父子切块 split_with_parents()
    按 (title, section, page) 连续分组
    句子为最小单元 → 聚合父块（约 1200 字）
    父块内 → 切子块（默认 500 字，重叠 80）
    父块/子块都做内容哈希，去掉完全重复
        │
        ▼
[5] 向量化 embedding_service.embed_documents()
    BGE-M3 输出 dense(1024) + sparse
    按 EMBEDDING_BATCH_SIZE 分批
    受 MAX_CONCURRENT_EMBEDDING 信号量约束
        │
        ▼
[6] MySQL 事务（先落库）
    写 parent_chunks、chunks（chunk_uid 由 doc_id+version+区块+内容哈希确定性生成）
    更新 document：processing、chunk_count
    同一事务写入 vector_outbox(op=replace_doc)
    知识库统计更新，提交
        │
        ▼
[7] 向量同步（outbox）
    collection: fitrag
    每条子块：chunk_uid 主键、kb_id/doc_id/chunk_index、
             content/title/section/page、dense、sparse
    批量 200 条 upsert（确定性 UID ⇒ 重试幂等）
    删除重建索引中已消失的 stale_uids
        │
        ▼
[8] 版本收敛
    本次文档：completed、is_current=true、update_action
    若是 update：旧文档 is_current=false、action=superseded，
                 删除旧 DB 行并写入 delete_doc 派生条目
        │
        ▼
[9] 失效缓存
    invalidate_search_caches(kb_id)
    Redis：检索缓存 + 回答缓存
    进程内：BM25 索引
        │
        ▼
[10] 结束
    成功：保留上传文件，记录日志
    unchanged：删除重复上传文件
    向量同步失败：outbox 保留 pending，按指数退避重试（重启后继续）
    解析/编码失败：status=failed + error_message，旧版本保持可检索
```

### 4.4 版本切换安全

版本替换不是“先删旧再写新”，而是：

1. 新版本分块与 `vector_outbox` 先提交，此时新文档 `is_current=false`；
2. outbox 完成向量 upsert 后，同一事务把新文档置为 `is_current=true/completed`，旧文档置为 `is_current=false` 并清理旧行；
3. 任一步失败时旧版本仍是 current，继续服务；新版本重试或最终失败。

因此入库失败不会导致知识库“空窗”。检索与 `enrich_hits` 都只认 `is_current=true`。

### 4.5 重新索引

`POST /api/documents/{id}/reindex`：

- 复用原文件与参数，重新解析、切块、向量化；
- 写入新的持久化任务行，由 worker 异步执行；
- 新分块先落库并写 outbox，向量就绪后删除 `stale_uids`，避免残留命中；
- 失败时保留旧分块（`reindex_failed`），不把文档置为不可用。

### 4.6 删除链路

删除知识库：

```text
校验 owner → 删除 MySQL（documents/chunks/parent_chunks/knowledge_bases）
          → 同一事务写入 vector_outbox(op=delete_kb) → 提交
          → 删除 uploads/kb_<id>/ 文件
          → 失效缓存与 BM25 索引
          → 立即尝试同步向量；失败由 worker 重试
```

删除文档：

```text
校验归属 → 删除 DB 记录 → 同一事务写入 vector_outbox(op=delete_doc)
         → 提交 → 删除原文件 → 失效缓存 → 立即尝试同步向量
```

DB-first：即使 Milvus 短暂不可用，删除意图也已持久化，outbox 会重试到成功；
`enrich_hits` 同时丢弃数据库中不存在的 `chunk_uid`，不会召回已删内容。

### 4.7 分块编辑

`PATCH /api/chunks/{uid}`：

1. 更新子块正文与哈希；
2. 重新计算父块正文与哈希；
3. 同一事务写入 `vector_outbox(op=upsert_chunk)` 并提交；
4. 立即尝试重编码并 upsert 到 Milvus，失败留给 worker；
5. 失效检索/回答缓存与 BM25 索引。

单块编辑不重建整篇文档，避免高成本。

### 4.8 任务队列与启动恢复

- `async_tasks`：`pending → running → succeeded/failed`，带 `attempts/max_attempts`、
  `lease_until`、`available_at`（指数退避）；
- `vector_outbox`：`replace_doc` / `upsert_chunk` / `delete_doc` / `delete_kb` /
  `delete_chunk`，DB 提交后同步 Milvus，失败重试；
- 领取使用 `SELECT ... FOR UPDATE SKIP LOCKED`，多 worker 不重复消费；
- 启动恢复：回收过期租约、为 `pending/processing` 且无活跃任务的文档补入队、
  超过 `UPLOAD_TASK_TTL` 仍未完成的任务标记失败；
- 同一文档同类型任务去重，只保留一个未完成行。

## 六、数据模型

### 6.1 实体关系

```text
users
 ├──1:N── knowledge_bases
 │          ├──1:N── documents ──1:N── parent_chunks
 │          │                     └──1:N── chunks
 │          └──1:N── knowledge_gaps（逻辑关联，无 FK）
 ├──1:N── conversations ──1:N── chat_messages
 └──1:N── eval_runs ──1:N── eval_cases
```

### 6.2 表说明

| 表 | 关键字段 | 说明 |
|---|---|---|
| `users` | `username` 唯一、`password_hash`、`is_active`、`is_admin` | 账号与角色 |
| `knowledge_bases` | `owner_id`、`name`、`embedding_mode`、`chunk_size/overlap`、`is_public`、`document_count` | 同一 owner 下名称唯一 |
| `documents` | `status`、`version`、`is_current`、`content_hash`、`content_simhash`、`replaces_doc_id`、`update_action`、`force_new` | 版本化文档 |
| `parent_chunks` | `uid`、`doc_id`、`content`、`title/section/page` | 章节级上下文 |
| `chunks` | `uid`、`parent_uid`、`content`、`content_hash`、`chunk_index` | 检索最小单元 |
| `conversations` | `kb_ids`、`model_name`、`temperature/top_p/max_tokens`、`history_rounds`、`archived_at` | 会话配置快照 |
| `chat_messages` | `role`、`content`、`sources`、`intent`、`rewritten_query`、`latency_ms` | 消息与引用 |
| `knowledge_gaps` | `question`、`best_score`、`vector_score`、`rerank_score`、`retrieval_mode`、`status` | 检索失败的问题 |
| `eval_runs` | 数据集、策略、TopK、裁判模型、聚合指标、状态 | 评估运行 |
| `eval_cases` | 逐题问题、答案、命中、doc/section 指标、RAGAS 分数 | 评估明细，级联删除 |

### 6.3 关键约束

- `documents.status`：`pending` → `processing` → `completed` / `failed` / `skipped`；
- `chunks.uid` / `parent_chunks.uid` 全局唯一，同时作为 Milvus 主键；
- `conversations.kb_ids` 是 JSON 数组，删除知识库后历史会话仍保留 ID，但再次提问会校验失败；
- `knowledge_gaps` 没有 FK，删除会话不会级联删除缺口；
- `eval_cases` 对 `eval_runs` 级联删除；
- 所有时间字段使用数据库本地时间（`server_default=now()`），维护任务用 UTC 去时区后比较。

### 6.4 Milvus Collection

| 项 | 值 |
|---|---|
| 数据库 | 默认 `asktofit` |
| Collection | 默认 `fitrag` |
| 主键 | `chunk_uid` VARCHAR(64) |
| 标量字段 | `kb_id`、`doc_id`、`chunk_index`、`content`(16384)、`title`/`section`(512)、`page` |
| dense | FLOAT_VECTOR，维度 1024 |
| sparse | SPARSE_FLOAT_VECTOR |
| dense 索引 | HNSW，COSINE，M=16，efConstruction=200 |
| sparse 索引 | 倒排索引，IP，drop_ratio_build=0.2 |
| 一致性 | Bounded |
| 写入批量 | 200 |

Milvus 中不存父块正文，父块只在 MySQL，检索命中后回表扩展。

## 七、缓存与索引

### 7.1 Redis 键空间

| 前缀 | 内容 | TTL | 失效时机 |
|---|---|---|---|
| `asktofit:intent:` | 意图结果 | 86400s | 自然过期 |
| `asktofit:embedding:` | 查询 dense+sparse | 86400s | 自然过期 / 模型变化即键变化 |
| `asktofit:strategy:` | 策略计划 | 3600s | 配置变化即键变化 |
| `asktofit:retrieval:` | 检索结果 | 180s；降级/空 30s | 知识库写操作 |
| `asktofit:answer:` | 完整回答 | 300s | 知识库写操作 |
| `captcha:*` | 图形验证码 | 300s | 校验后删除 |
| `ratelimit:*` | 滑动窗口 ZSet | 窗口长度 | 自动裁剪 |

键都带内容哈希与配置指纹：

- 检索键包含 query 列表、策略、BM25 模式、RRF K、dense/sparse 权重、重排序参数、去重阈值；
- 回答键包含完整 messages、模型名、温度、top_p、max_tokens。

### 7.2 进程内索引

BM25 索引存在进程内存：

```
{ kb_id: { docs, tokens, df, avgdl, built_at } }
```

- TTL 默认 120 秒；
- 每 KB 一把 `asyncio.Lock`，并发首查只建一次；
- 写操作通过 `invalidate_search_caches(kb_id)` 立即清空；
- 多 worker 下各进程独立，靠 TTL 收敛；生产建议单 worker 或后续引入 Redis 代次号。

### 7.3 缓存一致性

```text
文档入库 / 更新 / 删除 / 重建
分块编辑 / 删除
知识库删除
        │
        ▼
invalidate_search_caches(kb_id)
        ├─ Redis：检索 + 回答缓存
        └─ BM25：该 KB 索引
```

意图、向量、策略缓存不随知识库变化失效，因为它们不包含知识内容。

## 八、降级矩阵

| 组件故障 | 系统行为 | 用户感知 | 恢复方式 |
|---|---|---|---|
| Redis 不可用 | 缓存与限流放行 | 变慢，限流失效 | Redis 恢复后自动 |
| 意图 BERT 不可用 | 关键词规则 | 意图可能略偏 | 重启或修复模型 |
| 查询改写失败 | 用原问题检索 | 多轮指代效果下降 | LLM 恢复 |
| 策略生成失败 | direct | 复杂问题召回变少 | LLM 恢复 |
| 单个 query 向量化失败 | 其余 query 继续 | 召回略少 | 自动 |
| 单个向量路失败 | 其他路继续 | 无 | 自动 |
| 全部向量失败 + BM25 可用 | BM25 兜底 | 语义召回下降 | Milvus 恢复 |
| 向量与 BM25 全失败 | `error` 事件 | 提示检索失败 | 外部服务恢复 |
| 重排序失败，`drop` | 丢弃候选，记缺口 | 回答“资料不足” | 重启/恢复模型 |
| 重排序失败，`vector` | 向量分排序 | 正常但精度下降 | 自动 |
| 父子块扩展 DB 失败 | 用原始命中 | 上下文较短 | DB 恢复 |
| LLM 不可用 | `error` 事件 | 提示生成失败 | 服务商恢复 |
| 助手消息落库失败 | 仍发 `done` | 刷新后可能缺消息 | DB 恢复 |

原则：**检索失败不编造，生成失败不假装成功，降级必须显式。**

## 九、可观测性

### 9.1 日志

- 控制台 + `logs/app.log` 双输出；
- 格式：`时间 | 级别 | 文件:行号 | logger | 消息`；
- 轮转：10MB × 5；
- Windows 控制台强制 UTF-8；
- 请求日志带 `X-Request-ID` 与耗时；
- 关键阶段：意图、改写、策略、召回、重排序、首包、完成、缺口。

### 9.2 指标

`GET /api/metrics`（Prometheus 文本）：

| 指标 | 类型 | 标签 |
|---|---|---|
| `asktofit_http_requests_total` | counter | method、route、status |
| `asktofit_http_request_duration_seconds` | histogram | method、route |
| `asktofit_intent_total` | counter | intent、source |
| `asktofit_retrieval_strategy_total` | counter | strategy、source、outcome |
| `asktofit_retrieval_duration_seconds` | histogram | strategy |
| `asktofit_retrieval_candidates_total` | counter | strategy |
| `asktofit_rerank_failures_total` | counter | — |
| `asktofit_bm25_searches_total` | counter | mode、outcome |
| `asktofit_bm25_fallback_total` | counter | reason |
| `asktofit_cache_hits_total` | counter | cache |
| `asktofit_llm_requests_total` | counter | model、status |
| `asktofit_knowledge_gaps_total` | counter | intent |

指标存进程内存，多 worker 时各进程独立，由 Prometheus 汇总。

### 9.3 健康检查

`GET /api/health` 只表示进程可响应，不探测 MySQL / Milvus / LLM。完整可用性需要：

- 启动日志无模型缺失；
- `/api/chat/options` 返回至少一个 `available=true` 的模型；
- 实际上传与提问成功。

## 十一、关键设计取舍

| 选择 | 替代方案 | 为什么选当前方案 |
|---|---|---|
| 本地 BGE-M3 + 本地重排序 | 全用外部 embedding/rerank API | 数据不出内网、成本可控、离线可评估 |
| dense + sparse 混合 | 只用 dense | 型号、金额、专有名词等精确匹配更稳 |
| BM25 纯 Python | rank-bm25 / jieba | 无停更依赖，兼容 Python 3.13，token 规则可控 |
| RRF 融合 | 分数加权求和 | 跨模式、跨查询分数量纲不可比 |
| 查询相关摘要 + 短候选 | 全文送入交叉编码器 | CPU 上延迟从数十秒降到数秒 |
| 子块检索 + 父块回答 | 只用大块或只用小块 | 小块检索准，父块上下文完整 |
| Redis 缓存 + 写路径统一失效 | 不缓存或只靠 TTL | 常见问题零检索延迟，更新后立即生效 |
| SSE 流式 | 一次性 JSON | 首屏更快，长回答体验更好 |
| 评估指标本地纯函数 + RAGAS overlay | 全用 RAGAS | 检索指标无需 LLM、可离线、零成本；RAGAS 依赖隔离 |
| 版本化入库 | 覆盖写 | 失败不空窗，可追溯替换关系 |
| 管理员看板只读 | 页面触发评估 | 评估依赖 ragas overlay，不适合放进运行时进程 |
