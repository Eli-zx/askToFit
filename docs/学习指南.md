## 0. 如何使用这份指南

### 0.1 三条学习路线

| 路线 | 适合谁 | 时间 | 阅读顺序 |
|---|---|---:|---|
| 快速上手 | 只想先跑起来看看 | 半天 | 第 1、2、3、4 章 → 登录问一个问题 → 第 7 章 |
| 系统掌握 | 要接手开发或维护 | 2–3 天 | 从头按章节读，完成第 18 章实验 1–4 |
| 改造开发 | 要改检索、入库、前端或评估 | 1 周 | 第 5–10、16 章精读，配合对应深入文档与源码 |

### 0.2 阅读约定

- 所有文件路径都相对于项目根目录，例如 [app/services/chat.py](../app/services/chat.py)。
- “链路”指一次用户操作从 HTTP 请求到落库/返回的完整路径。
- 带 `Config.xxx` 的配置都能在 [config.py](../config.py) 和 [docs/配置参数手册.md](配置参数手册.md) 中找到。
- 本文负责“建立完整心智模型 + 指路”，细节以源码和专项文档为准；每章末尾都给出核实入口。
- 不建议一上来逐行读代码。先建立数据流，再带着问题跳到具体函数。

### 0.3 一张图记住整个系统

```text
                     ┌──────────────────────────────┐
                     │        Vue 3 前端 (SPA)       │
                     │ 登录 / 对话 / 知识库 / 缺口 / 评估 │
                     └──────────────┬───────────────┘
                                    │ HTTP + SSE (/api)
                     ┌──────────────▼───────────────┐
                     │        FastAPI 应用           │
                     │  routes → services → models  │
                     └───┬────────┬────────┬────────┘
                         │        │        │
              ┌──────────▼─┐ ┌────▼────┐ ┌▼─────────────┐
              │   MySQL    │ │  Redis  │ │    Milvus    │
              │ 唯一真相源  │ │ 缓存/限流│ │ 向量索引(可重建)│
              └────────────┘ └─────────┘ └──────────────┘
                         │
              ┌──────────▼──────────────────────────┐
              │ 本地模型：BGE-M3 / BGE-Reranker / BERT │
              │ 外部服务：LLM API / MinerU(Docker 可选) │
              └─────────────────────────────────────┘
```

三条最重要的设计原则：

1. **MySQL 是唯一真相源**。文档、分块、父块、会话、缺口、评估结果都在 MySQL；Milvus 和 Redis 都可以重建。
2. **写路径先 DB 后向量**。分块与 `vector_outbox` 同事务提交，再由 outbox 同步 Milvus，避免“库里有、检索不到”。
3. **检索与生成解耦**。检索层不调用 LLM（策略层除外），回答层只消费合格上下文；评估也把检索指标和生成指标分开报告。

## 1. 项目定位：它到底是什么

AskToFit 是一个**电商服装售前知识问答系统**，核心是 RAG（Retrieval-Augmented Generation，检索增强生成）：

```text
用户问题
  → 意图识别
  → 多轮查询改写
  → 检索策略规划
  → 多知识库 / 多查询 / 多模式召回
  → RRF 融合 + BM25 词法召回
  → BGE 重排序
  → 阈值过滤 + 父块补全
  → 组装提示词
  → LLM 流式回答（SSE）
```

### 1.1 它解决的问题

服装售前咨询有大量重复但细节密集的问题：尺码、面料、退换货、运费、发票、物流、会员优惠。答案必须来自商家的真实政策，不能让模型自由发挥。系统因此强调：

- **答案有出处**：每条回答带知识引用（文档名、章节、页码、得分）。
- **政策可运营**：知识库随时上传、判重、版本切换；检索不到的问题进入“知识缺口”供运营补料。
- **效果可度量**：有离线评估集、检索指标、RAGAS 生成指标和管理员看板。
- **性能可解释**：检索、重排、首包、总耗时都有日志和 Prometheus 指标。

### 1.2 它不是什么

- 不是通用聊天机器人：没有知识库或资料不足时会明确拒答，而不是闲聊补全。
- 不是模型训练项目：本地只训练了一个小型意图分类 BERT；生成依赖外部 LLM API。
- 不是多模态生成系统：图片只在入库阶段做 OCR，问答输出仍是文本。
- 不是微服务架构：单个 FastAPI 进程 + 前端静态站点，依赖外部 MySQL/Redis/Milvus。

### 1.3 一次完整的业务闭环

```text
运营上传文档
   ↓
解析 → 判重 → 父子分块 → 向量化 → 写 MySQL/Outbox → 同步 Milvus
   ↓
用户提问 → 检索 → 重排 → 生成 → 引用
   ↓
检索不到 → 记录知识缺口 → 管理员查看 → 补文档 → 再入库
   ↓
离线评估 / 线上指标 → 调参 → 回归
```

理解这条闭环，比记住某个函数的实现更重要。

## 2. 技术栈与系统边界

### 2.1 技术栈

| 层 | 技术 | 说明 |
|---|---|---|
| 后端语言 | Python 3.13+ | 使用 `uv` 管理依赖 |
| Web 框架 | FastAPI | 异步、自动 OpenAPI 文档 |
| ORM | SQLAlchemy 2.x（async） | `aiomysql` 运行时，`pymysql` 建库 |
| 数据库 | MySQL 8 | 业务数据唯一真相源 |
| 缓存/限流 | Redis 6+ | 验证码、多级缓存、滑动窗口限流 |
| 向量库 | Milvus 2.4.x | dense + sparse 混合检索 |
| 嵌入模型 | BGE-M3（本地） | 1024 维 dense + sparse 权重 |
| 重排模型 | BGE-reranker-v2-m3（本地） | Cross-Encoder |
| 意图模型 | 自训练 BERT（本地） | 10 类意图 + 关键词兜底 |
| LLM | DeepSeek / DashScope 兼容接口 | 流式生成 |
| 前端 | Vue 3 + Vite 6 + Pinia + Vue Router + Element Plus | 单页应用 |
| 前端测试 | Vitest + jsdom；Playwright 脚本 | 单元 + E2E |
| 后端测试 | pytest + fakeredis + 内存 SQLite + Fake 向量库 | 不依赖真实外部服务 |
| 评估 | 本地纯函数 + 官方 RAGAS 0.3.0（overlay） | 检索与生成分开 |
| 压测 | Locust（独立依赖组） | SSE 首包/总耗时分开统计 |
| 部署 | Docker + Nginx + GitHub Actions | CD 只推镜像，不自动部署 |

### 2.2 外部依赖与“缺了会怎样”

| 依赖 | 必需性 | 缺失/故障时 |
|---|---|---|
| MySQL | 必需 | 启动失败；无法登录、入库、问答 |
| 本地 BGE-M3 | 必需（检索） | 启动校验失败；关闭校验也无法检索 |
| 本地 Reranker | 默认开启 | 可降级为向量顺序；`drop` 会丢弃资料 |
| 本地意图 BERT | 默认开启 | 自动回退关键词规则，不阻断问答 |
| Redis | 强烈建议 | 验证码不可用；缓存/限流放行，服务变慢 |
| Milvus | 必需（向量检索） | 向量路失败；BM25 `fallback` 可临时兜底 |
| LLM API Key | 必需（生成） | 检索仍可跑，回答生成失败；`/options` 标记不可用 |
| Docker + MinerU 镜像 | 可选 | 仅选择 MinerU 解析时失败，标准解析不受影响 |

### 2.3 关键版本约束

| 约束 | 原因 |
|---|---|
| `pymilvus` 必须 2.4.x | 混合检索使用 2.4 的底层 handler，启动时会校验 |
| 向量维度固定 1024 | 与 Milvus collection schema 绑定；换模型必须重建 collection |
| RAGAS 只通过 overlay 安装 | 避免 LangChain 依赖污染运行时 `.venv` |
| 不引入 `rank-bm25` / `jieba` | 前者停更、后者无 Python 3.13 wheel；项目自带纯 Python BM25 |
| Node 20 | 前端构建与 CI 基线 |
| MySQL 8 | 入库任务使用 `FOR UPDATE SKIP LOCKED` |

## 3. 环境准备与首次启动

### 3.1 前置条件

- Python 3.13+
- [uv](https://docs.astral.sh/uv/) 0.9.x
- Node.js 20 + npm
- MySQL 8（本地或远程）
- Redis 6+
- Milvus 2.4.x（Standalone 或集群）
- 至少 16GB 内存（本地 CPU 跑 BGE-M3 + Reranker 的实际需求）
- 本地模型目录：
  - `models/bge-m3`
  - `models/bge-reranker-v2-m3`
  - `models/intent-bert`

### 3.2 第一次启动（按顺序）

```bash
# 1. 安装后端依赖
uv sync

# 2. 准备环境变量
cp .env.example .env
# 编辑 .env：MySQL / Redis / Milvus / 模型路径 / LLM Key / JWT_SECRET

# 3. 安装前端依赖
cd frontend && npm ci && cd ..

# 4. 启动后端
uv run uvicorn app.main:app --reload --host 0.0.0.0 --port 8000

# 5. 另开终端启动前端
cd frontend && npm run dev
```

访问：

- 前端：<http://127.0.0.1:5173>
- 接口文档：<http://127.0.0.1:8000/docs>
- 健康检查：<http://127.0.0.1:8000/api/health>

### 3.3 启动时后端做了什么

`app.main.lifespan` 的顺序（见 [app/main.py](../app/main.py)）：

1. `setup_logging()`：控制台 + 文件双输出，格式含文件名:行号。
2. `Config.ensure_dirs()`：创建上传、日志、数据目录。
3. `Config.validate_model_paths()`：按开关检查模型目录。
4. `ensure_database()`：MySQL 库不存在则创建。
5. `init_models()`：`create_all` 建表。
6. `ensure_schema_upgrades()`：给存量表幂等补列/索引。
7. `sync_admin_users()`：把 `ADMIN_USERNAMES` 中的账号提升为管理员。
8. 启动四个后台任务：
   - `cleanup_loop`：会话归档、过期任务清理；
   - `warmup_models`：依次加载 intent / embedding / reranker 并做一次极短推理；
   - `keep_warm_loop`：按 `MODEL_WARMUP_INTERVAL_SECONDS` 周期保活；
   - `task_worker`：入库任务 + 向量 outbox worker。
9. 关闭时：停止后台任务、关闭 LLM 客户端、Redis、数据库引擎。

### 3.4 首次验证清单

```bash
# 1. 健康检查
curl http://127.0.0.1:8000/api/health

# 2. 配置与模块导入
uv run python -c "from config import Config; print(Config.app_name, Config.embedding_dim, Config.collection_name)"

# 3. 后端单测（不需要真实 MySQL/Milvus/模型）
uv run python -m pytest tests/ -q

# 4. 前端单测与构建
cd frontend && npm run test && npm run build
```

然后在浏览器中：

1. 注册账号（需要图形验证码）。
2. 创建一个知识库（建议先设为私有）。
3. 上传一份 Markdown，等待状态变为 `completed`。
4. 新建会话（默认已选中公共的服装售前知识库；要检索其他库需在「新建对话」里手动勾选），提问。
5. 观察回答是否流式输出、是否带引用。

### 3.5 导入演示业务文档（可选）

```bash
# 导入指定账号名下的公共知识库，并做真实检索抽查
uv run python scripts/import_business_docs.py --username <你的账号>
```

脚本会解析 `data/business_docs/` 下的 PDF / PPTX / DOCX / Markdown / 图片，执行判重、分块、向量化，然后跑几条检索抽查。导入完成后，其他账号也能在知识库列表和对话设置中看到这个公共库。

### 3.6 启动常见故障

| 现象 | 优先检查 |
|---|---|
| 启动报数据库连接失败 | MySQL 是否启动、账号是否有建库权限、`.env` 是否被进程环境变量覆盖 |
| 启动报模型目录不存在 | `BGE_M3_PATH` / `BGE_RERANKER_PATH` / `INTENT_MODEL_PATH`；或临时关闭 `VALIDATE_MODELS_ON_STARTUP`（但问答仍会失败） |
| 登录页验证码一直报错 | Redis 是否可达；验证码一次性使用，刷新后需重新输入 |
| 上传后一直 `pending` | `task_worker` 是否启动；看日志中的任务领取与失败原因 |
| 上传后 `failed` 且提示 Milvus | Milvus 版本是否 2.4.x、collection 是否可加载、outbox 是否在重试 |
| 前端 401/跨域 | 后端是否在 8000；开发代理 `/api` 是否正常；生产 CORS 配置 |
| 第一次提问特别慢 | 模型预热是否完成；日志中是否有“模型预热完成” |

更完整的排查见 [docs/运维与故障排查.md](运维与故障排查.md)。

### 4.2 后端分层与依赖方向

```text
FastAPI routes
   │  参数校验、鉴权、SSE 包装
   ▼
services
   │  业务编排、检索、入库、LLM、缓存、评估
   ▼
models / db / core
   │  持久化、日志、安全、Redis
   ▼
外部基础设施：MySQL / Redis / Milvus / 模型 / LLM
```

规则：

- **routes 不写业务算法**。路由只负责取参数、查权限、调用 service、转换响应。
- **services 不 import routes**。服务层可被 API、脚本、测试共同复用。
- **模型层不做网络请求**。ORM 只描述表结构。
- **跨服务复用优先走 service 单例**，例如 `retrieval_service`、`llm_service`、`embedding_service`。

### 4.4 分阶段代码阅读地图

> 不要从 `app/` 的第一个文件按目录顺序读到最后。**按调用链读**：先找到入口，再沿调用往里走，每读完一个阶段用“自检问题”验证；答不上来就回到对应文件重读。

四条阅读原则：

1. **先跑通，再读代码**。看不懂某个分支时，先构造能触发它的请求，对照日志读。
2. **从入口往实现读**。顺序永远是 `routes → service → model / 外部客户端`。
3. **一次只追一条链路**。同一时间只追“上传”或“提问”，不要两边来回跳。
4. **每个结论都要能落到文件**。读完一个阶段，应能说出“这个行为在哪个函数里实现”。

八个阶段的推荐顺序：

| 阶段 | 主题 | 对应章节 | 预计时间 |

`stream_reply` 的阅读顺序（一次只读一段）：

```text
意图识别 → status(retrieving)
→ trim_history → should_rewrite → rewrite_query（失败回退原问题）
→ query_strategy.plan（失败回退 direct）
→ retrieval.retrieve → enrich_hits（失败直接 error 结束）
→ _filter_qualified → 无合格资料则 _record_gap_safe
→ build_sources → yield meta
→ build_llm_messages → answer_key → 缓存命中则直接分片回放
→ 未命中：LLM 流式生成 delta → 持久化 → yield done
```

必须掌握的分支：

| 分支 | 触发点 | 结果 |
|---|---|---|
| 问候语 | `intent == "greeting"` | 跳过改写/检索，直接生成 |
| 改写失败 | `rewrite_query` 抛 `LLMError` | 用原问题继续 |
| 策略失败 | `query_strategy_service.plan` 异常 | 回退 `direct` 单查询 |
| 检索异常 | `retrieve`/`enrich_hits` 抛错 | SSE `error`，不产生回答 |
| 无合格资料 | `_filter_qualified` 为空 | 记录知识缺口，提示模型无资料 |
| 回答命中缓存 | `answer_key` 命中 | 按 32 字符分片回放，仍写 `done` |
| 重排失败/超时 | `rerank_failed` / `rerank_timeout` | 按 `rerank_failure_mode` 降级，见第 10.5 节 |

## 5. 数据模型与存储

### 5.1 四种存储的角色

| 存储 | 角色 | 丢失后果 | 恢复方式 |
|---|---|---|---|
| MySQL | 唯一真相源 | 业务数据丢失 | 备份恢复 |
| Milvus | 可重建的向量索引 | 向量检索为空 | 从 MySQL 分块重新向量化 |
| Redis | 可丢弃的缓存/验证码/限流 | 变慢、验证码失效 | 自动回源，无需恢复 |
| uploads/ | 原始文件 | 无法重新解析/重建索引 | 文件备份 |
| 本地模型 | 推理能力 | 无法检索/重排/意图 | 重新下载/训练 |

### 5.2 MySQL 表一览

| 表 | 作用 | 关键字段 |
|---|---|---|
| `users` | 用户 | `username` 唯一、`password_hash`、`is_active`、`is_admin` |
| `knowledge_bases` | 知识库 | `owner_id`、`name`、`is_public`、`embedding_mode`、默认切块参数 |
| `documents` | 文档与版本 | `status`、`version`、`is_current`、`content_hash`、`content_simhash`、`replaces_doc_id`、`parser`、`force_new` |
| `parent_chunks` | 父分块（章节级上下文） | `uid` 全局唯一、`doc_id`、`parent_index`、`content`、`title`、`section`、`page` |
| `chunks` | 子分块（检索单元） | `uid` 全局唯一、`parent_uid`、`chunk_index`、`content`、`content_hash` |
| `conversations` | 会话 | `user_id`、`kb_ids`、`model_name`、温度/top_p/max_tokens/history_rounds、`archived_at` |
| `chat_messages` | 消息 | `role`、`content`、`sources`、`intent`、`rewritten_query`、`latency_ms` |
| `knowledge_gaps` | 知识缺口 | `user_id`、`question`、`intent`、`best_score`、`status`、`note` |
| `async_tasks` | 持久化入库队列 | `task_type`、`status`、`document_id`、`attempts`、`lease_until` |
| `vector_outbox` | 向量同步 outbox | `op`、`payload`、`status`、`attempts`、`lease_until` |
| `eval_runs` | 评估运行 | 数据集哈希、KB、策略、指标 JSON、状态 |
| `eval_cases` | 评估逐题结果 | `run_id`、问题、答案、命中、指标、错误 |

### 5.3 文档状态机

`documents.status`：

```text
pending ──► processing ──► completed
                    │
                    ├──► failed
                    └──► skipped（内容未变化）
```

- `pending`：任务已入队，尚未被 worker 领取。
- `processing`：解析/切块/向量化中。
- `completed`：分块与向量都已就绪，`is_current=true` 时参与检索。
- `failed`：解析、入库或向量同步失败；`error_message` 记录原因。
- `skipped`：判定为内容未变化，不产生新版本；该记录 `is_current=false`，原文档继续有效。

`async_tasks.status`：

```text
pending → running → succeeded
                  ├→ failed（达到最大尝试次数）
                  └→ 租约过期 → 被其他 worker 接管
```

`vector_outbox.status` 类似，只是操作类型不同：`replace_doc` / `delete_doc` / `delete_kb` / `upsert_chunk` / `delete_chunk`。

### 5.4 版本与“当前文档”

- 同一逻辑文档更新时，新记录 `version = 旧版本 + 1`，`replaces_doc_id` 指向旧记录。
- 新版本完成分块与向量同步前，旧版本保持 `is_current=true`，继续可检索。
- 新版本完全成功后，旧版本置为 `is_current=false`，退出检索。
- 检索后 `enrich_hits` 会再次校验 `is_current`，防止索引里残留旧数据。

### 5.5 Milvus schema

Collection 默认名 `fitrag`，主键是 `chunk_uid`（不是 MySQL 自增 id）：

| 字段 | 类型 | 说明 |
|---|---|---|
| `chunk_uid` | VARCHAR(64), PK | 与 `chunks.uid` 一致，确定性生成 |
| `kb_id` / `doc_id` / `chunk_index` | INT64 | 过滤与回溯 |
| `content` / `title` / `section` | VARCHAR | 检索展示与 BM25 字段 |
| `page` | INT64 | 页码 |
| `dense_vector` | FLOAT_VECTOR(1024) | HNSW + COSINE |
| `sparse_vector` | SPARSE_FLOAT_VECTOR | 倒排索引 + IP |

设计要点：

- **主键确定性**：`sha256(doc_id:version:kind:index:content_hash)` 截断，重试写入是幂等覆盖，不会产生重复向量。
- **Milvus 可重建**：只要 MySQL 的 `chunks` 和原始文件还在，就可以重新生成。
- **集合不自动迁移**：改 collection 名或向量维度后必须重新入库。

### 5.6 Redis 键与 TTL

| 前缀 | 内容 | 默认 TTL |
|---|---|---|
| `captcha:` | 图形验证码 | 300 秒，一次性删除 |
| `asktofit:intent:` | 意图分类结果 | 86400 秒 |
| `asktofit:embedding:` | 查询向量 | 86400 秒 |
| `asktofit:strategy:` | 检索策略计划 | 3600 秒 |
| `asktofit:retrieval:` | 检索结果 | 180 秒；降级/空结果 30 秒 |
| `asktofit:answer:` | 完整回答 | 300 秒 |
| `asktofit:kbver:` | 知识库版本号 | 7 天，写入时刷新 |

检索缓存键包含：查询文本、KB 列表与模式、`final_k`、`recall_k`、策略、BM25 模式、RRF K、配置指纹、KB 版本号、全局版本号。因此：

- 任一 KB 内容变化，只递增该 KB 版本，旧键自然不命中；
- 改重排/融合参数会改变配置指纹，旧缓存自然失效；
- 多 worker 共享 Redis 时，版本化失效比 scan 删除更安全。

### 5.7 一致性规则

1. **DB 先提交，向量后同步**：分块 + outbox 同事务；outbox 失败可重试。
2. **任务可恢复**：服务启动时回收过期租约、补入队丢失任务、清理超期任务。
3. **多 worker 不重复执行**：`SELECT ... FOR UPDATE SKIP LOCKED` 领取任务。
4. **检索时二次校验**：DB 可达时丢弃索引中已删除的分块和非 current 文档。
5. **缓存可丢**：任何缓存缺失都回源，不把 Redis 当存储。

## 6. 文档入库全链路

入口：`POST /api/knowledge_bases/{kb_id}/documents`

### 6.1 总览

```text
上传请求
  → 权限/大小/扩展名校验
  → 保存原始文件
  → 创建 Document(status=pending)
  → 写入 async_tasks(pending)
  → 立即返回 202 + 任务信息
        │
        ▼（后台 worker）
  claim task（租约 + SKIP LOCKED）
  → 解析（auto / MinerU）
  → 归一化正文 + 指纹
  → 判重决策（created / update / unchanged）
  → 父子分块
  → 向量化
  → 同事务写 chunks / parent_chunks / vector_outbox
  → outbox 同步 Milvus
  → 切换版本（旧版本 is_current=false）
  → 清理缓存（Redis + BM25）
  → 任务 succeeded
```

### 6.2 上传阶段

关键文件：[app/api/routes/knowledge.py](../app/api/routes/knowledge.py)、[app/services/storage.py](../app/services/storage.py)

- 校验知识库存在且当前用户有写权限（私有库仅创建者；公共库也只有创建者可写）。
- 校验扩展名（`pdf, ppt, pptx, md, markdown, doc, docx, png, jpg, jpeg`）和大小（`MAX_UPLOAD_MB`，默认 50MB）。
- 允许每次上传覆盖 `chunk_size`、`chunk_overlap`、`embedding_mode`、`parser`、`force_new`，并固化到 `Document`。
- 原始文件写入 `uploads/`，数据库记录 `stored_name` / `file_path`。
- 写 `async_tasks` 后立即返回 **202**，而不是等解析完成。

为什么异步：PDF/PPTX 解析、OCR、模型向量化可能耗时数十秒到数分钟，不能阻塞 HTTP 请求；持久化任务还能在服务重启后继续。

### 6.3 任务领取

关键文件：[app/services/task_queue.py](../app/services/task_queue.py)、[app/services/task_worker.py](../app/services/task_worker.py)

- worker 空转时按 `TASK_POLL_SECONDS` 轮询。
- 领取时设置 `status=running`、`lease_until=now+TASK_LEASE_SECONDS`、`attempts+1`。
- 使用 `FOR UPDATE SKIP LOCKED`，多进程不会抢到同一条任务。
- 进程崩溃后，租约过期的任务会被其他 worker 回收；`attempts >= max_attempts` 则失败。
- 服务启动时还会：
  - 为 `documents.status in (pending, processing)` 但无任务的文档补入队；
  - 清理超过 `UPLOAD_TASK_TTL` 的已完成任务与 outbox 记录。

### 6.4 解析

关键文件：[app/services/parsers.py](../app/services/parsers.py)、[app/services/mineru_parser.py](../app/services/mineru_parser.py)

| 解析器 | 适用 | 行为 |
|---|---|---|
| `auto` | 默认 | Markdown、PDF(fitz)、PPTX、DOCX、图片 OCR；旧 `.doc` 按 LibreOffice → antiword → OLE 文本降级 |
| `mineru` | 复杂版式、扫描件、跨页表格 | 调 Docker 容器解析；单并发、超时 900 秒、内存限制 |

解析产物是 `ParsedDocument`，包含按块组织的文本、标题、章节、页码等元数据。Markdown 会保留标题层级；PDF/PPTX/DOCX 中的图片会 OCR，作为可检索文本入库。

**失败语义**：

- 显式选择 MinerU 后，Docker/镜像/解析失败 → 文档标记 `failed`，不会静默降级。
- 重建索引失败 → 保留旧分块与向量，旧版本继续可检索。

### 6.5 判重

关键文件：[app/services/ingestion.py](../app/services/ingestion.py)、[app/services/dedup.py](../app/services/dedup.py)

先归一化正文：NFKC、去空白/标点、去 Markdown/HTML/URL 等，再计算：

- `content_hash`：归一化文本的 SHA-256；
- `content_simhash`：64 位 SimHash；
- `content_length`：归一化长度。

决策顺序：

```text
force_new=true
  → created（跳过判重）

同知识库、is_current=true、completed 的候选中：

1) 同名文档
   内容哈希相同 → unchanged（skipped）
   否则         → update（作为新版本）

2) 不同名文档
   归一化哈希相同 → unchanged
   长度比 < 0.35 → 跳过该候选
   SimHash 距离 > DOC_DEDUP_SIMHASH_MAX_DISTANCE → 跳过
   文本相似度 ≥ DOC_DEDUP_SIMILARITY（默认 0.90） → update
   否则 → created
```

这解决了几个常见坑：

- 只改标点、格式、文件名 → 识别为同一内容，不产生重复文档。
- 内容相近但文件名不同 → 作为同一逻辑文档的新版本，旧版本退出检索。
- 内容确实不同 → 作为独立文档入库。
- 需要保留两份相似文档 → 上传时勾选“强制作为新文档入库”。

### 6.6 父子分块

关键文件：[app/services/text_splitter.py](../app/services/text_splitter.py)

为什么要父子分块：

- 子块小（默认 500 字左右）→ 向量语义集中，检索精度高；
- 父块大（默认 1200 字左右）→ 命中子块后补全章节上下文，避免答案被切断；
- 送进提示词的是**父块正文**，但检索和重排序基于子块。

流程：

1. 按 Markdown 标题 / 章节 / 页码把解析块聚合成父块（目标 `PARENT_CHUNK_SIZE`）。
2. 在父块内部按句子打包成子块（目标 `CHUNK_SIZE`，重叠 `CHUNK_OVERLAP`）。
3. 子块短于 `MIN_CHUNK_SIZE` 会尝试合并；超长单元硬切；完全重复的子块去重。
4. 每个父块、子块记录 `title`、`section`、`page`，供引用与 BM25 字段加权。
5. UID 由 `doc_id + version + kind + index + content_hash` 确定性生成。

### 6.7 向量化与事务写入

关键文件：[app/services/ingestion.py](../app/services/ingestion.py)、[app/services/embedding.py](../app/services/embedding.py)

- 对每个子块构造嵌入文本：`title + section + content`。
- BGE-M3 同时产出 dense 向量和 sparse 权重。
- 向量化走线程池，受 `MAX_CONCURRENT_EMBEDDING` 限制，不阻塞事件循环。
- 同一个数据库事务内写入：
  - `parent_chunks`
  - `chunks`
  - `vector_outbox(op=replace_doc, payload={doc_id})`
- 提交后由 worker 处理 outbox，把该文档的所有向量幂等写入 Milvus。

为什么用 outbox：如果先写 Milvus 再写 MySQL，进程崩溃会产生“检索得到但 DB 没有”的孤儿向量；反过来先写 MySQL 再同步 Milvus，最坏情况是短暂“DB 有、索引无”，可通过重试修复。

### 6.8 版本切换

```text
新版本文档解析/分块/向量全部成功
  → 旧文档 is_current=false
  → 新文档 is_current=true
  → 新文档 status=completed
```

任一步失败：

- 新版本标记失败；
- 旧版本保持 `is_current=true`；
- 失败版本的临时分块与向量清理走 outbox。

重建索引（reindex）也遵循同样原则：失败不会破坏当前可检索版本。

### 6.9 缓存失效

关键文件：[app/services/search_index.py](../app/services/search_index.py)

以下写操作完成后统一调用 `invalidate_search_caches(kb_id)`：

- 文档入库成功 / 跳过未变化；
- 删除文档；
- 编辑分块；
- 删除分块；
- 删除知识库；
- 重建索引。

它会同时：

1. 递增 Redis 中该 KB 的版本号（检索/回答缓存自然失效）；
2. 清理 BM25 进程内索引。

新增写路径时也必须调用这个 helper，否则会出现“数据库已更新但检索还是旧结果”。

### 7.3 阶段细节

#### 1–2. 鉴权、限流、会话与知识库

- 聊天限流按**用户维度**；登录/注册按 IP + 用户名维度。
- Redis 异常时限流放行，不阻断服务。
- 会话必须属于当前用户。
- `kb_ids` 会先过滤为当前用户可见的知识库：
  - 私有库：仅创建者；
  - 公共库：所有登录用户可见/可检索，但只有创建者可编辑。
- 按知识库的 `embedding_mode` 分组为 `kb_modes`，例如 `{"hybrid": [7], "dense": [8]}`。

#### 3. 历史裁剪

`trim_history` 只保留最近 `history_rounds` 个逻辑轮（每轮 2 条消息），并受 `MAX_HISTORY_CHARS` 总预算限制。历史用于两处：

- 查询改写：把“那运费呢”补全为完整问题；
- 提示词：让模型理解上下文。

#### 4. 意图识别

10 类：退换货、发票、物流、支付结算、退款与资金安全、尺码、会员与优惠、商品咨询、问候、综合咨询。

判断顺序：

1. 整句问候语正则优先短路；
2. BERT 分类；
3. 置信度低于 `INTENT_CONFIDENCE_THRESHOLD` 或 top1-top2 边际低于 `INTENT_MARGIN_THRESHOLD` → 关键词规则；
4. 模型异常/关闭 → 关键词规则。

意图的用途：

- `greeting` 是**唯一跳过检索**的意图；
- 其他意图参与查询改写判断、策略触发和缺口分组；
- 前端只展示意图标签/来源，不展示概率。

#### 5. 查询改写

仅在需要时触发：

- 不是首轮；
- 不是问候；
- 满足以下任一：
  - 含追问线索：这个、那个、它、这件、那件、这款、那款、哪款、哪件、哪个、还有、那么、呢、同上、刚才、刚刚、上面、前面、上述、上次、来着、换成、如果、再；
  - 问题 ≤ 6 字且意图为 `other`（极短碎片，如“有货吗”）；
  - 问题 6–10 字、意图为 `other`，且不像完整疑问句（如“对照预算做取舍”）。带“吗/怎么/多少/多久/什么/是否/？”等完整疑问结构的短问题保持独立检索，避免把上一轮主题拼进去（如“支持以旧换新吗”）。

改写使用低温 LLM，输出经过清理；如果模型没有真正改写，会用上一轮完整问题拼接补全。**检索使用改写后的问题，最终提示词使用用户原问题**。

#### 6. 策略规划

`StrategyPlan`：

```python
strategy: "direct" | "hyde" | "subquery" | "backtrack"
queries: tuple[str, ...]      # 第一条始终是原改写问题
rerank_query: str             # 始终是原改写问题
source: "rule" | "llm" | "fallback" | "disabled"
```

规则优先级：`subquery > backtrack > hyde > direct`。详见第 8.2 节。

#### 7–10. 检索、融合、重排、补全

这是系统的核心，第 8 章展开。这里记住四个不变量：

1. **HyDE / 子查询 / 回溯文本只用于召回**，不进入提示词、不进入 `sources`、不返回前端。
2. **重排序始终使用原始改写问题**，避免扩展查询丢掉金额、时效、条件。
3. **BM25 词法召回始终使用原始改写问题**，额外查询只走向量。
4. **命中子块，返回父块正文**；引用仍记录子块的文档/章节/页码。

#### 11. 阈值过滤与知识缺口

`_filter_qualified` 的规则：

- 若存在 `rerank_failed`：
  - `RERANK_FAILURE_MODE=drop`（默认）→ 丢弃本轮资料；
  - `vector` → 保留并使用向量顺序。
- 若有 `rerank_score`：按 `RERANK_SCORE_THRESHOLD`（默认 0.25）过滤。
- 若未启用重排序：保留向量召回结果。

过滤后为空且不是问候 → 写入 `knowledge_gaps`，记录：

- 用户、会话、问题、意图与置信度；
- 所选 KB；
- `best_score`、`vector_score`、`rerank_score`、`retrieval_mode`；
- 初始状态 `open`。

注意：缺口判定基于**过滤后**结果，不是“完全没有召回”。

#### 12–14. 引用、缓存、提示词

`sources` 每条包含：

```json
{
  "doc_id": 12,
  "doc_name": "物流仓配与时效说明.md",
  "chunk_uid": "...",
  "title": "...",
  "section": "四、运费标准",
  "page": 3,
  "score": 0.87,
  "vector_score": 0.72,
  "rerank_score": 0.87,
  "retrieval_source": "fused"
}
```

具体字段以 [app/services/rag.py](../app/services/rag.py) 的 `build_sources` 为准。前端只展示可读字段，不展示 HyDE 文本。

回答缓存键由**完整 messages + 模型 + 温度 + top_p + max_tokens** 组成。因此：

- 上下文变化 → 键变化 → 自然不命中；
- 知识更新 → 检索结果变化 → 键变化；
- 相同问题在不同历史下不会错误复用答案。

提示词预算：

- `MAX_CONTEXT_CHARS`（默认 6000）：所有资料的总字符预算；
- `MAX_HISTORY_CHARS`（默认 3000）：历史总预算；
- 超出时按优先级裁剪，保证当前资料优先。

#### 15–16. 流式生成与持久化

SSE 事件：

| 事件 | 时机 | 关键字段 |
|---|---|---|
| `status` | 开始检索 | `stage`、`intent`、`intent_confidence`、`intent_source` |
| `meta` | 检索完成、生成前 | `sources`、`rewritten_query`、`retrieval_strategy`、`strategy_source`、`retrieval_query_count` |
| `delta` | 每个 token/片段 | `content` |
| `done` | 生成完成 | 完整内容、sources、intent、`latency_ms`、`cache_hit` |
| `error` | 失败 | `message` |

超时/断开的处理：

- 客户端断开（`CancelledError`）：保存已生成部分，释放 LLM 槽位。
- LLM 错误：保存已生成部分，发送 `error`。
- 空回答：发送 `error`，不写缓存。
- 回答成功后写 `chat_messages`，更新会话的 `message_count` 和 `last_message`。

### 7.4 关键不变量（务必记住）

1. 检索用**改写后问题**，生成用**原问题**。
2. 重排用**改写后问题**，扩展文本只影响召回。
3. 只有 `greeting` 跳过检索。
4. 引用来自**过滤后的合格命中**，不是全部候选。
5. 知识缺口记录的是“检索到了但都不合格”或“完全没检索到”的问题。
6. 回答缓存键包含完整提示词，不按问题文本简单缓存。
7. 检索失败与生成失败是两种不同的错误，前端提示也不同。

## 8. 检索子系统深潜

### 8.1 查询理解

三层：

```text
意图识别（这是什么类问题）
  → 查询改写（把追问补全成独立问题）
  → 策略规划（这个问题需要几种查法）
```

注意职责边界：

- 意图**不直接决定检索哪个知识库**，只影响改写、策略、缺口和展示。
- 改写只解决指代/省略，不改写业务事实。
- 策略只决定“怎么查”，不决定“查什么知识库”。

### 8.2 多策略检索

| 策略 | 触发线索（规则） | 生成内容 | 召回查询 | 是否进入提示词 |
|---|---|---|---|---|
| `direct` | 默认；短实体、数字、金额 | 无 | 原问题 | 是（原问题） |
| `hyde` | 抽象方法类：“为什么/怎么选/如何选择/怎么判断/适合/推荐/介绍”，长度 ≥ 12 | 2–3 句假设答案 | 原问题 + 假设答案 | 否 |
| `subquery` | 多要素：“并且/以及/分别/同时/还有/另外/对比/区别/哪个更/两个问号” | 最多 3 条子查询 | 原问题 + 子查询 | 否 |
| `backtrack` | 条件/宽泛：“如果/这种情况/怎么办/能不能/是否可以/遇到”，长度 ≥ 24 | 更宽泛/更基础的问题 | 原问题 + 简化问题 | 否 |

规则优先级：`subquery > backtrack > hyde > direct`。

其他行为：

- `STRATEGY_ENABLED=false` → 全部 direct。
- `STRATEGY_SELECTOR_LLM_ENABLED=false`（默认）→ 规则决定策略，LLM 只生成扩展文本。
- 生成超时/失败/空输出 → 回退 direct，`source=fallback`。
- 子查询去编号、去重、去空、截断到 `STRATEGY_MAX_QUERY_CHARS`；原问题始终排第一。
- 策略结果缓存 `STRATEGY_CACHE_TTL`。

为什么默认不让 LLM 选策略：每问多一次 LLM 往返会显著增加首包延迟；规则已经能覆盖大多数模式。

### 8.3 向量召回

召回组合数 = `查询数 × KB 模式数`。

- KB 模式来自知识库的 `embedding_mode`：
  - `dense`：只用 dense 向量；
  - `hybrid`：dense + sparse，Milvus `WeightedRanker`，权重 `DENSE_WEIGHT` / `SPARSE_WEIGHT`；
  - `sparse`：只用 sparse。
- 每个组合取 `CANDIDATE_K`（默认 20）条。
- 单组合失败只记录日志，其他组合继续；全部失败才考虑 BM25 兜底。
- 不捕获 `asyncio.CancelledError`，保证取消能向上传播。

### 8.4 BM25 词法召回

关键文件：[app/services/bm25.py](../app/services/bm25.py)

- 纯 Python Okapi BM25，不依赖第三方分词库。
- 中文按 **unigram + bigram**，英文/数字按整词；NFKC + 小写。
- 字段加权：标题 > 章节 > 正文（默认 3.0 / 2.0 / 1.0）。
- 每个 KB 一份进程内索引，TTL 默认 120 秒。
- 建索引与打分走 `asyncio.to_thread`，受 `BM25_MAX_CONCURRENT_SEARCHES` 限制。
- 索引容量按 `BM25_MAX_CORPUS_CHUNKS` / `BM25_MAX_TOTAL_CHUNKS` / `BM25_MAX_INDEXED_KBS` 做上限与 LRU 淘汰。

三种模式：

| 模式 | 行为 | 适用 |
|---|---|---|
| `fuse`（默认） | BM25 结果作为一个 list，与向量路一起 RRF | 型号、金额、专有名词；正常路径也有词法召回 |
| `fallback` | 仅当向量为空/异常时使用 BM25 | 最省 CPU，向量库故障时兜底 |
| `off` | 完全不调用 | 排查问题或纯向量实验 |

注意：

- 多 worker 各自维护索引，写操作只能清理当前进程；索引 TTL 会收敛。
- 索引 TTL 内新文档可能不可见，但写路径会主动失效。
- 重排序关闭时，BM25-only 命中按 `BM25_MIN_QUERY_COVERAGE` 过滤。
- `RERANK_FAILURE_MODE=drop` 仍会丢弃 BM25-only 候选；需要降级运行可改 `vector`。

### 8.5 RRF 融合

关键文件：[app/services/fusion.py](../app/services/fusion.py)

RRF（Reciprocal Rank Fusion）公式：

```text
score(d) = Σ weight_i / (K + rank_i(d))
```

- `rank_i(d)` 从 1 开始；
- `K` 默认 60，起平滑作用；
- 每个 list 先按分数降序、`chunk_uid` 升序确定性排序并去重；
- 同一 UID 在多个 list 命中时分数累加；
- 保留向量路中的最佳 `vector_score`；BM25-only 记 `0.0`；
- 写入 `fused_score`、`retrieval_sources`。

为什么用 RRF 而不是直接分数相加：hybrid 的 WeightedRanker 分、dense cosine 分、BM25 分**量纲不同**，直接比较无意义；RRF 只看排名，天然可跨路融合。

### 8.6 重排序

关键文件：[app/services/reranker.py](../app/services/reranker.py)

- 模型：BGE-reranker-v2-m3（Cross-Encoder）。
- 只取融合后的前 `RERANK_CANDIDATE_K`（默认 5）条。
- 每条候选构造“查询 + 相关性摘要”（`RERANK_PASSAGE_CHARS`，默认 160 字）。
- 输出 `rerank_score`，按分数降序取 `final_k`。
- 失败/超时语义：

| 配置/情况 | 行为 |
|---|---|
| 正常 | 写入 `rerank_score`，`score_mode=rerank` |
| 推理超时 | 按向量顺序降级，标记 `rerank_timeout`，不触发熔断 |
| 推理失败 | `RERANK_FAILURE_MODE=drop` 丢弃；`vector` 保留向量顺序 |
| 连续失败达到 `RERANK_MAX_CONSECUTIVE_FAILURES` | 熔断，需重启进程恢复 |
| `RERANK_ENABLED=false` | 直接使用融合/向量排序 |

性能经验（CPU）：

- 单候选约 1.0–1.3 秒；
- 降低 `RERANK_CANDIDATE_K` 比缩短文本更有效；
- 默认 5 候选 × 160 字 × 192 token，本机约 4.7–5.5 秒；
- 并发受 `RERANK_MAX_CONCURRENT` 限制，CPU 下是吞吐瓶颈。

冷启动边界：模型加载在推理超时**之外**执行（`rerank()` 先 `await asyncio.to_thread(_ensure_model)`，再开始计算 `RERANK_TIMEOUT_SECONDS` 预算）。否则首次加载的数十秒会被误判为推理超时并降级。启动预热成功后正常请求不承担加载耗时；CLI、评估脚本等未预热路径首次调用会等加载完成，但不会触发 `rerank_timeout`。

### 8.7 三级去重

| 层级 | 时机 | 依据 | 参数 |
|---|---|---|---|
| 文档级 | 入库判重 | 归一化哈希、SimHash、文本相似度 | `DOC_DEDUP_SIMILARITY`、`DOC_DEDUP_SIMHASH_MAX_DISTANCE` |
| 分块级 | 切块后 | 子块归一化哈希 / 近重复 | `CHUNK_NEAR_DUP_SIMILARITY` |
| 检索级 | 融合/重排后 | 父块相同、归一化哈希相同、SimHash + 文本相似度 | `RETRIEVAL_DEDUP_SIMILARITY` |

检索级去重顺序：

1. 同一 `parent_uid` 只保留第一条；
2. 归一化正文哈希相同 → 丢弃；
3. SimHash 距离在阈值内且文本相似度 ≥ 阈值 → 丢弃。

这样提示词里不会出现同一段资料的多个近似副本。

### 8.8 父块补全

`enrich_hits` 做四件事：

1. 查 `documents`，只保留 `is_current=true` 的文档；
2. 查 `chunks`，丢弃数据库中已不存在的 UID（防止 BM25 索引 TTL 内的残留）；
3. 用 `parent_uid` 查 `parent_chunks`，用父块正文替换子块正文；
4. 保留 `child_content` 供调试，补全 `doc_version`、`title`、`section`、`page`。

DB 查询失败时返回原始命中（不阻断问答），但会记录异常日志。

### 8.9 得分字段契约

| 字段 | 含义 | 何时存在 |
|---|---|---|
| `score` | 当前阶段排序分 | 始终 |
| `vector_score` | 最佳向量召回分 | 向量命中；BM25-only 为 0.0 |
| `bm25_score` | 原始 BM25 分 | BM25 命中 |
| `bm25_coverage` | 查询词覆盖比例 | BM25 命中 |
| `fused_score` | RRF 融合分 | 多路融合 |
| `retrieval_source` | `vector` / `bm25` / `fused` | 召回阶段 |
| `retrieval_sources` | 命中来源列表 | 融合路径 |
| `rerank_score` | 交叉编码器分数 | 重排成功 |
| `score_mode` | `vector` / `rerank` | 重排后 |
| `rerank_failed` | 重排失败标记 | 失败路径 |
| `rerank_timeout` | 重排超时标记 | 超时路径 |

排查“分数为什么不对”时，先确认看的是哪个阶段的字段，不要跨量纲比较。

两个最容易被误读的量纲：

```text
vector_score = DENSE_WEIGHT * (1 + dense_cosine) / 2
             + SPARSE_WEIGHT * (0.5 + atan(sparse_ip) / π)
rerank_score = sigmoid(cross_encoder_logit)
```

- `vector_score` 的归一化把余弦从 `[-1, 1]` 压到 `[0, 1]`：dense cosine 0.5 就会得到 0.75。知识库中**与问题无关的段落也常落在 0.65–0.75**，因此它只能说明“主题/字面相近”，不能单独判断相关性。
- `rerank_score` 是交叉编码器的相关性概率：真正相关的问答对通常 > 0.8，完全答非所问约 0.000x；`RERANK_SCORE_THRESHOLD=0.25` 以下的候选不会进入回答。
- 缺口记录同时保存两者，`best_score` 在有重排时取重排分。看到“向量 0.68、重排 0.0025”时，含义是**召回到了主题相近但不回答问题的资料**，属于知识缺口，不是分数计算错误。

### 8.10 调参决策树

```text
答案找不到 / 召回不足
  ├─ doc Hit 低 → 提高 CANDIDATE_K；开启 BM25 fuse；检查分块是否切断
  ├─ Recall 低、Hit 高 → 多要素问题检查 subquery 是否触发；提高候选数
  ├─ MRR/NDCG 低 → 重排是否开启；提高候选数或检查阈值
  └─ 关键词覆盖低 → 检查父块扩展、分块大小、重排摘要长度

答案有噪声 / 答非所问
  ├─ ContextPrecision 低 → 提高 RERANK_SCORE_THRESHOLD；减少 RETRIEVAL_K
  ├─ 回答超出资料 → 降低温度；强化提示词；检查上下文预算
  └─ 资料对但答案错 → 检查提示词与模型；看 sources 是否真的包含关键事实

太慢
  ├─ 重排慢 → 降 RERANK_CANDIDATE_K > PASSAGE_CHARS > MAX_LENGTH
  ├─ 首包慢 → 降 history_rounds；关闭策略生成；检查模型预热
  ├─ 检索慢 → 检查 Milvus/BM25 索引；关闭不必要的多查询
  └─ 生成慢 → 换模型；降低 max_tokens；检查 LLM 排队
```

### 8.11 检索缓存键

`retrieval_key` 包含：

- 查询文本；
- `kb_modes`（模式 → KB id 列表）；
- `final_k` / `recall_k`；
- 实际 `queries` 列表；
- `strategy`；
- `bm25_mode`；
- `rrf_k`；
- 配置指纹（dense/sparse 权重、重排开关与参数、去重阈值、BM25 权重等）；
- 各 KB 版本号；
- 全局版本号。

因此以下变化都会让旧缓存失效：

- 知识库内容变化；
- 改查询策略或扩展查询；
- 改融合/重排/去重参数；
- 改 BM25 模式。

## 9. 提示词、上下文与回答

关键文件：[app/services/rag.py](../app/services/rag.py)

### 9.1 提示词结构

`build_llm_messages` 组装：

```text
system：角色、业务边界、引用要求、资料不足时拒答
user：
  历史对话（裁剪后）
  检索资料（父块正文，按得分排序，带来源编号）
  用户当前问题（原始问题，不是改写问题）
```

原则：

- 资料是“证据”，不是“可选参考”；资料不足必须明确说明。
- 禁止编造金额、时效、政策、库存等事实。
- 引用编号与 `sources` 对应。
- 历史只用于理解上下文，不能覆盖当前资料。

### 9.2 上下文预算

| 预算 | 默认 | 行为 |
|---|---:|---|
| `MAX_CONTEXT_CHARS` | 6000 | 资料总字符上限，超出按得分优先级截断 |
| `MAX_HISTORY_CHARS` | 3000 | 历史总字符上限 |
| `MAX_TOKENS_DEFAULT` | 1024 | 默认输出上限 |
| `MAX_TOKENS_LIMIT` | 4096 | 会话可配置上限 |

调参注意：

- 资料预算不是越大越好：噪声和 token 成本会上升；
- 父块本身较大（默认 1200 字），`RETRIEVAL_K=5` 时很容易接近预算；
- 如果关键事实总在块尾，优先检查分块和 `RERANK_PASSAGE_CHARS`，而不是盲目加大预算。

### 9.3 拒答

系统在两类情况下应拒答：

1. 检索无合格资料（记录缺口，提示资料不足）；
2. 资料存在但不包含问题所需事实（由提示词约束模型承认“未收录/未说明”）。

评估中的“正确拒答率”就是检查第二类：不可回答问题是否明确承认资料不足，而不是编造。

### 9.4 回答缓存

- 键：完整 messages + 模型 + 温度 + top_p + max_tokens。
- TTL：`ANSWER_CACHE_TTL`（默认 300 秒）。
- 命中时仍然逐段发送 `delta`，并返回 `cache_hit=true`。
- 缓存的是**完整回答**，不是检索结果；知识变化会通过检索结果变化导致键变化。

## 10. 缓存、限流、并发与容错

### 10.1 多级缓存

| 缓存 | 键的核心 | 默认 TTL | 失效方式 |
|---|---|---|---|
| 意图 | 问题 + 模型 | 1 天 | TTL |
| 查询向量 | 文本 + 模型 | 1 天 | TTL |
| 策略 | 问题 + 意图 + 配置版本 | 1 小时 | TTL |
| 检索 | 查询 + KB + 策略 + 配置 + 版本 | 180 秒 | KB 版本递增 |
| 回答 | 完整提示词 + 模型参数 | 300 秒 | 检索结果变化 / KB 版本 |
| 验证码 | captcha_id | 300 秒 | 一次性删除 |

写入策略：

- 正常检索结果用正常 TTL；
- 重排降级/空结果用 `RETRIEVAL_DEGRADED_CACHE_TTL`（30 秒）；
- 由异常产生的空结果**不写缓存**，避免一次抖动压制整个 TTL；
- TTL 加随机抖动（`CACHE_TTL_JITTER`，默认 0.1），避免同时过期。

### 10.2 Single-flight

同一进程内，相同检索键的并发未命中只允许一个请求回源，其余等待并复用结果。

- 只对检索生效；
- 按事件循环隔离，避免测试中多个 `asyncio.run` 复用旧锁；
- 多 worker 部署时每个进程各合并一次。

### 10.3 限流

- 聊天：按用户，`RATE_LIMIT_REQUESTS` / `RATE_LIMIT_WINDOW_SECONDS`。
- 登录/注册：按 IP（登录额外按用户名），`RATE_LIMIT_LOGIN_REQUESTS`。
- 实现：Redis ZSet 滑动窗口。
- Redis 异常：放行并记录告警。

### 10.4 LLM 容错

| 机制 | 配置 | 行为 |
|---|---|---|
| 超时 | `LLM_TIMEOUT_SECONDS` | 单次请求超时 |
| 重试 | `LLM_MAX_RETRIES` | 只重试超时、连接错误、限流、429、5xx |
| 退避 | `LLM_RETRY_BACKOFF_SECONDS` | 指数退避，上限 8 秒 + 抖动 |
| 熔断 | `LLM_CIRCUIT_FAILURE_THRESHOLD` / `RESET_SECONDS` | 连续失败后快速失败，冷却后半开 |
| 并发槽位 | `MAX_CONCURRENT_LLM` | 每进程最多同时 N 路生成 |
| 排队超时 | `LLM_QUEUE_TIMEOUT_SECONDS` | 等槽位超时返回“当前咨询较多” |

注意：

- 已输出 token 后不重试，避免重复内容；
- SDK 自身重试关闭，避免叠加；
- 槽位在成功、失败、取消、流式断开时都会释放。

### 10.5 降级矩阵

| 故障 | 默认行为 | 可配置 |
|---|---|---|
| Redis 不可用 | 缓存/限流放行 | — |
| 意图模型失败 | 关键词规则 | `INTENT_ENABLED=false` |
| 向量路失败 | BM25 `fallback`（若启用） | `BM25_MODE=fallback` |
| 重排超时 | 向量顺序 + `rerank_timeout` | `RERANK_TIMEOUT_SECONDS` |
| 重排失败 | `drop` 丢弃 / `vector` 保留 | `RERANK_FAILURE_MODE` |
| Milvus 不可用 | 向量路失败；BM25 兜底 | `BM25_MODE=fallback` |
| LLM 不可用 | 返回错误事件 | 换模型 / 恢复 Key |
| MinerU 不可用 | 显式选择时失败；未选择不受影响 | 改用 auto |

### 10.6 可观测性

日志：

- 控制台 + `logs/app.log`；
- 格式含 `文件名:行号`；
- 关键指标：`检索耗时`、`重排序完成`、`首包到达`、`回答完成`。

Prometheus `GET /api/metrics`：

- HTTP 请求量/延迟；
- LLM 调用；
- 检索候选数/耗时；
- 策略、BM25 兜底；
- 缓存命中与限流。

### 11.4 SSE 前端流程

```text
用户输入
  → 创建/复用会话
  → fetch POST（Accept: text/event-stream）
  → 逐块读取
  → 解析 event/data
  → status：显示“检索中”
  → meta：渲染引用、策略、意图
  → delta：追加到气泡
  → done：替换为完整内容、刷新会话列表
  → error：显示错误并允许重试
```

关键实现点：

- 不能假设一个网络 chunk 等于一个事件，必须按 `\n\n` 分帧并保留半帧；
- `done` 中的完整内容应覆盖流式拼接结果，避免丢字；
- 组件卸载或切换会话时要中断请求；
- 引用在生成前就通过 `meta` 到达，因此可以先展示来源，再逐步生成答案。

## 12. 评估体系

关键文件：[app/services/evaluation.py](../app/services/evaluation.py)、[scripts/evaluate_rag.py](../scripts/evaluate_rag.py)

### 12.1 为什么拆成两套指标

| 类别 | 指标 | 依赖 LLM | 回答的问题 |
|---|---|---|---|
| 检索 | Hit@K、Recall@K、MRR、NDCG@K、关键词覆盖 | 否 | 该找的资料找到了吗？排得够前吗？ |
| 生成 | Faithfulness、AnswerRelevancy、ContextPrecision、ContextRecall | 是（RAGAS 裁判） | 答案忠于资料吗？切题吗？ |

混成一个分数无法定位问题：检索差要调召回/重排，生成差要调提示词/模型。

### 12.2 数据集

`data/evaluation/qa_eval.jsonl`，手写 60 条，覆盖 9 份业务文档、10 类意图；10–15 条不可回答，至少 10 条多跳/对比/条件题。

字段：

| 字段 | 必填 | 说明 |
|---|---|---|
| `id` | 是 | 唯一编号 |
| `question` | 是 | 用户问题 |
| `ground_truth` | 是 | 参考答案 |
| `expected_doc_names` | 是（可空） | 期望文档名，对应 `Document.original_name` |
| `expected_sections` | 否 | 期望章节片段 |
| `expected_keywords_all` | 否 | 必须全部出现的关键词 |
| `expected_keywords_any` | 否 | 至少出现其一 |
| `answerable` | 是 | 是否可由知识库回答 |
| `intent` | 是 | 意图标签 |
| `tags` | 否 | `single-hop` / `multi-hop` / `conditional` / `unanswerable` |

约束：

- `answerable=false` 时 `expected_doc_names` 必须为空；
- `answerable=true` 时，doc/section/keywords 至少有一项；
- `id` 全局唯一；
- 数据集 SHA-256 写入报告，确保两次运行可比。

### 12.3 检索指标定义

设 `K` 为返回条数，`E` 为期望单元集合，`R` 为前 K 条覆盖的单元：

```text
Hit@K    = 前 K 条至少命中一个期望单元
Recall@K = |R| / |E|
RR       = 1 / 第一个命中单元的排名
MRR      = 所有题目 RR 的均值
NDCG@K   = DCG@K / IDCG@K（二元增益，同一单元只计一次）
```

文档名与章节在比较前做 NFKC、小写、去空白和标点，再做双向包含匹配。

### 12.4 生成指标与拒答

- 四项 RAGAS 指标只聚合 `answerable=true` 的样本。
- 不可回答样本单独统计：
  - `count`；
  - `refused`；
  - `refusal_accuracy`。
- 拒答判定是启发式：答案中出现“未收录、未找到、未提及、未说明、无法确认、无法给出、抱歉”等即视为正确拒答。
- RAGAS 缺失值记 `null`，不记 0；均值只对有有限值的样本计算。

### 12.5 运行命令

```bash
# 只校验数据集格式（CI 同款，不连 DB，不需要 ragas）
uv run python scripts/evaluate_rag.py --validate-dataset

# 连知识库校验期望文档/章节
uv run python scripts/evaluate_rag.py --validate-only

# 仅检索指标
uv run python scripts/evaluate_rag.py --retrieval-only --limit 10 --strategy direct
uv run python scripts/evaluate_rag.py --retrieval-only --limit 10 --strategy auto

# 检索 + 官方 RAGAS（overlay，不污染运行时 .venv）
uv run --with-requirements scripts/eval_requirements.txt \
  python scripts/evaluate_rag.py --limit 5 \
  --judge-metrics faithfulness,answer_relevancy

# 全量
uv run --with-requirements scripts/eval_requirements.txt \
  python scripts/evaluate_rag.py --limit 60 --strategy auto
```

参数：

| 参数 | 说明 |
|---|---|
| `--dataset` | 数据集路径 |
| `--kb-name` / `--kb-id` | 评估目标知识库 |
| `--top-k` | 检索返回条数，默认 10 |
| `--limit` | 只跑前 N 条 |
| `--strategy auto\|direct\|hyde\|subquery\|backtrack` | 检索策略 |
| `--retrieval-only` / `--no-llm` | 跳过生成指标 |
| `--judge-model` | RAGAS 裁判模型 |
| `--judge-metrics` | 只跑指定生成指标 |
| `--persist/--no-persist` | 是否写入 `eval_runs` / `eval_cases` |
| `--output-dir` | 报告目录，默认 `reports/` |

### 12.6 报告与看板

每次运行产出：

- `reports/eval_<timestamp>.json`
- `reports/eval_<timestamp>.md`
- 可选 `reports/ragas_<timestamp>.csv`

报告包含：

- `metadata`：数据集哈希、KB、策略、TopK、样本数、RAGAS 版本、配置快照；
- `aggregate.retrieval.doc` / `.section`；
- `aggregate.retrieval.keyword_coverage`；
- `aggregate.generation`（仅可回答）；
- `aggregate.unanswerable`；
- `aggregate.valid_counts`；
- `aggregate.by_intent` / `by_tag`；
- `cases`：逐题问题、答案、命中、指标、错误。

持久化后，管理员可在前端“评估看板”查看概览、趋势、运行列表和逐题详情。概览/趋势只统计 `status=success` 且样本数 ≥ `EVAL_MIN_MEANINGFUL_SAMPLES`（默认 10）的运行。

### 12.7 当前基线（2026-10-18，run 13）

```text
样本：60（可回答 48，不可回答 12）
doc      Hit@10 0.9375  Recall@10 0.9375  MRR 0.8333  NDCG@10 0.8596
section  Hit@10 0.9167  Recall@10 0.9167  MRR 0.7931  NDCG@10 0.8242
```

- 必须同时看 `sample_count` 和 `valid_counts`；

- section 级只统计配置了期望章节的题目，不能和 doc 级直接横比。

## 13. 测试体系

### 13.1 测试分层

| 层级 | 工具 | 命令 | 依赖 |
|---|---|---|---|
| 后端单元 | pytest | `uv run python -m pytest tests/ -v` | 无外部服务 |
| 前端单元 | Vitest | `cd frontend && npm run test` | mock API |
| 端到端 | Playwright 脚本 | `cd frontend && npm run test:e2e` | 后端 + 前端 + MySQL/Redis/Milvus |
| 数据集校验 | 纯文件 | `uv run python scripts/evaluate_rag.py --validate-dataset` | 无 |
| 真实评估 | 脚本 + RAGAS | 见第 12 章 | MySQL/Milvus/模型/LLM |
| 压测 | Locust | 见 13.5 | 全套服务 |

设计原则：**单元测试不依赖真实模型、MySQL、Milvus、Redis**，保证 CI 稳定；真实链路由评估、E2E、压测和手工验收覆盖。

### 13.2 后端测试如何隔离外部依赖

见 [tests/conftest.py](../tests/conftest.py)：

- 内存 SQLite 替代 MySQL；
- `fakeredis` 替代 Redis；
- `FakeVectorStore` 替代 Milvus；
- Fake/关闭模型推理；
- `httpx.AsyncClient` 直接打 FastAPI 应用。

因此新增测试时不要连接真实服务，也不要加载真实模型。

### 13.3 新增测试的写法

```python
@pytest.mark.asyncio
async def test_xxx():
    # 1. 构造最小输入
    # 2. 调用纯函数或 service
    # 3. 断言输出与关键副作用
    ...
```

建议：

- 纯函数优先直接测（`fusion`、`dedup`、`evaluation`、`sse`）；
- 服务层测试用 fake 依赖；
- 每个新配置项至少测“合法解析 + 非法值报错”；
- 每个失败语义至少测“异常时降级/抛错”；
- 测试名写清场景，例如 `test_same_content_different_filename_is_skipped`。

### 13.4 修改后的验收顺序

```bash
# 1. 后端全量
uv run python -m pytest tests/ -v

# 2. 前端单元与构建
cd frontend && npm run test && npm run build

# 3. 数据集校验
uv run python scripts/evaluate_rag.py --validate-dataset
```

涉及前端页面时，还必须启动服务，用 Playwright MCP 实际打开页面验证，再通知用户验收。

### 13.5 压测

```bash
# 安装压测依赖组
uv sync --group loadtest

# 创建临时用户与会话（要求存在可检索的公共 KB）
uv run python scripts/prepare_load_test.py --users 20

# Windows 中文环境加 PYTHONUTF8=1
PYTHONUTF8=1 uv run locust -f scripts/locustfile.py --headless \
  -u 20 -r 2 -t 60s --host http://127.0.0.1:8000

# 清理
uv run python scripts/prepare_load_test.py --cleanup
```

关注：

- `SSE_FIRST`：首 token 延迟；
- `SSE_TOTAL`：整段回答耗时；
- 失败率：出现 `error`、缺 `meta`/`done`、回答为空；
- P95/P99；
- RPS。

注意：

- Locust 对 `stream=True` 的默认 `response_time` 只统计首包，不要当总耗时；
- 压测时建议 `CACHE_ENABLED=false`；
- 按并发数调大 `RATE_LIMIT_REQUESTS`，否则主要压到限流器；
- CPU-only 下重排是瓶颈，建议先单 worker。

| 症状 | 先看 | 常见原因 |

| 启动失败 | 日志首段异常 | MySQL 未启动、库权限、模型目录、非法配置 |

| 检索结果重复 | `retrieval_sources`、`parent_uid` | 判重阈值过高、旧版本未退出、重复上传 |
| 上传一直 pending | `async_tasks`、worker 日志 | worker 未启动、任务租约、数据库锁 |
| 上传 failed | `documents.error_message` | 解析器、MinerU、模型、Milvus |
| 回答没有引用 | `meta.sources` | 检索为空、阈值过滤、重排 drop |
| 普通用户看到缺口/评估 | 前端路由守卫、后端依赖 | `is_admin` 未设置、token 缓存 |
| 403 | 资源归属、`is_admin` | 访问他人私有库、非管理员访问管理接口 |
| 429 | 限流配置 | 并发过高、窗口太小 |
| RAGAS 不可用 | overlay 是否安装、API Key | 未用 `--with-requirements`、余额/网络 |

## 15. 安全与权限

### 15.1 角色与权限矩阵

| 能力 | 未登录 | 登录用户 | 资源创建者 | 管理员 |
|---|---:|---:|---:|---:|
| 注册/登录/验证码 | ✓ | — | — | — |
| 查看公共知识库 | — | ✓ | ✓ | ✓ |
| 检索公共知识库 | — | ✓ | ✓ | ✓ |
| 编辑/上传/删除公共库 | — | — | ✓ | — |
| 私有知识库全部操作 | — | — | ✓ | — |
| 对话 | — | ✓ | — | ✓ |
| 知识缺口列表/统计/更新 | — | — | — | ✓ |
| 评估看板/API | — | — | — | ✓ |
| 删除他人评估运行 | — | — | — | ✓ |

注意：管理员**不会**自动获得他人私有知识库的读写权限；权限仍按资源归属判断。

### 15.2 认证

- 图形验证码：4 位、一次性、Redis 存储、300 秒有效。
- 密码：bcrypt，成本 `BCRYPT_ROUNDS`；长度 6–64，UTF-8 不超过 72 字节。
- JWT：HS256，默认 24 小时；生产必须替换密钥。
- 账号不存在时仍执行一次等价耗时校验，降低用户名枚举风险。
- bcrypt 在 `asyncio.to_thread` 中执行，并受 `PASSWORD_HASH_CONCURRENCY` 限制。

### 15.3 前端与后端双重校验

- 前端路由守卫只负责体验，不构成安全边界；
- 后端每个资源操作都校验 `user_id` / `owner_id`；
- 管理接口统一 `Depends(get_current_admin)`；
- SSE 端点同样需要 Bearer token。

### 15.4 密钥与日志

- 日志和接口永不输出 API Key、JWT、密码；
- 密钥只做 set/unset 检查；
- `.env` 已在 `.gitignore`；
- 压测脚本只写 JWT 到 `loadtest/users.json`，不打印；
- 生产环境限制 CORS 来源，不要把开发用的 `localhost` 配置带到公网。

### 15.5 内容安全

- 前端 Markdown 使用 DOMPurify 清理，避免 XSS；
- 提示词明确要求模型只依据资料回答；
- 知识库文档本身是可信运营内容，但仍应避免上传包含敏感凭证的文件；
- 上传文件按扩展名和大小限制，原始文件不通过静态目录直接暴露。

## 16. 常见开发任务配方

### 16.1 新增一个 API

1. 在 `app/schemas/` 定义请求/响应模型；
2. 在 `app/api/routes/` 对应路由文件添加端点；

### 16.3 调整切块策略

涉及：

- `app/services/text_splitter.py`
- `Config.CHUNK_SIZE` / `CHUNK_OVERLAP` / `MIN_CHUNK_SIZE` / `PARENT_CHUNK_SIZE`
- `tests/test_text_splitter.py`

步骤：

1. 先明确目标（召回、上下文完整性、成本）；
2. 改参数或切分算法；
3. 跑单测；
4. 用评估集跑 `--retrieval-only` 对比 Hit/Recall/NDCG；
5. 对已有文档重建索引（旧分块不会自动重切）。

- `app/services/retrieval.py`

- `app/services/rag.py`

## 18. 动手实验

### 实验 1：追踪一次上传

**目标**：理解异步入库与 outbox。

步骤：

1. 上传一份新的 Markdown；
2. 立即查 `GET /api/documents/{id}`，记录状态；
3. 每 2 秒查一次，直到 `completed`；
4. 查 `async_tasks` 与 `vector_outbox` 的状态变化；
5. 查 `/documents/{id}/chunks` 和 `/parents`；
6. 在日志中找出解析、判重、向量同步的记录。

**预期**：状态 `pending → processing → completed`；任务 `pending → running → succeeded`；outbox 最终 `succeeded`。

### 实验 2：观察查询改写与策略

**目标**：理解“检索用改写问题、生成用原问题”。

步骤：

1. 先问一个完整问题，例如“满 99 元包邮的运费标准是什么？”；
2. 追问“那偏远地区呢？”；
3. 看日志中的 `original=` 和 `rewritten=`；
4. 看 `meta.rewritten_query` 与 `meta.retrieval_strategy`；
5. 构造一个多要素问题（“分别说明运费和发货时效”），观察是否走 `subquery`。

**预期**：追问被补全；多要素问题策略变化；HyDE/子查询文本不出现在 `sources`。

### 实验 3：关闭重排对比效果与延迟

**目标**：理解重排的收益与成本。

步骤：

1. 用当前配置跑 5 条评估题，记录 Hit/NDCG 和耗时；
2. `.env` 设 `RERANK_ENABLED=false`，重启；
3. 跑同一批题；
4. 对比指标与日志中的 `rerank=`。

**预期**：关闭后延迟下降，排序质量可能下降；记录差异。

### 实验 4：制造一次重排超时

**目标**：理解降级路径。

步骤：

1. 设 `RERANK_TIMEOUT_SECONDS=0.01`；
2. 提问；
3. 看日志“重排序超时 ... 按向量顺序降级”；
4. 观察 `sources` 中的 `rerank_timeout`（如果暴露）或回答质量；
5. 恢复配置。

**预期**：请求不失败，按向量顺序返回；不触发熔断。

### 实验 5：验证判重

**目标**：理解“改标点/文件名不产生重复文档”。

步骤：

1. 上传 `a.md`；
2. 复制一份，改文件名和标点，上传为 `b.md`；
3. 查文档列表与状态；
4. 修改正文中一个事实，再上传为 `c.md`；
5. 观察 `skipped` / `update` 与版本切换。

**预期**：只改格式 → `skipped`；实质修改 → 新版本，旧版本 `is_current=false`。

### 实验 6：新增一条评估样本

**目标**：理解评估数据与指标。

步骤：

1. 在 `data/evaluation/qa_eval.jsonl` 手写一条 `answerable=true`；
2. 跑 `--validate-dataset`；
3. 跑 `--limit 1 --retrieval-only`；
4. 查看报告中的 doc/section 指标；
5. 手写一条 `answerable=false`，观察它不进入检索均值。

**注意**：不要用脚本批量生成内容。

### 实验 7：新增一个只读 API

**目标**：走通后端开发流程。

建议：新增 `GET /api/knowledge_bases/{kb_id}/stats`，返回文档数、分块数、父块数。

步骤：

1. schema；
2. route + 权限；
3. service 查询；
4. pytest；
5. 更新接口文档；
6. curl 验证。

### 实验 8：压测冒烟

**目标**：理解瓶颈与指标口径。

步骤：

1. `uv sync --group loadtest`；
2. 准备 5 个用户；
3. 跑 20 秒；
4. 记录 SSE_FIRST、SSE_TOTAL、失败率；
5. 清理。

**预期**：CPU 环境下重排是瓶颈；浏览类接口明显更快。

## 20. 术语表

| 术语 | 含义 |
|---|---|
| RAG | 检索增强生成：先找资料，再让模型基于资料回答 |
| 分块（chunk） | 文档切分后的检索单元 |
| 父块 / 子块 | 父块保存章节上下文，子块用于向量检索；命中子块后补全父块 |
| Dense 向量 | 语义向量，BGE-M3 输出 1024 维 |
| Sparse 向量 | 词法权重向量，用于混合检索 |
| Hybrid | dense + sparse 混合召回 |
| BM25 | 经典词法检索算法，按词频和逆文档频率打分 |
| RRF | Reciprocal Rank Fusion，按排名倒数融合多路结果 |
| 重排序（Rerank） | Cross-Encoder 对候选逐条打分，精度高但慢 |
| HyDE | 先生成假设答案，再用假设答案召回 |
| 子查询 | 把多要素问题拆成多个查询分别召回 |
| 回溯 | 把具体问题改写成更宽泛的问题再召回 |
| 知识缺口 | 检索不到合格资料的问题记录 |
| 判重 | 通过归一化哈希/SimHash/相似度识别重复或新版本 |
| Outbox | 先写数据库、再可靠同步外部系统的模式 |
| SSE | Server-Sent Events，服务器单向流式推送 |
| TTFT | Time To First Token，首 token 延迟 |
| RAGAS | 官方 RAG 评估框架，本文用 0.3.0 |
| Faithfulness | 答案是否忠于检索资料 |
| Answer Relevancy | 答案是否切题 |
| Context Precision / Recall | 上下文的相关性与覆盖度 |
| Single-flight | 相同请求并发未命中时只回源一次 |
| 熔断 | 连续失败后快速失败，避免雪崩 |

## 21. 常见问题 FAQ

### Q1：为什么回答很慢？

按阶段看日志：

1. `prep`：意图 + 改写 + 策略；
2. `retrieval`：embed + vector + bm25 + rerank；
3. `ttft`：LLM 首包；
4. `latency`：总耗时。

CPU 环境下最常见瓶颈是重排（单候选约 1–1.3 秒）。优先降低 `RERANK_CANDIDATE_K`，其次 `RERANK_PASSAGE_CHARS` 和 `RERANK_MAX_LENGTH`。

### Q2：为什么资料明明在库里却检索不到？

依次检查：

1. 文档状态是否 `completed`、`is_current=true`；
2. 会话是否选择了该知识库；
3. 问题是否被改写丢失了关键约束（看 `rewritten_query`）；
4. 分块是否把关键事实切断（看 `/chunks`）；
5. 重排阈值是否过高（`RERANK_SCORE_THRESHOLD`）；
6. 是否被重排 `drop`；
7. BM25 是否开启。

### Q3：为什么会重复入库/重复检索？

- 入库：检查归一化哈希、SimHash 距离、`DOC_DEDUP_SIMILARITY`；只改格式应判 `skipped`。
- 检索：检查检索级去重阈值、父块 UID、旧版本是否 `is_current=false`。

### Q4：为什么普通用户能看到缺口/评估？

检查：

1. 后端是否返回 `is_admin=true`；
2. 前端路由守卫是否生效；
3. 直接访问 API 是否被 `get_current_admin` 拦截（应返回 403）。

### Q5：为什么回答没有引用？

`sources` 来自过滤后的合格命中。可能原因：

- 检索为空；
- 重排分数低于阈值；
- 重排失败且 `RERANK_FAILURE_MODE=drop`；
- 问候意图跳过检索。

### Q6：为什么知识缺口没有记录？

只有“非问候且过滤后为空”才记录。如果检索到了低质量但未触发过滤的结果，不会记缺口。检查 `_filter_qualified` 与阈值。

### Q7：为什么 RAGAS 指标是 `—`？

- 未使用 `--with-requirements scripts/eval_requirements.txt`；
- 没有配置裁判模型 API Key；
- 裁判调用失败/余额不足；
- 该题 RAGAS 返回 `NaN` 或缺行。

缺失值不是 0，报告会单独标注可用性。

### Q8：为什么第一次问答特别慢？

模型冷启动。启动预热会加载 intent / embedding / reranker；如果预热还没完成就提问，首个请求会承担加载耗时。日志中应看到“模型预热完成”。`MODEL_WARMUP_INTERVAL_SECONDS` 控制空闲保活。

### Q9：为什么上传后一直 pending？

- worker 未启动；
- 任务被其他进程领取但租约未过期；
- 数据库锁；
- 服务重启后任务回收尚未执行。

查 `async_tasks` 与日志。

### Q10：为什么 Milvus 报版本不兼容？

项目要求 `pymilvus 2.4.x`，混合检索依赖 2.4 的底层 handler。升级/降级都会触发启动校验失败。

### Q11：换嵌入模型要做什么？

- 向量维度必须仍是 1024，或同步修改 schema；
- 重建 collection；
- 所有文档重新入库；
- 清空检索/回答缓存；
- 重新跑评估。

### Q12：为什么评估结果不能跨运行直接比较？

必须保持：

- 数据集 SHA-256 一致；
- 裁判模型一致；
- 指标集合一致；
- 聚合口径一致（可回答/不可回答是否分开）；
- 样本数足够。

## 结语

学习这个项目最重要的不是记住每个函数，而是记住四条主线：

1. **数据怎么进来**：解析 → 判重 → 父子分块 → 向量化 → outbox → 版本切换。
2. **问题怎么被回答**：意图 → 改写 → 策略 → 召回 → 融合 → 重排 → 过滤 → 提示词 → 流式生成。
3. **效果怎么被证明**：检索指标 + RAGAS + 评估看板 + 压测。
4. **系统怎么不出错**：MySQL 真相源、版本化缓存、持久化任务、outbox、降级矩阵、日志与指标。

掌握这四条线，再去看任何单个文件，都会知道它在这张图上的位置。
