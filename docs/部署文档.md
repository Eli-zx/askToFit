## 一、部署架构

```text
浏览器
  │ 80/443
  ▼
web（nginx：静态站点 + /api 反向代理，SSE 关闭缓冲）
  │ http://api:8000
  ▼
api（uvicorn，FastAPI）
  ├── MySQL 8        业务数据、会话、评估记录
  ├── Redis          验证码、意图/向量/检索/回答缓存、限流
  ├── Milvus 2.4     分块向量（dense + sparse）
  ├── /models        只读挂载：bge-m3、bge-reranker-v2-m3、intent-bert
  ├── /app/uploads   上传原始文件
  └── /app/logs      应用日志
```

要点：

- 模型**不打进镜像**，通过 volume 挂载，镜像体积可控；
- 前端 nginx 必须关闭 SSE 代理缓冲，否则回答会等生成结束才一次性出现；
- MySQL / Redis / Milvus 不在 compose 内，需提前准备并在 `.env` 中配置地址。

## 二、环境要求

| 组件 | 版本/建议 | 说明 |
|---|---|---|
| Python | 3.13 | 由 `uv` 管理，见 `.python-version` |
| uv | 0.9.x | 镜像内固定 0.9.7 |
| Node.js | 20 | 见 `.nvmrc`，仅构建前端需要 |
| MySQL | 8.x | 字符集 `utf8mb4` |
| Redis | 6+ | 验证码、缓存、限流 |
| Milvus | 2.4.x | **pymilvus 必须 2.4.x**，否则混合检索启动即报错 |
| 内存 | 建议 ≥16 GB | BGE-M3 + reranker + BERT + Milvus 客户端 |
| 磁盘 | 模型约 4–6 GB，另加上传与日志 | |
| Docker | 24+（部署方式） | Compose v2 |

CPU 与 GPU：

- 默认 `EMBEDDING_DEVICE=cpu`、`INTENT_DEVICE=cpu`；
- 有 CUDA 时可改为 `cuda`，重排序与向量化会明显加速，但镜像需要换 GPU 版 torch；
- 当前 Dockerfile 使用 `UV_TORCH_BACKEND=cpu`，不带 CUDA。

## 三、准备模型

目录结构：

```text
models/
├── bge-m3/
├── bge-reranker-v2-m3/
└── intent-bert/
```

要求：

- `bge-m3`：BGE-M3 完整模型目录（含 config、tokenizer、权重）；
- `bge-reranker-v2-m3`：FlagEmbedding 可加载的重排序模型；
- `intent-bert`：项目微调后的意图分类模型，可用 `uv run python scripts/train_intent_bert.py --epochs 8` 重新训练生成。

路径可用环境变量覆盖：

```text
BGE_M3_PATH=models/bge-m3
BGE_RERANKER_PATH=models/bge-reranker-v2-m3
INTENT_MODEL_PATH=models/intent-bert
```

相对路径按项目根目录解析。启动时会校验目录，缺失直接失败（`VALIDATE_MODELS_ON_STARTUP=true`）。首次部署尚未下载模型时可临时设为 `false`，但问答会失败。

模型预热在启动后后台进行：依次加载 intent-bert、bge-m3、reranker，并各跑一次极短推理。首次加载本机约：intent-bert 22 秒、bge-m3 4 秒、reranker 4.5 秒。之后按 `MODEL_WARMUP_INTERVAL_SECONDS`（默认 600 秒）周期保活，避免长时间空闲后首个问答出现数倍冷启动开销。预热完成前服务可响应，但首个问答会更慢。

## 四、配置环境变量

复制模板：

```bash
cp .env.example .env
```

**`.env` 含数据库密码、JWT 密钥和 API Key，禁止提交到版本库。** 项目已在 `.gitignore` 中忽略 `.env`、`.claude/`、`models/`。

### 4.1 必改项

| 变量 | 说明 |
|---|---|
| `MYSQL_*` | 数据库地址与账号 |
| `REDIS_*` | Redis 地址与密码 |
| `MILVUS_*` | Milvus 地址、数据库名、collection |
| `DEEPSEEK_API_KEY` / `DASHSCOPE_API_KEY` | 至少配置一个可用模型服务商 |
| `JWT_SECRET` | **生产必须替换**，至少 32 字节随机串 |
| `ADMIN_USERNAMES` | 管理员账号，逗号分隔；启动时幂等提升 |

### 4.2 生产建议

| 变量 | 建议 |
|---|---|
| `DEBUG` | `false` |
| `VALIDATE_MODELS_ON_STARTUP` | `true` |
| `RERANK_ENABLED` | `true`（CPU 性能不足时再评估） |
| `RERANK_CANDIDATE_K` | 5（默认）；单候选约 1.0~1.3 秒，优先降候选数 |
| `RERANK_TIMEOUT_SECONDS` | 6.0（默认）；超时按向量顺序降级，避免负载尖峰拖到 20 秒 |
| `RERANK_BATCH_SIZE` | 1（本机实测比 8 快） |
| `CACHE_ENABLED` | `true` |
| `RATE_LIMIT_ENABLED` | `true` |
| `LOG_LEVEL` | `INFO` |
| `CONVERSATION_RETENTION_DAYS` | 按合规要求，默认 90 |

完整参数见[配置参数手册](配置参数手册.md)。

### 4.3 数据库与 Milvus 初始化

无需手工建库建表：

- MySQL：启动时 `ensure_database` 创建数据库，`init_models` 建表，`ensure_schema_upgrades` 幂等补列/索引；
- Milvus：首次检索或入库时自动创建 database 和 collection（HNSW + 稀疏倒排索引）。

需要注意：

- MySQL 账号要有 `CREATE DATABASE` 权限，或提前手工建库；
- Milvus 的 database 名与 collection 名要和 `.env` 一致；
- 生产环境建议用迁移工具管理表结构，当前 `create_all + 补列` 只是轻量兼容方案。

## 五、本地启动

### 5.1 后端

```bash
uv sync
uv run uvicorn app.main:app --host 0.0.0.0 --port 8000 --workers 1
```

- 只有在本机改后端代码时才加 `--reload`；演示、压测或多人访问时不要加，reload 会重启进程并重新加载模型与进程内 BM25 索引。
- 单 worker（`--workers 1`）是演示默认值：每个 worker 各持有一份模型，多开会翻倍内存与重排序并发。

验证：

```bash
curl http://127.0.0.1:8000/api/health
# {"status":"ok","app":"AskToFit 售前智能导购","version":"0.2.0"}
```

接口文档：<http://127.0.0.1:8000/docs>

### 5.2 前端开发服务器

```bash
cd frontend
npm install
npm run dev
```

访问 <http://127.0.0.1:5173>。Vite 已将 `/api` 代理到 `http://127.0.0.1:8000`。
前后端均绑定 `0.0.0.0`，同一局域网内可用本机 IP 访问（如 `http://192.168.1.10:5173`）。
开发模式与构建预览共用 5173，二者不能同时启动；演示时先停掉 `npm run dev`。

### 5.3 前端生产预览

```bash
cd frontend
npm run build
npm run preview
```

预览地址固定为 <http://127.0.0.1:5173>（与演示域名一致）。本项目的演示与浏览器验收使用该端口；`strictPort` 会在端口被占用时直接报错，避免域名指向错误的端口。

### 5.4 首次初始化

1. 打开前端，获取验证码并注册；
2. 创建知识库；
3. 上传文档，等待状态从 `pending` → `processing` → `completed`；
4. 创建会话并提问；
5. 如需评估看板：`uv run python scripts/set_admin.py --username <账号>`，重新登录。

如需演示数据，按[客户演示指南](客户演示指南.md)准备 9 份手写业务文档；项目要求训练/演示数据逐份手写，不使用脚本生成内容。

## 六、Docker 镜像与 Compose 部署

### 6.1 镜像说明

| 镜像 | 构建文件 | 内容 |
|---|---|---|
| `asktofit-api` | 根 `Dockerfile` | python:3.13-slim + uv + 运行时依赖，非 root 用户，端口 8000 |
| `asktofit-web` | `frontend/Dockerfile` | node:20 构建 + nginx:1.27 托管，端口 80 |

API 镜像：

- `uv sync --locked --no-dev`，只装运行时依赖；
- CPU 版 torch，不带 CUDA；
- 不包含 `models/`、`.env`、`uploads/`、`logs/`；
- 启动命令 `uvicorn app.main:app --host 0.0.0.0 --port 8000`。

前端镜像：

- 构建产物在 nginx；
- `/api/` 代理到 `api:8000`；
- `proxy_buffering off`、`proxy_cache off`、读超时 300 秒，保证 SSE；
- SPA 路由回退到 `index.html`。

### 6.2 本地构建

```bash
docker build -t asktofit-api:local .
docker build -t asktofit-web:local frontend
```

### 6.3 服务器部署

前提：服务器已安装 Docker Compose，目录中包含：

```text
docker-compose.deploy.yml
.env
models/
uploads/     （可空）
logs/        （可空）
```

步骤：

```bash
export GHCR_OWNER=<github 用户名或组织>
export IMAGE_TAG=latest          # 或具体版本 tag
docker compose -f docker-compose.deploy.yml pull
docker compose -f docker-compose.deploy.yml up -d
```

检查：

```bash
docker compose -f docker-compose.deploy.yml ps
docker compose -f docker-compose.deploy.yml logs -f api
curl http://127.0.0.1:8000/api/health
curl -I http://127.0.0.1/
```

访问 `http://<服务器地址>/`。API 的 8000 端口按需对外开放；生产建议只暴露 80/443，由 nginx 统一代理。

### 6.4 Compose 关键配置

```yaml
api:
  image: ghcr.io/${GHCR_OWNER:-asktofit}/asktofit-api:${IMAGE_TAG:-latest}
  env_file: [.env]
  environment:
    BGE_M3_PATH: /models/bge-m3
    BGE_RERANKER_PATH: /models/bge-reranker-v2-m3
    INTENT_MODEL_PATH: /models/intent-bert
  volumes:
    - ./models:/models:ro
    - ./uploads:/app/uploads
    - ./logs:/app/logs
  ports: ["8000:8000"]
  restart: unless-stopped

web:
  image: ghcr.io/${GHCR_OWNER:-asktofit}/asktofit-web:${IMAGE_TAG:-latest}
  depends_on: [api]
  ports: ["80:80"]
  restart: unless-stopped
```

注意：

- `models` 只读挂载，容器内不能写；
- `uploads` 与 `logs` 必须持久化，否则重建容器会丢文件与日志；
- compose 里的 `environment` 会覆盖 `.env` 中的模型路径，这是刻意为之；
- MySQL / Redis / Milvus 是外部服务，`localhost` 在容器内指向容器自身，必须写可达的主机名或 IP。

### 6.5 HTTPS

前端 nginx 默认只监听 80。生产建议在宿主机或外层负载均衡终止 TLS，再转发到 web 容器；如直接改 nginx，请保留 SSE 相关配置。

## 七、CI/CD

### 7.1 CI（`.github/workflows/ci.yml`）

触发：`push`、`pull_request`。

| Job | 内容 |
|---|---|
| Backend tests | `uv sync --locked` + `pytest tests/ -v` |
| Evaluation dataset | 校验 JSONL、断言 60 条与必填字段 |
| Frontend tests and build | `npm ci`、`npm run test`、`npm run build` |
| Docker build | 构建 API 与前端镜像，`push: false` |

CI 不连接 MySQL / Milvus / Redis，不使用 Secrets，不跑真实检索、RAGAS 与 E2E。

### 7.2 CD（`.github/workflows/cd.yml`）

触发：推送 `v*` tag，或手动 `workflow_dispatch`。

流程：

1. 登录 GHCR；
2. 生成镜像标签（版本、`latest`、`sha-*`）；
3. 构建并推送：
   - `ghcr.io/<owner>/asktofit-api`
   - `ghcr.io/<owner>/asktofit-web`
4. **不自动部署**，服务器侧手动 `pull && up -d`。

发布示例：

```bash
git tag v0.2.0
git push origin v0.2.0
```

镜像 owner 统一转小写。若 GHCR 包为私有，服务器需先 `docker login ghcr.io`。

## 八、升级与回滚

### 8.1 升级

```bash
export IMAGE_TAG=v0.2.1
docker compose -f docker-compose.deploy.yml pull
docker compose -f docker-compose.deploy.yml up -d
docker compose -f docker-compose.deploy.yml logs -f api
```

升级前：

- 备份 MySQL；
- 确认 `uploads/` 与 `logs/` 已持久化；
- 确认新版本配置项在 `.env` 中已补齐（缺失项有默认值，但行为可能变化）。

### 8.2 回滚

```bash
export IMAGE_TAG=v0.2.0
docker compose -f docker-compose.deploy.yml pull
docker compose -f docker-compose.deploy.yml up -d
```

注意：

- 镜像回滚不等于数据回滚；如果新版本做过不可逆的表结构变更，需要同时恢复数据库备份；
- 当前 schema 升级只做“加列/加索引”，通常可向前兼容；
- 回滚后清理 Redis 缓存（尤其检索/回答缓存），避免旧版本读到新格式数据。

### 8.3 重建索引

模型、分块参数或向量维度变化后，需要重新入库：

- 单文档：调用 `POST /api/documents/{doc_id}/reindex`；
- 全库：逐文档重建，或新建知识库重新上传；
- 重建失败时旧分块与向量仍保留，检索不中断。

## 九、上线检查清单

### 配置

- [ ] `.env` 未提交，权限仅服务账号可读
- [ ] `JWT_SECRET` 已替换为随机长串

- [ ] `GET /api/health` 返回 ok

## 十、常见部署问题

| 现象 | 原因 | 处理 |
|---|---|---|
| 启动报“本地模型目录缺失” | 路径不对或未挂载 | 检查 `BGE_M3_PATH` 等与 volume |
| 启动报 MySQL 连接失败 | 容器内 `localhost` 指向自身 | 改用宿主机名/IP，确认端口开放 |
| 混合检索报 pymilvus 版本错误 | 安装了 2.5+ | 固定 `pymilvus 2.4.x` |
| 回答一次性出现 | nginx 缓冲未关闭 | 保留 `proxy_buffering off` 与 `X-Accel-Buffering: no` |
| 上传后一直 `pending` | 后台任务未执行/进程重启 | 查看日志 `文档入库`，必要时重新入库 |
| 上传后 `failed` | 解析失败、OCR 缺失、切块为空 | 看 `error_message` 与日志 |
| 页面刷新 404 | nginx 未做 SPA fallback | `try_files $uri $uri/ /index.html` |
| 首个回答特别慢 | 模型尚未预热完成 / 空闲后冷启动 | 等预热日志出现，或调整重排序参数 |
| 429 过多 | 限流阈值过低 | 调整 `RATE_LIMIT_REQUESTS` |
| 检索结果旧 | 缓存未失效 | 检查变更路径是否调用 `invalidate_search_caches` |

更多排查见[运维与故障排查](运维与故障排查.md)。
